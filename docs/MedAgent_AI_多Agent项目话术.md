### 0. 项目描述：按五点组织面试介绍

#### ① 为什么做项目：业务痛点与商业价值

我做的是面向医院内部医生和药师的临床辅助工作台。选这个场景，是因为药品资料、患者档案、临床指南和检验信息分布在不同入口；一次用药审核可能既要看患者的过敏史和当前用药，又要查相互作用或禁忌，医务人员需要来回查找、整理结果。

这个项目把这些查询变成一次自然语言请求：系统先确认员工能访问哪位患者，再拆出业务任务、调用对应工具，最后汇总结果供临床人员复核。对机构的价值是减少重复检索和信息整理，统一患者访问与写入控制，并保留咨询、工具操作和审计记录，方便核对过程与排查问题。

目前有工程实现和本地验证记录；节省多少工时、降低多少差错，需要真实业务试点后测量。面试中可以讲清价值目标，量化成果使用后面的工程评测数据。

#### ② 项目架构：技术选型、职责划分与业务流程

我把系统分成工作台、业务入口、协调与专科执行、工具与数据四层。模型负责识别或生成调用请求，服务端负责权限、执行预算、结果检查和持久化。

| 层次 | 技术选型与职责 | 为什么这样选 |
|---|---|---|
| 工作台与入口 | Streamlit（交互工作台）＋ FastAPI（接口框架）；登录、患者选择、请求校验和 SSE（服务器发送事件） | 用较少界面代码验证业务流程，并通过流式事件呈现执行状态与回答 |
| 路由与协调 | 正则 → 本地 BERT（本项目用于意图分类）→ 本地 BGE-M3（向量模型）→ 云端大语言模型；`MedicalCoordinator` 与 `Planner` | 明确任务尽早在本地识别，复杂表达继续后续层；规划结果由代码校验 |
| 专科执行 | 症状、药品、指南三个 A2A（智能体间通信）服务；LangChain `create_agent` 工具循环 | 按业务职责绑定工具白名单，各专科分别维护本轮任务、消息和调用预算 |
| 工具与数据 | FastMCP（工具服务）、SQLAlchemy（数据库访问）、Alembic（数据库迁移）；关系数据库与可选 Redis | 集中校验工具调用；数据库保存业务和操作记录，Redis 支持跨入口实例的近期会话与锁 |

三个专科使用同一个 `SILICONFLOW_MODEL` 云端模型配置，分别发起请求；本地 BERT 和 BGE-M3 用于路由。生产参考数据库为 MySQL，本地默认可使用 SQLite；没有配置 Redis 时，近期会话使用进程内缓存。

以“解读检验指标，同时查阿司匹林说明书”为例，主流程是：**员工登录并选择授权患者 → 入口核验身份与患者范围 → 急症、业务范围检查 → 多意图识别与缺信息澄清 → 生成并校验专科计划 → 通过 A2A 依次交给专科 → 专科通过 MCP 调用获准工具 → 汇总工具结果 → 保存本轮记录 → 发送完成事件。** 当前跨专科串行执行，前步结果不会自动成为后步输入；最终统一汇总。

#### ③ 项目中遇到的问题：四个可展开的案例

讲每个问题时按“触发场景 → 原因 → 解决方案 → 验证结果”展开。下面的例子用于说明触发条件，修复依据见链接。

**问题一：单标签路由提前结束，遗漏同一句话中的其他任务。** 例如请求同时包含药品查询与检验解读，单标签 BERT 即使对药品意图给出高分，也不能证明已经识别完整请求。问题在于把“某个标签可信”当成“整句话只有一个任务”。处理方案是增加多任务线索检查：规则只命中一个意图且存在多任务线索时继续后续层，BERT 不直接结束；向量层保留满足阈值和分差条件的多个候选，只得到一个时继续交大模型核对。规划阶段再检查必要专科是否完整、有无重复或额外专科。现有回归覆盖用药上下文和显式多任务保留；33 条固定路由回归的意图集合严格匹配率为 100%。[路由与规划代码](../backend/agents.py)、[专项测试](../tests/test_agents.py)、[回归摘要](../evaluation/intent_regression_summary.json)。

**问题二：只在业务入口鉴权，内部服务仍可能被绕过。** 直接调用 A2A 或 MCP，或者员工权限在登录后发生变化，都要求执行点重新确认权限。处理方案是使用独立密钥签发短期受限委托，绑定目标服务、员工、患者、请求、专科、工具和批准动作；专科重读可信档案，工具执行前重新检查数据库中的员工状态、角色和患者授权，写工具额外校验本轮确认。现有测试覆盖匿名调用、伪造令牌、令牌跨服务使用和授权撤销。[历史修复记录](audit-2026-09-26.md)、[委托校验](../backend/service_auth.py)、[工具授权](../backend/mcp_security.py)、[权限回归](../tests/test_enterprise_boundaries.py)。

**问题三：写接口超时后重试，可能重复创建转诊草稿。** 医院侧可能已经写入，只是成功响应丢失；因此超时不能直接等同于失败。处理方案是先校验参数，再按“员工＋请求标识＋工具”在数据库登记唯一操作记录，同时保存患者和参数摘要，然后执行写工具。已完成的同键同参数调用复用结果，参数冲突拒绝；执行中或结果未知的操作阻止重发，转诊写接口不自动重试，需要查询操作状态并核对 HIS（医院信息系统）。现有测试验证完成结果重放和未知结果拦截。换一个请求标识仍可能重复，跨系统的恰好一次执行还依赖医院接口契约。[历史修复记录](audit-2026-09-26.md)、[操作记录实现](../backend/mcp_security.py)、[重复写回归](../tests/test_enterprise_boundaries.py)。

**问题四：流式文字已经显示，保存失败却被用户当成成功。** 如果把模型结束当成业务完成，数据库提交失败或后续会话存储失败就会造成页面状态与持久化结果不一致。处理方案是将增量文字与完成事件分开：业务入口接到协调器的完成信号后，先完成本轮分支要求的数据库、会话和阶段记录保存，再向页面发送 `done`；前端遇到 `error` 或断流且未收到 `done`，不确认完成。现有回归检查数据库提交失败时不发送完成事件。数据库已提交后 Redis 失败不会回滚此前写入，涉及写工具仍需查询操作状态，不能直接重做。[历史修复记录](audit-2026-09-26.md)、[流式入口](../backend/main.py)、[提交失败回归](../tests/test_audit_regressions.py)。

### 1. 一分钟开场：做什么、为什么做、重点是什么

我做的是面向医院医生和药师的临床辅助工作台。一次用药审核需要看患者档案、查药品资料，再整理依据；工作台把这些步骤组织在同一个入口，希望减少切换系统、重复录入已有资料和手工汇总，让医生和药师把时间用于复核结果。

我主要做意图路由、三个专科 Agent 的编排和受控工具调用。模型提出怎么查，服务端校验能查谁、能用哪些工具；Agent 调用写工具前，服务端还要核验员工对本轮动作的批准。专科查询根据工具结果生成回答，最终由医生或药师复核。

目前完成本地工程验证，33 条固定路由回归的意图集合严格匹配率为 100%。真实医院接入和试点验收仍待完成，后续重点衡量高频任务每天实际省下多少时间、质量是否保持，以及收益能否覆盖接入和使用成本。

**以下内容用于追问，开场不必全部展开。**

**被追问“医院为什么愿意用”时：** 医生和药师关心能否少切换入口、少重复录入、少整理资料，同时结果有依据、复核方便；院方还要看接入现有流程的难度、隐私与安全，以及培训、维护和模型调用成本。不存在达到某个提效比例就必然采购的统一门槛，应把单次净省时与实际使用频率一起算，具体见下方假设算例。释放的时间可以用于患者服务或减少加班，也不自动等于减少人员成本。

**被追问“效率怎么衡量”时：** 我会选定同类任务，在可比条件下对比原有人工操作与使用工作台两种流程，记录从开始查询到完成复核的总时间、切换入口与重复录入次数，并同时检查结果完整性和人工纠错量。耗时降低比例按“（原流程平均耗时－工作台平均耗时）÷原流程平均耗时”计算，失败后的重做和人工修正时间也计入。先确认结果质量，再计算时间节省；33 条路由回归的正确率和健康接口压测吞吐量都不能代替这项业务测量。

**被追问“具体目标是多少”时：** 暂定试点目标是在结果完整性不降低、人工纠错量不增加的前提下，将同类任务从查询到完成复核的总耗时降低 20%。20% 没有当前业务实测或外部研究作为依据，需在取得基线后评估可行性。仅作假设算例：原流程平均用时 10 分钟，目标降到 8 分钟；每次省 2 分钟，每人每天使用 10 次，就净省 20 分钟。这组数字均未在本项目测得，不可写成已完成的试点结果或简历业绩，也不能外推为整体诊疗效率或医疗质量改善。

### 2. 两分钟主链路：跟着一次药品查询讲

以医生查询阿司匹林说明书为例。医生先登录工作台、选择已授权患者，再提交问题。工作台把患者标识、问题、会话标识、请求标识和本次批准的写动作发给聊天流式接口。

入口使用 FastAPI（接口服务框架），先检查 JWT（JSON Web Token，本项目用于员工身份认证），再查数据库中的员工状态、当前角色和患者授权。权限不通过，请求就在入口结束。

接着，主协调器先用急症规则检查是否需要提示启动院内急救流程，再由 Domain Guard（业务范围守卫）判断请求是否属于本系统支持的院内工作，然后识别具体意图。TaskReadinessGuard（任务参数澄清守卫）对几类典型的缺信息请求先追问，例如“这个药能吃吗”缺少药名、“解读报告”没有报告内容。范围守卫检查业务是否支持，入口和工具服务检查访问权限。

普通药品查询可以直接交给 DrugAgent（药品智能体）。主协调器通过 A2A（智能体间通信）传任务和受限委托；专科验证身份后重新读取可信患者档案，再用 MCP（模型上下文协议）调用药品查询工具。每次工具执行前，服务端再次核验员工、患者和工具范围。

专科至少有一次成功工具调用且没有工具失败，才能返回正常结果。协调器随后用汇总提示词调用与专科相同配置的云端模型，根据专科结果逐段生成最终回答，供临床人员复核。API（应用程序接口）保存咨询、审计和会话状态，最后发送 done（完成事件），页面才确认本轮完成。工具失败时，系统记录错误并返回失败提示。

**理解主线：** 工作台提问 → 入口授权 → 守卫与意图路由 → 专科调用受控工具 → 汇总证据 → 保存后确认完成。

**代码对照：** 聊天流式接口是 `POST /api/chat/stream`；药品查询工具是 `query_drug_info`。讲解时说中文功能名即可。

### 3. 四层路由：为什么这样设计

我的意图路由是 Regex（正则规则）、本地 BERT（本项目用于意图分类）、本地 BGE-M3（文本向量模型）和云端 LLM（大语言模型）四层级联。明确表达先由规则处理，稳定单意图用分类模型，近义表达用向量匹配，剩下的复杂表达再交给大模型，兼顾成本、延迟和可解释性。前一层接受后通常就结束，不是四层全部执行或一起投票。

BERT（本项目用于意图分类）对十个意图输出 Softmax（归一化指数函数）分数，只取最高分标签。最高分默认至少为 0.95，且请求没有命中多任务提示规则时，系统才接受该标签。向量层使用 BGE-M3 编码问题，与带意图标签的示例句比较余弦相似度；这些示例句就是“意图原型”，不是医学指南文档。单任务取最高分意图，默认相似度至少为 0.78。

请求命中多任务提示规则时，向量层最多选择三个意图：每个候选的分数都必须至少为 0.78，且与最高分的差不超过 0.04。如果只选出一个意图，系统仍交给大模型核对是否漏了任务。这里的 0.04 用来筛选多意图候选，不表示系统会普遍拒绝第一、第二名接近的单任务结果。

正则规则命中多个意图时直接返回；只命中一个意图且没有多任务提示时，也直接返回。若请求含“同时、另外”等多任务线索而规则只识别出一个意图，系统继续后续层，避免遗漏其他任务。大模型兜底必须返回已注册的意图标签，后端校验结果后才用于路由。若大模型调用失败但先前有规则命中，系统返回规则结果，并在路由记录中标记 `llm_failed`；没有可用规则结果则报错，这不是自动切换到另一个大模型。

各层分数含义不同，不能直接选最大分，也不能把分类分数当医学正确率。级联的风险是前层错误接受请求后，后层没有纠错机会，所以评测还要看漏意图和错误提前退出。

### 4. 十类任务、三个专科、十四个工具

十类是系统识别的业务意图；三个专科是分别执行症状、药品、指南检验任务的 Agent；十四个是这些 Agent 可以申请调用的工具。多个意图可以归同一个专科，系统按专科职责提供工具白名单，再根据本轮授权过滤可执行工具。

**模型与 Agent 的关系：** 模型负责根据输入生成回答或工具调用请求；Agent 是围绕该模型建立的执行程序，包含任务、提示词、工具、消息历史、调用预算和结果检查。本项目三个专科复用 `MCPToolAgent` 这一实现类，使用不同的专科名称和工具白名单，分别在三个 A2A（智能体间通信）服务中运行。每次专科任务都会创建自己的 `create_agent` 工具循环，并单独向云端模型发起请求；不会把三个专科的任务放在同一个工具循环里执行。

三个专科都读取 `SILICONFLOW_MODEL` 配置，按仓库默认配置启动时使用同一个模型标识。这里的“同一模型”指调用同一种配置的模型能力，不表示共享一个本地模型对象、同一段对话或云端同一个推理实例。本地 BERT（本项目用于意图分类）和 BGE-M3（文本向量模型）用于意图路由，不是三个专科各自的大语言模型。

| 专科                  | 对应意图                                 | 工具及中文含义                                                                                                                                                |
| ------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| SymptomAgent（症状智能体） | 症状评估、院内分诊建议、转诊协同                     | analyze_symptoms（症状分析）、suggest_department（科室建议）、get_disease_info（疾病资料）、load_patient_history（读取病史）、save_patient_history（保存病史）、generate_referral（生成转诊草稿） |
| DrugAgent（药品智能体）    | 药品信息查询、用药审核                          | query_drug_info（药品资料查询）、check_drug_interaction（相互作用检查）、check_contraindications（禁忌检查）、query_drug_alternatives（替代药资料查询）                                  |
| GuideAgent（指南智能体）   | 临床指南检索、临床知识查询、检验结果辅助解读、检查报告辅助解读、随访管理 | search_guidelines（指南检索）、interpret_lab_results（检验数据辅助解读）、get_treatment_protocol（诊疗路径查询）、save_medical_record（保存辅助记录）                                     |

“检验结果辅助解读”主要针对一项或一组检验指标，例如解释白细胞、血糖或转氨酶结果；“检查报告辅助解读”在本项目中指整份报告的综合解读，例如梳理体检、CT 或肝功能报告的重点。这里按请求的解读范围区分，不能简单理解为“化验”和“影像”两个互斥类别：同一份肝功能报告，询问某个指标和要求整份报告解读可能对应不同意图。两者都交给 GuideAgent，意图标签本身不代表存在两套独立的解读工具。

总共 14 个注册工具，其中 11 个调用配置的外部接口，3 个读写项目数据库。指南检索采用外部指南服务接口：`search_guidelines` 把疾病和关键词发送到 `GUIDELINE_API_BASE_URL` 指定服务的 `/v1/guidelines/search`。接入方提供指南内容和检索结果，项目负责受控调用与结果整理。

药品和指南专科的病史背景来自服务端读取的患者档案。检验解读以请求提供的项目、数值、单位和参考范围为输入，通过 LIS（检验信息系统）解释接口获取结果。意图识别负责确定业务目标，专科通过本轮允许的工具执行相应任务。

### 5. Planning（任务规划）和 ReAct（推理与行动）：外层分任务，内层选工具

如果一个问题包含检验解读和药品查询，主协调器调用 `Planner.plan`，让云端模型根据问题和已识别意图生成专科任务列表，例如先交给 GuideAgent（指南智能体）解读检验，再交给 DrugAgent（药品智能体）查药品。计划最多三步，每个必要专科只执行一次；服务端校验有没有漏专科、加无关专科或重复步骤。结构不合法就回退为受控计划，网络调用失败仍按失败处理。

文档中的 Planning Agent（规划角色）对应协调器进程内的 `Planner.plan` 方法：它使用与专科相同的 `SILICONFLOW_MODEL` 配置，以规划提示词单独发起模型请求，返回结构化任务列表。规划角色作为协调器内部方法运行，三个专科则通过独立 A2A 服务执行工具循环。最终汇总由 `Planner.synthesize` 或 `Planner.synthesize_stream` 另行调用同一配置的模型完成，规划、专科执行和汇总是不同阶段的模型请求。

当前跨专科按顺序串行执行，前一个结果没有自动传给后一个，最终统一汇总。用药审核、检查报告辅助解读和转诊协同等单标签复杂任务也可能进入规划，因此不能简单说“单意图一定不规划”。

专科内部用 LangChain（大模型应用框架）的 `create_agent` 执行 ReAct（推理与行动）：模型选择工具，服务端执行，结果作为 Observation（观察结果）返回，模型再决定继续查询还是回答。模型调用和工具调用分别最多六次，同工具、同参数的重复调用会被拦截；没有成功工具证据或出现工具失败，就不接受正常专科结论。

这里可展示的 Trace（调用轨迹）是工具与状态摘要。Reasoning（推理）指模型决定下一步动作，不需要展示内部思维链。

### 6. A2A（智能体间通信）、MCP（模型上下文协议）和权限：谁负责哪一段

A2A（智能体间通信）负责协调器和专科之间交任务，MCP（模型上下文协议）负责专科和工具服务之间连接，Function Calling（函数调用）负责模型选择工具名称和参数。患者授权由服务端实现。

员工 JWT（JSON Web Token，本项目用于员工身份认证）用于访问业务入口。内部委托使用 `INTERNAL_SERVICE_SECRET` 签发短期 Delegation（受限委托），与员工 JWT 使用的 `SECRET_KEY` 分开。委托令牌限定员工、患者、请求、专科、工具和批准动作。A2A（智能体间通信）与 MCP（模型上下文协议）分别校验 Audience（目标服务）、签名和有效期，再查实时权限。A2A 传当前任务、患者标识和裁剪历史，可信患者档案由专科重新读数据库。

“专科调用受控工具”具体分为两步：专科程序先按 `AGENT_TOOLS` 白名单、本轮批准动作与父 A2A 委托工具范围的交集筛选工具，只将筛选后的工具绑定给模型，并把允许的工具写入 MCP 委托令牌；签发器同时拒绝改变父委托专科或扩大其工具范围；MCP 服务收到调用后，再检查工具是否在令牌范围内、员工是否有效、患者是否获授权，写操作还需满足角色和确认要求。模型提出的调用只有通过这些检查才会执行。

医生、药师按员工—患者授权表访问；医务管理员使用医院级只读范围；系统管理员的患者访问也需显式授权。员工账号和初始患者授权由运维脚本创建。工具执行和最终保存会重新查询数据库中的员工状态、角色和患者授权，使数据库中已生效的权限变更在后续校验时得到执行。

登录密码用 PBKDF2-SHA256（密码派生算法）60 万次迭代。默认同工号在固定 300 秒窗口内最多尝试十次，配置 Redis（共享内存存储）后跨入口实例共享；限流故障时拒绝登录。

这里的“主模型”是 `SILICONFLOW_MODEL` 指定的云端大语言模型，三个专科的工具选择、复杂任务规划、最终汇总，以及需要模型兜底的范围判断和意图识别都使用这一配置。本地运行的是意图分类 BERT 和意图原型匹配 BGE-M3。临床文本发送到云模型前经过规则脱敏。默认模型标识以仓库 `.env.example` 为准。

### 7. MCP 写工具、档案编辑与幂等：两条写入路径怎么处理

保存病史、保存辅助记录和生成转诊草稿是三个有副作用的 MCP 工具，员工在本轮批准相应动作后才开放。服务端还会按角色和患者校验；转诊仅医生可做。当前采用动作级确认，由请求中的 `approved_actions` 指定获准的工具动作。

工作台还支持医生、药师直接编辑已授权患者的档案。员工在“编辑档案”表单中填写姓名、年龄、性别、过敏史、既往病史和当前用药，点击保存后，由独立的 `PUT /api/patients/{patient_id}/profile` 接口处理。该接口校验身份、写角色、患者授权和 `ProfileUpdate` 字段约束，再把档案变更与 `profile_updated` 审计记录放在同一数据库事务中提交。这条路径由员工直接提交表单，三个 MCP 写工具则由 Agent 在本轮授权范围内申请执行。

三个 MCP 写工具先校验参数，再在数据库登记 `pending`（已登记、尚未确认结果）操作记录，利用唯一约束阻止同一操作重复执行，随后才调用工具。“员工、请求标识、工具名”生成 Idempotency Key（幂等键），记录同时包含患者和参数摘要。同键同参数已完成时返回记录的结果；参数不同则拒绝；状态为 `pending` 或 `unknown`（结果未知）时阻止重发。参数校验失败发生在登记前，因此修正参数后可以沿用原请求标识。

转诊超时可能是医院已写入但回复丢失，所以写接口不自动重试，要查操作状态并核对 HIS（医院信息系统）。本地去重保护同一请求，换新请求标识仍可能重复，跨系统恰好一次还依赖医院契约。正常转诊返回也必须有真实编号和待确认或草稿状态。

只读查询结束后，业务入口自动保存本轮咨询、审计与会话；这是系统的固定持久化步骤。`GET /api/operations/{request_id}` 查询当前员工在该请求下的三个 MCP 写工具操作状态，并重新核验患者权限。档案编辑由 REST 接口直接提交事务、记录审计，不进入 MCP 工具操作状态表；两条写入路径分别按各自的记录方式核对结果。

### 8. 会话、流式和持久化：什么才算成功

会话按员工、患者和会话标识隔离，默认 TTL（生存时间，即会话缓存的有效期）为 1,800 秒、最多二十条消息。整轮锁阻止同一会话同时提交；Redis（共享内存存储）锁默认租期 180 秒，释放时校验所有者，避免旧请求删除其他请求持有的锁。

关系数据库保存档案、授权、咨询、审计和工具操作状态；生产参考方案使用 MySQL，本地默认配置也支持 SQLite。配置 Redis 后，近期对话、阶段 Checkpoint（检查点）和整轮锁存放在 Redis；未配置时使用进程内的带过期缓存，不能跨实例共享。本地执行锁容量为 1000 个，容量满时拒绝新任务，避免驱逐活动会话锁。等待模型前结束入口读事务，回答生成后再开短事务复核权限和保存。关系数据库与会话存储先后写入，不会作为一个跨存储事务一起提交或回滚。

SSE（服务器发送事件）让页面持续接收事件：session（会话与请求标识）、meta（路由信息）、trace（工具轨迹）、card（展示卡片）、delta（增量文字）、done（完成确认）、error（失败提示）。专科完成工具后，最终汇总才原生流式出字；轨迹也主要在专科完成后整理。页面暂存文字，收到 done（完成事件）才确认已完成保存。

数据库提交后 Redis 写入失败，页面仍可能报错，已经提交的数据库记录不会回滚。未收到 `done` 只能说明客户端未确认完成，不能据此认定此前所有写操作都失败；涉及写工具时先查询本地操作记录，并核对实际写入目标。`done` 表示本次分支要求的持久化已结束：正常查询保存咨询、审计和会话，澄清或拒识分支会按规则跳过部分保存，不表示每个回答都创建咨询记录。

阶段检查点记录请求开始、专科完成、整轮完成或失败，用于追踪执行进度和排查中断位置。上一轮需要澄清时，系统把原请求和本轮补充拼接后重新识别，再决定本轮应执行的任务。

### 9. 超时、重试与熔断：失败怎么收住

默认模型客户端请求超时为三十秒，医院 HTTP 请求超时为十秒，API 一轮执行预算为一百二十秒，每次模型输出上限为 2,048 个 Token（词元）。客户端超时和整轮预算分别限制单次调用与整轮等待。MCP 写工具执行超时后保留未知状态，再核对实际执行结果。

医院只读调用遇到网络异常或 429、500、502、503、504，总计最多尝试三次（首次调用一次，失败后最多重试两次），采用指数退避；参数、权限和业务拒绝不重试，也不计入医院瞬态故障熔断。转诊写入和 A2A（智能体间通信）不自动重试，模型 SDK（开发工具包）自动重试也关闭。范围判断模型失败可转澄清，其他失败按对应错误路径结束。

Circuit Breaker（熔断器）在连续失败达到阈值后，暂时直接拒绝对该依赖的新调用；等待设定的恢复间隔后，只放行探测调用，探测成功再恢复正常请求。医院接口只把网络和指定 HTTP 瞬态错误计入故障，A2A 则按专科调用失败计数。当前每个进程维护自己的熔断状态，同一进程内可复用，多个服务进程之间不共享。

“覆盖率”是达到接受阈值的样本数占该评测集总数的比例；“接受准确率”只在这些被接受的样本中计算。例如 0.95 阈值接受 988 条且全部正确，不说明其余 12 条或真实临床问题都能答对。各集合的分母和目的不同，不能合成一个系统准确率。原型与评测数据做过完全相同文本的去重，但近义句或同一模板仍可能造成泄漏。

多意图历史评测中，`raw_top1_hit_rate=248/250` 只衡量首选标签是否在目标集合中，不是完整意图集合正确率；`accepted_coverage=42/250` 是独立 BERT 的阈值覆盖率，不是运行时多意图直接接受率。旧字段 `outcomes.multi_top1_hit=42` 同时要求达到阈值，`multi_top1_miss=208` 包括未接受样本，不能理解为 208 条未筛选分类错误。历史摘要中的字段说明针对该次记录，新评测脚本输出通用定义；历史数值未改写，也未在本次测试中重跑模型评测。

核对历史数据集指纹时须区分换行：BERT 与向量摘要的 `dataset_sha256` 对应本机 CRLF 文件，`repository_dataset_sha256` 对应 Git 仓库的 LF 文件。两者经核对仅换行不同；克隆后可按 LF 原始字节核对后一个字段。本机保留的两组 BERT 报告已按原始字节核对，均匹配 `source_report_sha256`；每组有两份同字节副本，哈希只能确认内容一致，不能区分最初生成文件与事后复制文件。报告属于被忽略的本地产物，未随仓库提供，因此仅凭克隆不能独立验证来源报告，核对报告也不等于重新运行历史模型评测。说明及复核命令见 [README 模型与指标复核](../README.md#克隆后的模型准备与指标复核)。

档案编辑 REST 回归覆盖医生与药师成功保存、管理员写入拒绝、授权撤销、账号停用、匿名请求、姓名/年龄/性别越界、病史条目长度与数量约束，以及提交失败时档案和审计共同回滚；该路径不生成 MCP ToolExecution。

协议测试通过真实本地 HTTP 连接 A2A/MCP 服务，用 Test Double（测试替身）控制模型回答和医院接口返回结果，验证协议、权限和错误处理。Redis 锁另有真实 Redis 7.4 容器验证，覆盖锁竞争、租期、所有者校验和取消释放。

项目已有 Docker（容器平台）、Kubernetes（容器编排平台）参考配置、90/10 灰度权重、Prometheus（指标采集系统）、Grafana（监控可视化平台）和隐藏医疗正文的 LangSmith（大模型链路追踪平台）摘要，覆盖部署配置与运行观测。

业务设计的价值是把任务分派、资料查询和结果整理串成一条流程，让临床人员在同一个工作台查看工具依据和辅助结果。

### 12. 一个可直接讲的故障机制与收尾

我会用转诊超时解释写操作设计：医院可能已经创建草稿，但回复丢失，系统只知道结果未知。我的处理是执行前持久化占位，写请求不自动重试，同键再次到达先查状态；未确认的结果保留给医院侧核对。验证时用故障注入模拟远端成功、本地没有确认的情况，检查是否重复执行、误报成功或泄露数据。这个例子描述工程验证，经历题按自己的真实参与情况展开。

这个项目让我重点掌握了意图路由、受控智能体编排，以及权限和写操作状态治理。我的设计目标是让自然语言任务有明确执行边界，有证据可复核，失败也能解释和定位。

## 第二部分：核心追问

下面每个回答都可以直接说；前面正文提供理解所需的完整机制。

### 医务管理人员具体使用哪些功能？有没有管理后台？

医务管理员通过同一工作台查看本项目中的院内患者资料、历史辅助记录，并发起查询类辅助任务，采用医院级只读权限，不能执行三个写工具。当前角色权限已经实现，人员、患者授权、统计和质控管理后台未实现。员工账号与初始患者授权由运维脚本创建；日常权限维护可进一步对接医院身份系统或增加管理接口。

### 识别十类意图，是否意味着十类业务都已有完整工具链？

意图识别负责确定业务目标，具体执行能力由工具链提供。检验解读已有 LIS（检验信息系统）解释接口，需要请求提供项目、数值、单位和参考范围。报告、随访和临床知识已纳入意图路由，但尚无各自完整的专用工具链；影像识别、报告自动拉取和随访调度属于后续扩展。指南检索当前调用外部指南服务，本仓库没有自建指南 RAG 索引或通用网页搜索。

### 受控工具能否防止被攻破的内部服务伪造权限？

当前机制约束可信后端下的模型工具调用：专科程序按固定白名单生成工具范围，MCP 再核验委托令牌和实时业务权限。内部服务共享委托签名密钥，MCP 也没有独立重算专科固定白名单，因此持有签名密钥的服务仍可能伪造更大的工具范围。若扩展到企业生产，我会使用独立服务身份和集中签发机制，并让工具端独立核对专科、员工和本轮批准范围的交集。

### 为什么三个 Agent（智能体）？

三个领域需要的工具不同，因此分别建立症状、药品和指南检验 Agent，每个专科只绑定自己本轮获准的工具。这样能限制模型的选择范围，也便于定位哪类任务失败。十类业务意图映射到这三个专科，并不是每个意图都需要一个 Agent。

### A2A（智能体间通信）、MCP（模型上下文协议）、Function Calling（函数调用）有何区别？

A2A 传递协调器分派给专科的任务与结果；MCP 连接专科和工具服务，提供工具发现与调用；Function Calling 是模型返回工具名称和参数的方式。以药品查询为例，协调器经 A2A 找 DrugAgent，模型提出 `query_drug_info`，专科再经 MCP 请求工具执行。协议与函数调用格式都不能代替患者和动作权限校验。

### Planning（任务规划）和 ReAct（推理与行动）有何区别？

Planning 先生成专科任务列表，例如查指南和查药品，由后端校验后调度；ReAct 是一个专科内部根据工具返回结果继续选工具或结束回答。当前项目按顺序执行专科，每次专科任务的模型调用和工具调用各最多六次，尚未根据前步结果自动重新规划。

### 为什么不用长任务框架？

当前一版计划最多调用三个专科，协调器负责按顺序调度，`create_agent` 负责每个专科内部的工具循环，已经覆盖现有短任务流程。若将来需要跨小时任务、进程重启后续跑或大量文件产物，我会再评估长任务框架，并补齐状态恢复与外部写操作核对；引入框架本身不会自动解决这些问题。

### 结构合法为什么还需校验？

JSON 能解析、字段类型正确，只能证明返回格式符合约定。例如工具请求可以写出合法的患者 ID，却指向未授权患者。执行前还要检查患者授权、工具范围、参数值和业务条件；药名真实性、引用是否支持结论也不能仅靠格式校验确定。

### 模型能改患者 ID 吗

模型可能生成另一个患者 ID，但不能借此扩大本次授权。对于带患者参数的工具，专科包装器会把该参数强制替换为服务端授权 ID，模型填写的其他 ID 不会作为访问目标。A2A 会拒绝任务患者与委托范围不一致的请求；MCP 会拒绝实际收到的患者参数与令牌不一致或当前员工无权访问的请求。这里既有参数强制注入，也有服务端拒绝校验，不能笼统说模型写错 ID 就一定报错。

### 是否有人工确认

三个 MCP 写工具有动作级确认：员工在本轮请求中通过 `approved_actions` 批准保存病史、保存辅助记录或生成转诊草稿，后端再检查角色和患者权限。批准的是工具动作类别，不是模型随后生成的每项最终参数；展示最终参数并绑定批准记录的审批机制尚未实现。工作台的档案编辑则由员工填写表单并点击保存，走独立 REST 接口，不使用聊天请求中的 `approved_actions`。

### 患者档案怎么写入？与 MCP 保存病史有何区别？

工作台的“编辑档案”表单调用 `PUT /api/patients/{patient_id}/profile`，医生、药师可修改已授权患者的姓名、年龄、性别、过敏史、既往病史和当前用药。接口校验身份、写角色、患者授权与字段约束，把档案和审计记录在同一事务中提交。档案编辑与 MCP 病史更新都把每类病史列表限制为最多 100 项，并复用 `ClinicalEntry` 将每项限制为 1 至 500 个字符。

`save_patient_history` 则是 Agent 申请执行的 MCP 工具，只接受病史白名单中的过敏史、既往病史和当前用药，并经过本轮动作批准和持久化操作状态管理。直接档案编辑不使用 `approved_actions`，也不登记 `pending/completed/unknown` 工具状态，因此操作查询接口查不到这次表单保存；其结果要核对档案和 `profile_updated` 审计。两条路径都能修改病史字段，但触发方式、可改字段和记录机制不同。

### 是否有幂等

有，三个 MCP 写工具在项目数据库中使用“员工、请求标识、工具名”生成唯一操作键。同键同参数已经完成则返回已记录结果，未确认或结果未知则阻止再次执行。换一个请求标识可能成为新操作；若要避免医院侧跨请求重复写入，还需要医院接口支持幂等键或可靠的结果查询。档案编辑 REST 接口不使用这套操作键和状态表。

### 会话共享会串数据吗

会话存储键同时包含员工、患者和会话标识，因此不同员工或不同患者的历史不会使用同一个键。整轮锁阻止同一会话同时执行两轮请求，问题与回答成对写入。它保护的是会话历史，不能阻止两个员工通过不同会话同时编辑同一份患者档案；档案并发更新还需版本控制。

### 是否完全私有化

当前不是完全私有化推理：应用服务、数据库、意图分类 BERT 和向量模型可在本地运行，但专科工具选择、规划和汇总仍调用配置的 SiliconFlow 云端模型。若要求推理不出院内，需要替换为院内模型服务，并验证工具调用、结构化输出和流式行为。

### 分类错了怎么定位

先查看实际预测意图、最终接受它的层级、经过的路由层和分数。例如正则已经错误接受请求，后续 BERT 再准确也不会纠正这一轮。定位最早偏离预期的层级后，再修改对应规则、模型或意图原型，并把原问题加入回归集。

### 是否有独立 EMR（电子病历系统）接口

目前没有，病史和临床辅助材料存在项目数据库。医院正式电子病历接入需要另做接口契约与验收。

### 是否已经上线

仓库已有工程实现和部署参考配置，本讲稿没有真实医院正式上线的验收证据。因此可以讲本地验证和已实现功能，不能把部署文件、自动化测试或健康接口压测当作医院上线证明；若有实际上线经历，应另列环境、时间、范围和验收记录。

### 医院一直超时为何不无限重试？

无限重试会放大下游故障。医院只读瞬态错误总计最多尝试三次，写操作不自动重试，未知写结果先核对。

### 工具失败为何不让模型凭常识补答？

临床辅助结论需要可追溯依据。专科没有成功工具证据或有工具失败时，就不接受正常结论，明确返回失败。

### 三个专科调用的是同一个模型吗？为什么仍然称为多 Agent（智能体）？

**三个专科默认调用同一个云端大语言模型，但分别运行三个 Agent。** 模型提供生成和工具选择能力；Agent 围绕模型组织任务、工具与运行状态。因此，模型相同与 Agent 有多个可以同时成立，项目也没有分别训练三个专科大模型。

| 区分项         | 本项目的实际实现                                                                      |
| ----------- | ----------------------------------------------------------------------------- |
| 模型配置        | 三个专科都读取 `SILICONFLOW_MODEL`，默认使用同一个模型标识；每个专科分别发起自己的模型请求                       |
| Agent 实现与服务 | 三个专科复用 `MCPToolAgent` 类，分别以 SymptomAgent、DrugAgent、GuideAgent 身份运行在三个 A2A 服务中 |
| 提示词与任务      | 提示词模板填入各自专科名称，协调器分别传入对应任务                                                     |
| 工具与权限       | 每个专科有自己的工具白名单，并按本轮批准动作进一步过滤；MCP 执行前校验令牌和业务权限                                  |
| 本轮运行状态      | 每次专科任务单独创建工具循环，维护自己的模型消息、工具结果、调用次数和去重记录                                       |
| 会话与长期记忆     | 专科可接收同一员工、同一患者会话的历史快照，但不共同修改一个正在执行的工具循环；三个专科没有各自的长期会话记忆                       |

例如查药品和查指南时，DrugAgent 与 GuideAgent 分别调用同一配置的模型，在各自循环中使用不同工具。协调器当前按顺序执行二者，前步结果不自动传入后步，最终再汇总结果。

“多 Agent”描述任务执行的分工，不按模型品牌或供应商数量计算。“上下文独立”指各自维护本轮状态，可以有共同的患者事实和历史输入；它不代表操作系统级沙箱或完整服务安全隔离。

### 规则全部覆盖了吗？

没有全部覆盖。固定工程回归集通过，只能证明当前规则能处理这些已知表达；否定句、改口、特殊人群和新的组合请求仍可能出错。需要持续加入真实失败样本并由临床人员核对，不能从小样本满分推断所有请求都能正确处理。

### 面试官：工具超时了，直接重新问一次不就行了吗？

要先区分只读查询和写操作。只读查询可按错误类型有限重试；写操作超时可能是医院已写入、响应丢失，此时重新提问若生成新请求标识，可能再次创建记录。应先保留原请求标识，查询本地写工具状态并核对医院记录，确认未写入或下游能可靠去重后再决定是否重发。

### 面试官：那你有幂等键，为什么还需要人工核对？

本地幂等键只保护同员工、同请求、同工具的重复调用。换请求标识可能成为新操作，医院接口也未必支持同一幂等键。结果未知时，要把本地操作记录与医院实际记录进行核对，确认医院是否已经写入；本地没有收到成功响应，不能证明医院没有执行。

### 面试官：怎么判断这次到底算成功？

对正常工具查询，专科需要有成功工具证据且没有工具失败，入口还要完成本轮规定的咨询、审计、会话和阶段保存，再发 `done` 确认完成。这是工程执行的完成条件，不能自动证明医学结论正确或问题的全部目标已完成，医学内容仍需临床复核。客户端未收到 `done` 只能判断“未确认”，不能判断所有写入都失败。澄清或拒识也可正常结束，但不代表已完成用户要求的医学查询。

### 面试官：你拿什么证明这套处理有效？

对于权限控制、重复写入拦截和未知结果处理，我展示授权检查、操作键、数据库唯一约束、状态记录与对应故障测试。协议测试通过真实本地 HTTP（超文本传输协议）连接 A2A/MCP 服务，但模型和医院接口使用测试替身，验证的是这些工程机制。临床结论的正确性和真实医院业务效果仍需另行验收。

## 第三部分：架构与工程追问

本部分讨论架构与工程设计。通用设计说明做法与条件；涉及本项目时明确指出已实现部分，不把拟议方案写成现有能力。

### 一、Agent（智能体）工程范式与架构辨析

#### 1. 你怎么定义 Agent（智能体）？

Agent（智能体）是围绕任务目标组织模型、提示词、工具和运行状态的执行程序。模型在其中提出下一步工具调用，程序检查并执行工具，把结果回填给模型，再决定继续查询或结束。本项目的三个专科分别使用 ReAct（推理与行动）工具循环，但默认调用同一个配置的云端模型；工具范围、权限和停止预算由代码控制。

#### 2. 这个项目到底是 Workflow（工作流）还是 Agent（智能体）？

项目是固定 Workflow（工作流）与三个专科 Agent（智能体）子流程结合。业务入口先检查员工身份与患者授权，`MedicalCoordinator` 协调程序随后处理急症和业务范围、识别意图、检查必要参数、分派任务并收集结果；最终由业务入口保存咨询、审计和会话。复杂任务时，协调器调用 `Planner.plan` 让模型提出计划，再由代码校验计划。内层专科使用各自的工具循环，让同一配置的模型根据工具结果决定下一步。协调器、规划方法与专科 Agent 的职责不同，不能把流程中的每个方法都算成一个独立部署的 Agent。

#### 3. Prompt Engineering（提示词工程）、Context Engineering（上下文工程）和 Harness Engineering（智能体执行框架工程）有什么区别？

Prompt Engineering（提示词工程）解决“怎样向模型说明任务”，例如要求规划结果按指定 JSON 返回。Context Engineering（上下文工程）解决“本轮给模型看哪些信息”，例如选择患者档案、历史消息和工具结果。Harness Engineering（智能体执行框架工程）解决“模型提出动作后如何受控执行”，例如工具白名单、授权检查、调用上限和结果验收。三者分别对应指令、输入材料和执行程序。

#### 4. Loop（循环）、Graph（图式流程）和 Orchestration（任务编排）分别是什么？

Loop（循环）表示执行动作后读取结果，再决定下一步；Graph（图式流程）用节点和边表示步骤及其依赖、分支或循环；Orchestration（任务编排）负责决定哪些执行者何时运行，以及如何收集结果。本项目由 `create_agent` 维护专科内部循环，由协调器按顺序调度专科，A2A 只承担任务传输，不决定执行顺序。

#### 5. Graph（图式流程）一定比 Chain（链式流程）更先进吗？

不一定。步骤固定、按顺序执行时，Chain（链式流程）通常更容易理解和维护；流程存在条件分支、依赖关系或需要从某个节点恢复时，Graph 更便于表达。图式框架仍需明确状态如何更新、并行结果如何合并和失败如何处理，不能仅凭采用 Graph 判断系统更先进。

#### 6. Supervisor（监督调度者）和 Plan-and-Execute（规划后执行）是一回事吗？

不是一回事。Supervisor（监督调度者）是负责分派任务的角色，可以每一步都重新选择执行者；Plan-and-Execute（规划后执行）是先形成计划、再按计划执行的方式，监督者也可以使用这种方式。本项目复杂任务由 `Planner.plan` 提出最多三步计划，经代码校验后由协调器执行，没有在每个专科结果后自动重新规划。

#### 7. 有循环为什么计划还可以是 DAG（有向无环图）？

DAG（有向无环图）的“无环”只约束该计划中节点之间的依赖，例如先查检验、再评估用药；其中一个节点内部仍可多次调用工具。若执行后重新生成计划，可以产生新一版 DAG，但不能在同一版图里无限回到旧节点。本项目跨专科是串行列表，没有实现完整依赖图或自动重规划；这些属于扩展方案。

#### 8. Agent（智能体）与 Dify（低代码应用平台）、Coze（低代码智能体平台）这类平台有什么区别？

Agent 是一种执行任务的程序，Dify、Coze 是可用于搭建 Agent 或工作流的平台，因此不是同一层面的概念。低代码平台可以加快原型搭建，但仍需核对其权限、状态和部署能力是否满足医院要求。本项目使用代码实现，是为了直接控制员工—患者授权、医院接口鉴权、工具执行和故障状态。

### 二、主协调器的路由、槽位与任务契约

#### 1. 面对很抽象的指令，Agent（智能体）怎么执行？

先确定操作对象、要完成的动作、限制条件和预期结果。例如“帮我看看这个药”还缺药名，也没有说明要查说明书还是核对禁忌，应先追问。患者身份必须来自已验证的授权上下文，不能由模型猜测；其他关键业务信息足够后，再分派专科任务。

#### 2. 什么是槽位，和意图有什么区别？

Intent（意图）是要完成的业务目标，Slot（槽位）是执行该目标所需的参数。例如“用药审核”是意图，药品列表、患者当前用药和过敏史是相应槽位。意图识别正确，只能确定应交给药品专科；缺少关键参数时仍不能开始可靠审核。

#### 3. 槽位识别怎么做？

患者身份和已记录病史应由服务端从授权上下文与可信档案读取；问题中的药名、症状、检验指标可用规则、词典或模型抽取。抽取结果还要核对类型、单位和业务要求，缺失或有歧义时追问。当前项目只有部分缺信息规则和工具参数校验，没有统一覆盖所有意图的槽位抽取器。

#### 4. 多轮对话中槽位怎么继承？

当前项目在上一轮需要澄清时，把原请求和新补充拼接后重新识别，没有逐槽位继承机制。若扩展，我会给每个槽位保存来源、时间和确认状态；用户明确更正时替换旧值，切换患者后清除原患者的任务参数。过敏史等重要事实还要区分用户描述与数据库记录，不能直接用一条新消息覆盖可信档案。

#### 5. 用户问题短且模糊怎么办？

先看服务端已有信息能否明确对象，例如当前已选择的患者；不能用历史猜测缺失药名或检查结果。只追问影响执行的必要信息，例如“请提供药名和需要核对的问题”。若患者过敏史读取失败，应停止依赖该事实的个体化判断，不能将读取失败当作“没有过敏”。

#### 6. 意图漂移怎么处理？

用户从查药改成解读检验时，应根据本轮目标重新路由，不能因为上一轮是药品任务就继续调用药品专科。当前项目每轮重新识别请求，但澄清分支会合并上一轮原任务与本轮补充。若要可靠处理澄清途中改换任务，还需识别“继续补充”与“切换目标”，并重置旧任务参数。

#### 7. 路由结果的 Schema（结构约束）应包含什么？

当前 `IntentDecision` 包含意图列表、复杂任务标记、规范化术语、判断理由、接受结果的层级、分数和经过的路由层；目标专科由意图映射表确定，不直接存放在该对象中。缺失参数由澄清结果另行表示。若扩展任务契约，我会再加入每项任务的必需参数、依赖和失败策略，不能把这些拟议字段说成已有结构。

#### 8. 交给子 Agent（智能体）的是一句话还是任务契约？

当前 A2A 请求体包含任务文本、患者标识和裁剪后的历史；短期委托令牌携带员工、患者、专科、工具和批准动作，患者档案由专科自行读取。若扩展成完整 Task Contract（任务契约），还应明确交付物、可引用事实、剩余时间和失败返回格式。任务文本说明“做什么”，结构化授权字段控制“允许做什么”，不能用一句自然语言代替权限校验。

### 三、串行、并行、异步与多 Agent（智能体）协同

#### 1. 什么情况下串行执行？

后一步必须使用前一步结果，或需要先核对事实再执行写操作时，应串行并显式传递所需结果。当前项目虽然按顺序调用专科，但前步结果没有自动加入后步输入，因此不能据此宣称已支持跨专科依赖链。若要让药品审核使用指南专科刚得到的结果，还需补充任务依赖与结果传递。

#### 2. 什么情况下并行执行？

不依赖彼此结果、没有相互影响的只读任务可以并行，例如独立查药品说明书和疾病指南。若扩展并行调度，我会限制每个下游的并发和连接数，并规定一项失败时是取消整轮还是返回部分结果。当前项目仍按顺序调用专科，异步网络代码不表示同一请求中的专科已经并行执行。

#### 3. 并行结果怎么合并？

若扩展并行执行，各任务应返回任务标识、数据来源、状态和结果，协调器先检查哪些成功、哪些失败，再按交付物合并。对重复事实可去重，对不一致字段保留来源与版本；临床结论冲突交医生复核，不能让最后返回的结果自动覆盖前面的结果。

#### 4. 什么情况下做异步后台任务？

批量统计或长报告不能在合理交互时间内完成时，可以先提交到后台队列，立即返回任务编号，再提供进度查询和结果获取。取消只能阻止尚未执行的步骤，已写入外部系统的动作仍需核对。当前项目在请求内执行实时问答，通过 SSE 返回事件，没有后台任务队列。

#### 5. 同步任务阻塞事件循环怎么办？

同步网络请求若直接在异步函数中等待，会占住事件循环，其他请求也难以前进。当前 A2A 同步客户端通过工作线程运行，避免阻塞事件循环；可替换的接口也可使用异步客户端。计算密集任务需按实现选择进程或推理服务，并限制并发；把函数写成 `async` 不会自动让计算变快。

#### 6. Python GIL（全局解释器锁）会影响 Agent（智能体）系统吗？

在启用 GIL 的 CPython 中，同一进程的多个线程通常不能同时执行 Python 字节码，因此线程不适合加速纯 Python 的重计算。模型 API 和医院接口主要花时间等待网络，异步或线程仍能改善并发；部分底层计算库也会释放 GIL。是否使用多进程应根据真实瓶颈决定，不能只因系统用了 Agent 就认为受 GIL 限制。

#### 7. 多 Agent（智能体）会不会互相甩锅或死循环？

如果允许子 Agent 随意互相转交任务，职责重叠可能形成“你处理—我处理”的循环。当前只有协调器分派给三个注册专科，子专科没有再调用其他专科的工具；每次专科任务的模型调用和工具调用分别最多六次。这样限制了循环次数，但仍需检查结果是否完成任务，不能只看循环正常结束。

#### 8. 如何判断多 Agent（智能体）是否值得？

要与“一个 Agent 使用相同模型和全部必要工具”的方案对照，而不是只看拆分后有多少 Agent。在同一批任务上比较完成率、越权与高风险错误、延迟、词元成本和维护工作量。本项目按三个工具领域拆分便于限制权限，但是否提高整体效果和效率，还需要这种对照评测。

### 四、上下文、状态和记忆深挖

#### 1. State（状态）、Context（上下文）和 Memory（记忆）有什么区别？

State（状态）是程序保存的任务数据，例如当前步骤、工具结果和是否完成；Context（上下文）是某次模型请求实际收到的消息与材料；Memory（记忆）是跨轮保留、以后可以再次读取的信息，例如会话历史。一项事实可以存于状态或记忆，但只有被选入当前模型输入后才成为本轮上下文；每轮仍需按权限和相关性筛选。

#### 2. 什么是上下文污染？

上下文污染是把不该参与本轮判断的信息送给模型，例如另一患者的病史、已更正的药名或网页中的恶意指令。防护时既要按员工和患者隔离存储，也要检查信息来源、时间和是否仍适用于当前任务。外部文档只能作为待核验的数据，不能因出现在上下文中就获得修改权限或执行规则的权力。

#### 3. 多 Agent（智能体）共享 State（状态）会不会互相覆盖？

共享可变状态可能互相覆盖。本项目当前按顺序调用专科，每个专科任务维护自己的模型消息、工具结果和去重记录；它们收到的是同一患者会话的历史快照，不直接共同修改会话历史。协调器收集各自返回的结果，业务入口在最终回答完成后统一保存会话。若将来改成并行执行，我会继续使用各专科的局部状态，再通过 Reducer（归并器）或版本检查合并结果；共享患者档案的写入仍需单独处理并发，不能靠专科上下文隔离解决。

#### 4. RAG（检索增强生成）结果和患者数据冲突怎么办？

若增加 RAG，检索到的指南通常描述某类人群的通用推荐，患者档案描述具体患者的事实，两者不是同一种数据。应先核对指南适用人群、版本以及患者数据的时间和来源；不能因指南写“通常正常”就改掉患者的异常值。无法解释的冲突保留双方依据交临床人员复核，当前仓库没有自建指南 RAG 链路。

#### 5. 历史摘要会不会把模型带偏？

会，例如摘要把“否认青霉素过敏”压成“青霉素过敏”，就改变了关键事实。若引入历史摘要，应从可信结构化记录读取过敏、用药等重要字段，只用摘要压缩非关键背景，并保留时间与来源。当前会话使用近期消息快照，没有实现自动摘要，因此不能把摘要质量控制说成现有功能。

#### 6. 工具结果太长怎么办？

先确定回答所需字段，再删除重复或无关项；多条结果可分页或只保留最相关的前 K 条，长文保留命中段落和原文位置。裁剪不能丢掉单位、版本、否定词和错误状态。若把完整结果另存到产物库，应让有权限的人员能按引用回查；当前项目没有通用产物库或工具结果分页机制。

#### 7. Context Builder（上下文构建器）怎么设计？

Context Builder（上下文构建器）负责把程序中的数据筛成某次模型输入。若扩展，我会分别组织可信系统规则、当前任务、授权患者事实、可用工具、外部证据和近期历史，并为各类材料分配词元预算。外部证据标明来源，不与系统指令混写；最后检查患者一致性和关键信息是否被截断。当前这些组装逻辑分散在提示词、历史裁剪和脱敏函数中。

#### 8. Checkpoint（检查点）和 Memory（记忆）、日志有什么区别？

Checkpoint（检查点）为恢复执行保存状态，例如运行到第几步及其结果；Memory 保存下一轮可能使用的信息；日志供排障和审计记录发生过的事件。当前项目只存“开始、专科完成、完成或失败”等阶段记录，不能恢复某次模型工具循环。若要精确恢复，还需步骤位置、执行状态和外部写操作结果，先核对副作用再决定哪些步骤可重放。

### 五、稳定性、恢复与故障隔离

#### 1. 稳定性的目标是不是永不失败？

不是。模型、网络或医院接口都可能失败，稳定性要求系统在失败时给出可识别的错误、限制重试与影响范围，并记录哪些动作已完成或结果未知。依赖不可用时，应明确停止需要它的任务，不能通过编造医学结果维持表面上的“成功”。

#### 2. 超时应该怎么设置？

先设定整轮截止时间，再让每个模型、工具和数据库调用只使用剩余预算的一部分，避免多次调用累计超过用户可接受时间。例如整轮只剩五秒，下游不能再申请三十秒等待。当前配置分别设置整轮 120 秒、模型请求 30 秒和医院请求 10 秒，但没有统一传播剩余预算，客户端请求超时也不能保证远端工作已停止。

#### 3. 重试为什么可能让故障更严重？

下游过载时，大量请求立即重试会增加流量，使服务更难恢复，这就是 Retry Storm（重试风暴）。当前医院只读接口对网络和指定瞬态错误最多尝试三次，使用指数退避；这段实现没有随机抖动。若扩展高并发场景，我会加入抖动和统一重试预算；转诊写入当前不自动重试，因为超时可能发生在写入成功之后。

#### 4. Checkpoint（检查点）能保证写操作不重复吗？

不能。若医院已经写入，而本地尚未保存该步骤的检查点，恢复后照旧重放会再次写入。应先查看持久化操作记录，再用医院支持的幂等键或结果查询核对；无法确认时保留未知状态交人工，而不是仅根据检查点缺失判定该步骤未执行。

#### 5. 如何防止过载和故障扩散？

应分别给模型、医院接口和数据库设置并发与连接上限，防止入口请求把所有资源耗尽。队列也要有长度和等待期限，满额后明确拒绝或返回可用的降级结果，而不是无限积压。当前项目已有超时和熔断，但没有完成覆盖全部依赖的容量准入与压测验收。

#### 6. 模型服务突然不可用怎么办？

当前急症规则仍可返回固定安全提示，范围判断模型失败可以转为澄清；依赖模型的专科查询或汇总不能靠模型记忆补答。意图兜底失败时，只有先前命中的规则结果可能被保留。若以后增加备用模型或公共缓存，需要验证工具行为、数据有效期和权限，当前没有自动多模型切换或公共医学答案缓存。

#### 7. 输出波动大怎么排查？

先保存导致差异的输入、模型标识、提示词版本、工具结果和采样参数，再在受控条件下重放，定位变化首先出现在路由、工具选择还是汇总。如果工具返回已经变化，应先查数据版本；如果输入证据一致而回答变化，再评估模型输出稳定性。温度为零不保证跨服务端版本或运行环境完全一致。

#### 8. 故障演练怎么做？

在隔离测试环境控制某个依赖返回超时、限流、非法数据或存储失败，检查请求是否按预期停止、重试次数是否受限、用户是否收到正确提示。写操作重点模拟“远端已成功，但响应丢失”，检查系统保留未知状态且不会自动重复提交。故障注入验证的是这些特定分支，不能代替真实医院环境验收。

### 六、输出聚合、流式体验与效果评估

#### 1. 多个 Agent（智能体）的结果怎么聚合？

协调器收集已执行专科的名称、回答和工具轨迹，流式路径通过 `Planner.synthesize_stream` 单独调用同一配置的云端模型生成最终答复，没有另部署汇总 Agent。非流式路径只有一个结果时直接使用该回答，多个结果时调用 `Planner.synthesize`。每轮只执行必要专科，不要求三个全部参与；当前工具证据门槛还不能替代逐项交付物验收。

#### 2. 子 Agent（智能体）结果冲突怎么办？

先核对双方引用的数据版本、适用条件和原始来源，区分重复数据、过期数据和真实结论冲突。程序能确定的字段按来源和业务规则处理，医学判断冲突则保留双方依据交医生复核。当前没有专门的冲突裁决模块；让同一模型再投票只能生成新的判断，不能增加原始事实证据。

#### 3. 如何做输出审查？

输出审查要检查是否对应授权患者、单位和版本是否保留、引用是否支持结论，以及失败工具有没有被误写成成功。格式、患者范围和部分禁止行为可由代码检查；医学正确性仍需权威证据和临床复核。当前有提示词边界、工具证据门槛和脱敏，但没有独立覆盖全部医学内容的审查器。

#### 4. Structured Output（结构化输出）为什么仍可能错？

Structured Output（结构化输出）让字段和类型符合约定，例如药名字段是字符串，但字符串内容仍可能是错误药名。Pydantic 可以检查类型和枚举，患者访问要查授权，数值与单位要按业务规则核对，医学依据还要核查来源。符合结构不能替代这些内容检查。

#### 5. 首 Token（词元）慢怎么定位？

先测从用户提交到第一段回答文字出现的 TTFT（首词元时间），再记录前面各阶段的耗时：范围判断、意图识别、规划、专科工具执行和汇总等待。当前需要专科完成后才开始最终回答流式生成，因此前置工具慢也会表现为“出字慢”。应先优化最耗时阶段，不能只调整 SSE 的发送频率。

#### 6. 流式生成中断怎么办？

当前没有精确续传能力；客户端中断后没收到 `done`，不能认定后台一定没保存。涉及写工具时先核对操作记录和实际写入目标。若扩展断点续传，需要保存可重放事件并给它们编号，客户端用 Last-Event-ID 请求未收到的事件；只有带编号而没有事件存储，仍无法恢复内容。

#### 7. 如何自动评估执行轨迹？

将每次运行轨迹与预期任务对照，检查意图是否完整、专科是否选对、参数是否正确、是否越权，以及工具证据是否支持最终回答。调用次数和权限可由规则判断；表达质量可以用经人工样本校准的模型裁判评分，但不能让裁判模型替代事实核验。当前轨迹主要是工具与状态摘要，不包含完整内部推理过程。

#### 8. 缺少真实用户反馈时怎么评估？

先建立版本化离线任务集，覆盖正常查询、信息缺失、多意图、越权和工具失败，并给出预期路由、可执行动作及结果标准。高风险答案需要临床人员审核，测试样本不能与训练数据重复。当前合成数据和 33 条固定路由回归用于工程验证，不足以证明真实用户任务效果。

#### 9. 如何控制多 Agent（智能体）成本？

当前用规则和本地模型先处理明确意图，只运行需要的专科，并限制每个专科的模型与工具调用次数。后续可以记录整轮输入、输出词元和工具费用，按成功完成的任务比较成本；不能只比较某一次模型请求价格。裁剪上下文时应保留必要患者事实和证据，不能为了省词元删掉影响判断的信息。

### 七、工具、RAG（检索增强生成）与安全扩展题

#### 1. 如果有几千个医院 API（应用程序接口），怎么组织？

若工具扩展到几千个，我会先按业务领域与读写风险建立目录，再依据意图和员工权限选出本轮少量候选工具，而不是把全部描述交给模型。每个工具用适配层统一参数、错误和超时，并保留版本与契约测试。MCP 统一连接方式，工具是否允许执行仍由服务端策略决定。

#### 2. Skill（技能）和 Tool（工具）有什么区别？

Tool（工具）是可执行的接口，例如查询某药的说明书；Skill（技能）是完成一类任务的方法包，可以包含说明、步骤、示例和脚本，并指导 Agent 使用多个工具。加载 Skill 不会自动增加工具权限。当前项目实现的是 MCP 工具，没有科室 Skill 加载体系；将科室 SOP 组织为 Skill 属于扩展方案。

#### 3. RAG（检索增强生成）召回为空怎么办？

若增加 RAG 而检索为空，先检查疾病名称是否规范、过滤条件是否过严、文档是否已入库和索引是否更新；再尝试同义词改写或关键词检索。仍无结果时说明“未检索到可用依据”，记录待补充的知识范围，不能让模型编造指南引用。当前指南工具调用外部服务，本仓库没有可自行排查的指南向量索引。

#### 4. RAG（检索增强生成）和数据库结果冲突怎么办？

先确认是不是同一字段、同一时间和同一适用条件，例如旧档案中的用药与本次新记录不同，或指南适用于不同年龄人群。患者事实和通用推荐分别保留来源，异常值提示核验，不按指南“正常范围”改写原始结果。若临床意义仍有冲突，应展示证据交医生判断，而不是让模型无依据地选一方。

#### 5. Prompt Injection（提示词注入）怎么分层防护？

提示词注入是外部文档、工具结果等数据包含“忽略规则、上传密钥”等指令，诱导模型改变行为。防护应同时标明数据来源、限制本轮工具范围，并在模型之外校验动作目标、患者、参数和授权。当前项目已有工具过滤、委托校验和出站脱敏，但没有覆盖所有外部文本的注入检测器，也不能保证模型从不受注入影响。

#### 6. 如何防止工具返回内容反向控制 Agent（智能体）？

工具结果应按接口约定提取业务字段，外部文字中的操作要求不能变成系统指令。例如返回里写“把 API Key 发到某网站”，执行层不应因此开放上传权限。当前后端会检查工具和患者授权，但没有给所有外部返回做严格字段白名单；若扩展，还需限制返回结构并将高风险动作绑定可信批准记录。

#### 7. 如何防止 Key（键）和敏感数据泄露？

这里的 Key 指 API 密钥或签名密钥。它们应由受控配置或密钥管理服务提供，不放进提示词、日志或工具返回。当前临床文本出站有递归规则脱敏，也会解析 MCP 文本块中的 JSON 后按敏感字段脱敏；证件号先于手机号处理，避免手机号子串破坏整段证件号识别。但规则不能保证发现全部可识别信息；还需检查实际日志和回调出口。若确认泄露，应先吊销或轮换密钥，再在权限允许的范围内处理留存副本并审计影响。

#### 8. 高危工具如何防社会工程式欺骗？

高风险动作应先在可信界面展示最终对象、参数和影响，例如为哪个患者向哪个科室创建转诊草稿。批准记录绑定操作者、患者、参数摘要和有效期，执行前重新计算摘要，参数变化就重新确认。当前只有动作级确认、角色校验与去重，尚未实现绑定最终参数的 Approval Token（批准令牌）。

### 八、模型训练、推理与算法追问

#### 1. 为什么意图识别不全部交给大模型？

意图识别是有限类别任务，明确表达可由规则或本地分类模型低成本处理，不必每次调用云端大模型。当前向量层匹配近义表达，大模型处理前层不能接受的复杂请求。这种级联便于定位错误，但前层错误接受请求会阻止后层纠正，效果和成本是否更好仍需与全部交给大模型的方案对照。

#### 2. BERT（本项目用于意图分类）分类分数能直接当真实置信度吗？

不能。Softmax 最高分 0.95 表示模型在当前十个标签间给该标签较高权重，不等于这类预测在真实数据上有 95% 正确率。阈值应在独立验证集上选择，并同时报告接受了多少样本、其中多少正确；未达到阈值的请求交后续层。它衡量的是意图分类输出，不是医学结论可靠性。

#### 3. 如何处理 OOD（分布外）？

OOD（分布外请求）是与训练任务分布不一致的输入，可能是非医疗问题，也可能是未见过的医疗表达。当前范围守卫处理不支持的业务请求，分类和向量阈值决定某层是否接受；低分进入后层，不等于整轮已经拒识。若扩展，还可用负样本、距离和第一第二名分差评估拒识，但必须验证不会大量误拒正常任务。

#### 4. 微调、RAG（检索增强生成）和 Prompt（提示词）怎么选？

任务规则说明不清时，先改 Prompt（提示词）；缺少可更新事实和出处时，优先补数据源或 RAG；在输入与工具正确的情况下，模型仍稳定违反某种可标注行为要求，才考虑 SFT（监督微调）。三者可以组合，但微调不能代替持续更新的医学依据。本项目训练了意图分类 BERT，没有对专科使用的云端大语言模型做 SFT。

#### 5. Prompt（提示词）调优到瓶颈后怎么办？

先用失败样本判断瓶颈在哪里：缺事实就补检索，参数或格式错误就补校验，任务说明有歧义就改提示词。如果事实、工具和说明都正确，模型仍无法完成所需推理，再评估换模型或微调。每次只改变能解释问题的因素，用同一评测集对照，避免同时修改后无法判断原因。

#### 6. 如何降低推理成本？

先减少不必要的模型请求，并只发送任务需要的工具描述和上下文，通常比直接换更便宜模型更容易控制效果。云 API 可考虑符合数据使用要求、且内容仍在有效期内的缓存，或供应商支持的批处理；量化主要针对自己部署的模型，不能由调用方直接改变云模型精度。FP16、INT8 等方案要在目标硬件上验证准确性、显存和延迟。

#### 7. 为什么 PyTorch（深度学习框架）装好了还可能不能用 CUDA（英伟达并行计算平台）？

安装 PyTorch 不表示当前包支持 CUDA，也不表示进程能访问 GPU。应核对正在使用的 Python 环境、PyTorch 构建是否带 CUDA、驱动是否兼容、设备是否对该进程可见，再查看 `torch.version.cuda` 和 `torch.cuda.is_available()`。本地成功只能证明该环境可用，换容器或服务器后需要重新验证。

#### 8. 幻觉是怎么产生的，怎么降低？

大语言模型生成的是在上下文条件下可能的后续词元，不自带对每条事实的真实性保证。缺少依据、证据冲突或提示词要求必须作答时，都可能生成听起来合理的错误内容。应让模型使用可追溯工具结果、允许说明无法查询，并核验引用与业务参数；这些措施降低风险，不能替代临床复核。

### 九、ToB（面向机构）项目交付与软技能追问

#### 1. 如何把医院的模糊需求转成系统能力？

先选一个具体场景，例如药师核对药品相互作用，明确谁使用、需要哪些数据、系统应返回什么，以及哪些动作必须人工确认。再用真实或获准的样本定义成功与失败标准，做一条可验收的完整流程。工具和专科拆分应服务于这个流程，不能先堆 Agent 再找业务用途。

#### 2. 客户说“智能体不好用”，怎么定位？

先请用户提供一次具体失败：输入是什么、预期是什么、实际出现了什么。再沿调用记录找到最早异常，例如路由错、缺药名、医院接口失败或页面未显示完成，而不是笼统归因模型。按影响范围排序修复，并用原样本复测让业务方确认改善。

#### 3. 如何定义验收标准？

验收标准应绑定具体场景和数据集，例如药品查询是否返回正确资料与来源、未授权患者访问是否全部被拒绝。业务效果、延迟、工具成功率和审计完整性分别设标准，并明确哪些组件是真实接口。权限与急症边界应单独设置必须通过的条件，不能被平均成功率掩盖。

#### 4. 项目到期但甲方不满意怎么办？

先把反馈与约定的验收标准逐项对照，区分原需求未完成、实现缺陷和新增要求。影响约定交付的问题优先修复，新增优化给出工作量、风险和排期，再由双方确认。已完成范围与未完成事项都用演示和记录说明，不能只争论“代码已经写完”。

#### 5. 开发中新增需求怎么处理？

先确认新增需求是否改变原交付范围，再检查它需要哪些数据、工具、权限和状态变化。例如新增转诊不是只加一句提示词，还会引入写审批、幂等和结果核对。估算实现与验收工作量后，由业务方确认优先级和排期，并留下变更记录。

#### 6. 业务部门不配合、需求频繁变化怎么办？

先选一个范围明确的场景，让业务方提供代表性样本并共同确认预期结果；每轮演示按这些样本验收。确定本轮范围后，新需求进入 Backlog（需求池）另行排序，避免开发中不断替换目标。如果缺少必要数据或业务审核，应明确其对交付的影响和需要谁决策。

#### 7. 怎么回答“项目最大的难点”？

可以围绕一个具体矛盾回答：模型能灵活解释请求，但服务端必须限制实际可执行动作。例如用户同时要求查药和查指南，单标签分类若提前接受就会漏任务，因此代码在出现多任务线索时不直接接受 BERT 的单标签结果。说明触发条件、修改点和验证样本，比只说“多 Agent 编排很难”更清楚；是否本人实施过须按真实经历回答。

#### 8. 怎么回答“如果重做一次会改什么”？

我会在增加业务工具前先定好员工—患者授权、每层路由记录和写操作状态模型，再统一工具错误格式。这样新增接口时就能明确谁可调用、失败在哪一层、写入是否已发生，减少后期补权限和恢复逻辑的返工。这个回答应结合自己真正遇到过的返工说明。

#### 9. 如何证明你不是只会调框架？

选一个可回查的失败案例，解释框架原本提供什么、哪些业务规则需要自己补，以及代码如何改变结果。例如转诊响应丢失后，为什么保留未知状态、怎样阻止重复提交、测试如何验证。能把触发条件、实现位置和证据连起来，比罗列框架名称更能说明贡献。

#### 10. 面试官要求看内网系统怎么办？

我会展示可公开的架构、契约和测试方法，内部环境按真实授权范围演示。个人演示项目就如实说明，医院保密经历必须有真实依据。

### 十、开放式系统设计追问

#### 1. 如果增加语音电话入口，怎么设计？

电话网关接入音频后，VAD 检测是否有人说话，ASR 将语音转成文本，再把已确认文本交给现有对话流程；回答经 TTS 转成语音。另需处理用户插话、药名和剂量识别歧义、身份确认及人工转接，并为各阶段设置延迟预算。当前项目没有语音链路，这属于扩展设计。

#### 2. 如果增加医学影像或报告图片，怎么设计？

报告图片先经文件校验、OCR 和版面解析，提取项目、数值、单位与参考范围，并保留原图位置供医生核对，再交给现有检验辅助流程。CT、MRI 等医学影像需要另行设计影像处理与临床验证，不能把 OCR 读取文字等同于影像诊断。当前两类图片能力都未实现。

#### 3. 如果让 Agent（智能体）生成月度医疗服务总结，怎么闭环？

如果增加月报，应先用有权限的数据库查询计算指标，固定时间范围、分母和统计口径，再让模型根据这些数值写说明。报告中的数值能回查到查询结果，解释与建议交负责人审核；不能让模型自行猜测医院经营数据。生成过程可放入后台队列，当前项目没有该流程。

#### 4. 从开发版走向生产版还要检查什么？

先验证真实医院身份、患者授权和业务接口，再确认数据使用范围、云模型使用批准及写操作审批。随后在目标环境验证容量、监控、备份恢复和灰度回滚，并给每项验收指定责任人和证据。仓库的部署配置只是起点，当前未满足正式医院生产放行条件，具体缺口见生产验收清单。

## 第四部分：扩展储备题

本部分是设计与原理储备，不是本项目功能清单。代码智能体、强化学习、语音、多模态和平台级多租户均未作为本项目已实现能力；以下第一人称回答表示设计思路，不表示本人已经落地过这些系统。个人经历题按实际情况填写。

### 一、代码 Agent（智能体）与 AI Coding（人工智能编程）

#### 1. 代码 Agent（智能体）如何建立 Repository Map（代码仓库结构地图）？

Repository Map（代码仓库结构地图）是帮助定位代码的索引，不是把所有文件全文发给模型。可以记录目录与模块、类和函数定义、调用关系及对应测试，再从当前任务选相关部分。静态索引看不到的运行时行为，通过日志、配置和测试补充。

#### 2. 如何从报错、符号依赖和测试覆盖选择最小上下文？

先从报错栈或失败测试定位函数，读取它的定义、直接调用方、依赖配置和断言。每发现一个尚不能解释的行为，再补相应文件，避免一开始载入整个仓库。最小上下文不是字数越少越好，而是包含能复现、修改和验证问题所需的信息。

#### 3. 为什么代码修改应输出 Patch（补丁）而不是整文件覆盖？

局部修改用 Patch（补丁）能直接展示哪些行改变，便于审查，也更容易发现与用户已有修改冲突。应用前要核对原文或基线版本，失败时重新读取，不强行覆盖。新建文件或明确要求整体重写时可以输出完整文件，不能把补丁形式本身当作正确性保证。

#### 4. 如何设计“定位—修改—测试—审查—修复”的有界循环？

先复现失败并确定通过标准，再修改相关代码、运行必要检查和测试，把真实失败输出作为下一轮输入。每轮记录做了什么、问题是否有变化；达到验收标准就结束，同一尝试反复失败则更换方法。触及权限边界或预算耗尽时停止执行并说明未完成项，而不是无限循环改代码。

#### 5. 如何在 Sandbox（沙箱）中限制文件、命令和网络权限？

沙箱应在执行层限制可读写目录、可运行程序、可访问网络和 CPU、内存等资源，并让任务使用权限受限的身份。模型即使提出越界命令，也应被沙箱拒绝；提示词要求“不要删除文件”不能替代这些控制。容器仍需正确设置挂载、凭据和运行权限，不是启动容器就自动隔离全部风险。

#### 6. 如何防止 Agent（智能体）修改无关文件、删除用户代码或泄露仓库密钥？

在执行层限定任务可写路径，并在修改后检查 Git 差异是否超出目标范围；删除、大范围覆盖等动作按授权处理。需要凭据时由代理或密钥服务按需提供，避免让模型读取长期密钥。完成后检查代码差异及日志是否含敏感信息，不能仅靠模型自称只改了相关文件。

#### 7. 单元测试通过但业务仍错误时，如何增加集成测试和回归测试？

先确定单测遗漏了哪种真实交互，例如接口返回格式、事务提交或权限撤销。补集成测试验证这些组件配合，再用端到端样本检查用户可见结果，并将原失败保留为回归用例。覆盖率只说明代码被执行过，断言仍要核对实际业务结果。

#### 8. 多个 Coding Agent（智能体）并行修改时，如何处理分支、冲突和责任边界？

给每个 Agent 分配明确模块和交付物，使用独立分支或工作树，尽量避免同时修改同一文件。合并前对照最新基线检查差异；即使 Git 没有文本冲突，也要核对接口与行为是否一致。最终由统一协调者或人工合并，并运行覆盖跨模块关系的检查。

### 二、强化学习与 Agent（智能体）训练

#### 1. 如何防止 Reward Hacking（奖励投机）？

Reward Hacking（奖励投机）是模型提高奖励分数，却没有完成真正目标，例如通过固定模板骗过只检查格式的评分器。需要用独立任务集、对抗样本和人工抽检核对实际效果，重点检查奖励上升但正确率下降的情况。KL 约束只能限制策略偏离参考模型的程度，不能修复奖励定义本身的漏洞。

#### 2. Verifier（验证器）需要评估正确性、格式、安全还是过程？

Verifier（验证器）应按任务目标分别检查结果正确性、格式、权限和必要执行过程。例如代码任务可运行测试，数据任务可核对数据库结果，工具任务可检查是否使用真实返回。不是每项都能由模型评分可靠判断；临床事实或证据不足的结论仍需人工复核。

#### 3. 如何检测和缓解 Entropy Collapse（熵坍缩）？

Entropy Collapse（熵坍缩）指训练后策略过度集中于少数输出，探索和有效回答多样性明显下降。应同时监控输出概率熵、重复率、独立评测效果及相对参考策略的变化，区分合理收敛与质量退化。再分别调整学习率、更新幅度或奖励尺度做对照实验；推理时提高温度不能代替修复已退化的训练策略。

#### 4. 什么是 Gradient Starvation（梯度饥饿），如何处理？

Gradient Starvation（梯度饥饿）是模型先利用少数容易预测的特征降低损失，使其他有用特征得不到充分学习。例如只依赖训练集中的背景线索，换背景后就失效。应通过移除特征和域外测试确认这种依赖，再评估数据重平衡或解耦特征学习的正则方法，不能把任何梯度变小都称为梯度饥饿。[原论文](https://arxiv.org/abs/2011.09468)

#### 5. 长思维链训练如何减少 Train–Inference Mismatch（训练与推理不一致）？

训练若总能看到完整工具答案、允许超长输出，而上线只能逐步查工具且长度受限，模型学到的策略可能无法使用。应让训练样本包含与上线一致的工具可用条件、输入模板和长度约束，并在真实执行设置下评测。无需把内部推理全文展示给用户，但最终结果和可审计动作必须符合上线要求。

#### 6. 训练数据如何按难度、质量、长度和可验证性分层筛选？

先去掉错误、无授权和重复样本，再按领域、难度、长度与验证方式分组，避免训练集被大量简单或同模板样本主导。困难样本也必须有可靠答案或结果检查方式，不能把未知正确性的长答案当高质量数据。训练集用于学习，验证集用于选参数，最终测试集保留作独立检验。

#### 7. KL Divergence（KL 散度）约束应该按 Token（词元）、序列还是阶段计算？

先说明 KL 约束比较哪两个策略：通常比较当前策略与固定参考策略在同一上下文下的输出分布。逐词元估计后，按序列求和会随长度增长，取平均则得到不同尺度，因此必须明确有效词元、聚合方式和系数。采样得到的近似 KL 日志不等于计算了完整分布，口径不一致的数值不能直接比较。

#### 8. GRPO（组相对策略优化）的 Group Size（组大小）如何在方差、显存和吞吐间取舍？

GRPO 对同一问题采样一组回答，依据各回答相对于组内奖励的表现计算训练优势；Group Size 就是每个问题采样多少个回答。组更大可能提供更丰富的比较，但增加生成、评分和训练开销；若整组奖励相同，增加样本也未必提供有效区分。应固定总采样或训练预算，比较独立评测效果、显存和耗时。[DeepSeekMath 原论文](https://arxiv.org/abs/2402.03300)

#### 9. 什么时候应该做 SFT（监督微调），什么时候继续优化工具和流程？

如果模型在多次相似任务上稳定选错工具或不遵守已明确的输出要求，而且有可靠标注样本，可考虑 SFT。若失败来自数据过期、检索为空、接口报错或权限设计，应先修数据与流程，微调不能把错误事实变正确。训练后仍要在独立任务集检验，不以训练损失下降作为上线依据。

#### 10. 如何判断某个 Bad Case（失败样本）应归因于模型能力，而不是检索、工具或编排？

沿轨迹找到最早偏离预期的位置，再固定其他条件做替换实验。例如直接提供正确证据后仍答错，才进一步检查模型；直接执行正确工具后任务成功，则应先查工具选择或编排。事实、输入和执行流程均正确而模型仍稳定失败，才能较有依据地归因其能力。

### 三、大模型底层与研究型问题

#### 1. Self-Attention（自注意力）为什么拆成 Query（查询）、Key（键）、Value（值）？

每个词元的表示经过不同投影得到 Query、Key 和 Value。当前位置的 Query 与各位置的 Key 计算匹配分数，经归一化后用于加权汇总各位置的 Value。分别学习“怎样匹配”和“传递什么内容”，比直接用一套表示同时承担两种角色更灵活。

#### 2. Multi-Head Attention（多头注意力）解决什么问题？

多个注意力头使用不同投影，分别对同一段输入计算关注关系，再把各头结果合并，使模型能够同时表示不同位置关系或特征。不能预先保证某个头固定负责语法或某种知识；增加头数还会改变每头维度和计算资源，效果需要评测。

#### 3. KV Cache（键值缓存）如何影响显存、吞吐和并发？

自回归生成时，KV Cache 保存各层已处理词元的 Key 和 Value，下一步只计算新词元并读取缓存，不必重新计算全部历史。缓存显存大致随层数、序列长度、并发序列数和键值头数增加。长上下文即使模型权重不变，也可能占用更多缓存显存，降低可同时服务的请求数。

#### 4. 长上下文中的 Attention Sink（注意力汇聚）和 Context Corruption（上下文腐化）是什么？

Attention Sink（注意力汇聚）指某些初始词元即使语义作用不大，也会获得较高注意力权重；在部分流式模型中保留这些词元的 KV 能改善滑动窗口效果。Context Corruption（上下文腐化）在这里泛指无关、错误或累积内容干扰当前任务，不是与前者等价的机制。不能把注意力汇聚直接解释为上下文污染，也不能据此推断长上下文必然失效。[Attention Sinks 原论文](https://arxiv.org/abs/2309.17453)

#### 5. FlashAttention（高效精确注意力）为什么能减少显存访问？

普通注意力会读写较大的中间分数矩阵。FlashAttention 将计算分块，并在片上存储中使用在线 Softmax 更新结果，减少 GPU 高带宽显存与片上存储之间的搬运，避免保存完整中间矩阵。它主要优化存储访问，不是通过丢弃注意力项来近似计算，数学上保持原注意力结果，仍可能有浮点舍入差异。[原论文](https://arxiv.org/abs/2205.14135)

#### 6. 量化中的 Calibration（校准）、离群值和精度损失怎么处理？

量化把权重或激活映射到较低精度表示；Calibration（校准）用代表性输入估计数值范围与缩放参数。少数离群值可能扩大范围，使普通值分辨率下降，可评估按通道或分组量化、部分层保留高精度等方法。是否值得采用，要同时测任务效果、显存和目标硬件延迟，而不是只看位宽变小。

#### 7. Speculative Decoding（投机解码）适合什么场景？

较小的草稿模型先生成多个候选词元，目标大模型一次验证一段候选，从而减少逐词元调用大模型的次数。严格的接受与拒绝采样机制可保持目标模型的生成分布，这不等于大模型在核验答案事实。只有候选接受率足够高、验证收益超过草稿开销时才加速，需要在目标负载下测量。[原论文](https://arxiv.org/abs/2211.17192)

#### 8. MoE（Mixture of Experts，混合专家）如何在参数规模与计算量之间取舍？

稀疏 MoE 在模型内部用路由器为每个词元选择少量专家网络，因此总参数可以很大，而每个词元只使用其中一部分。代价包括专家负载不均、跨设备通信和训练稳定性问题。这里的专家是模型内部网络模块；本项目的专科 Agent 是模型外部执行程序，不能把两者的“专家分工”混为一谈。

#### 9. World Model（世界模型）、GVF（General Value Function，广义价值函数）等研究概念如何与 Agent（智能体）联系？

World Model（世界模型）学习动作之后环境会怎样变化，可供 Agent 预测后果并规划。GVF（广义价值函数）则预测在某个策略和终止条件下，某种未来信号的累积，例如未来一段时间的传感器读数；信号不必是奖励。多种 GVF 可表示预测知识，但不自动提供完整环境状态转移模型，当前项目也未实现这些机制。[Horde 原论文](https://sites.ualberta.ca/~pilarski/docs/papers/Sutton_2011_Horde_AAMAS.pdf)

#### 10. 面试官问到 OaK 等不熟悉的架构时，你会如何核对和回答？

先请对方明确缩写指哪篇论文或哪个实现，避免按相似名称猜测。若没研究过，就说明已知范围，依据原始定义讨论它的输入、输出和执行机制，再与自己掌握的工具、状态和规划设计比较。不能因为概念有关联就声称项目已经采用该架构。

### 四、Deep Agents（深度智能体框架）与开放式长任务 Agent（智能体）

#### 1. Deep Agents（深度智能体框架）与 LangChain（大模型应用框架） `create_agent` 的能力边界是什么？

`create_agent` 主要建立模型提出动作、程序执行工具、结果回填模型的循环。Deep Agents 在这一类循环上增加待办规划、文件操作和子 Agent 委派等组织能力，适合需要持续管理任务与产物的场景。本项目使用 `create_agent`，没有采用 Deep Agents；是否支持持久化恢复等能力还需核对具体版本与运行环境，不能仅从框架名称推断。

#### 2. Todo Planning（待办规划）、文件系统和子 Agent（智能体）委派分别解决什么问题？

Todo Planning（待办规划）用明确的任务清单记录待做、进行中和完成的步骤，便于跟踪目标。文件系统把长结果和产物放在模型输入之外，按需读取；子 Agent 委派让一个子任务在单独的工具循环与上下文中执行，再返回结果。三者分别管理进度、材料和分工，不需要在每个短任务中全部使用。

#### 3. 大量上下文为什么要外置到文件或产物仓库？

把长文全文反复放入每轮输入，会增加费用、延迟并挤占真正相关的信息。可以将完整材料保存在受控文件或对象存储，本轮只读取索引和相关片段，并保留原文引用。存储权限也要绑定用户和任务，不能因为模型知道文件路径就允许它读取全部产物。

#### 4. 子 Agent（智能体）如何隔离上下文又共享必要产物？

主协调者向每个子 Agent 传入任务、必要事实和授权范围，子 Agent 在自己的消息历史与工具范围内执行。完成后返回结构化结果或有权限的产物引用，主协调者只读取汇总所需部分。独立上下文不要求事实完全不同，关键是子任务不随意共享可变消息历史，也不能借产物引用跨越数据权限。

#### 5. 长任务如何保存进度、恢复执行和传播取消信号？

长任务需要持久化计划版本、步骤位置、已完成结果和剩余预算，重启后才能确定从哪里继续。涉及外部写入的步骤先核对操作记录与下游结果，不能仅根据本地进度重放。取消信号传给调度器和可取消的下游任务，停止新步骤并保留已完成产物；已发出的远端写操作不能因此自动撤销。

#### 6. 如何限制 Shell（命令行）、文件写入和网络访问？

命令工具在受限身份和沙箱中运行，只允许指定工作目录、程序、网络目标和资源额度；执行层核对实际命令与参数。凭据按任务提供短期、受限权限，模型不持有全局长期密钥。需要删除文件或对外写入时按批准范围执行，不能只靠系统提示词约束 Shell。

#### 7. 什么时候使用 Deep Agents（深度智能体框架）属于过度设计？

如果任务只有少量步骤，不需要跨进程恢复或管理大量产物，引入长任务框架可能只增加配置、状态和排障成本。本项目现有协调器与受控工具循环已覆盖短链调用，应先用实际失败或需求证明需要哪些新增能力，再选框架。

### 五、多模态与语音 Agent（智能体）深挖

#### 1. Streaming ASR（流式语音识别）如何处理打断、端点检测和噪声？

VAD 检测是否有人说话，端点检测判断这次发言是否结束，ASR 在过程中产生可修订的临时转写。降噪和领域词表可改善药名识别，但关键药名、剂量和身份仍需用户确认。是否打断系统播报由对话控制层根据说话事件决定，不能把 ASR 临时文本直接用于提交写操作。

#### 2. Barge-in（用户插话）时如何停止 TTS（语音合成）并取消下游任务？

检测到用户插话后，先停止当前语音播放，再按业务策略取消旧话轮尚未提交的任务，给新话轮分配版本号。后续收到旧版本的模型或工具结果时，不用于生成新话轮回答。旧话轮已经发往远端的写操作仍需核对结果，不能因停止播报就认定已取消。

#### 3. 关键药名、剂量和身份信息如何做二次确认？

识别到药名、剂量或身份字段后，将规范化结果显示或复述给用户逐项确认，例如“识别为某药、某单位，是否正确”。确认记录关联原音频、患者和话轮版本，转写更改后原确认失效。存在无法消除的识别歧义时暂停相关动作，不让模型猜测关键字段。

#### 4. 多人对话如何做 Speaker Diarization（说话人分离）？

Speaker Diarization 根据声音和时间段区分“说话人 1、说话人 2”，但不能仅凭这个编号确定谁是医生或患者。真实身份需要登录、人工绑定或另行验证；尚未确认时只保存说话人编号，不给予对应业务角色权限。

#### 5. 语音、文本和工具事件如何维护统一时间线？

为每个音频片段、转写修订、话轮和工具调用保存编号、时间戳及其关联对象。例如工具调用要记录它依据哪一版已确认转写，而不只记录调用时间。修订后旧版本保留作审计，但只有当前有效且已满足确认条件的版本能触发新动作。

#### 6. OCR（光学字符识别）如何处理医学表格、单位和参考范围？

先识别表格行列和跨页关系，再把项目名、数值、单位与参考范围配成同一条记录，避免把相邻行数据拼错。关键字段保留页码、坐标和原图，检查单位与数值格式；不能识别或位置不确定的项标记待人工核对，不把 OCR 结果直接当可靠医学事实。

#### 7. DICOM（医学数字成像和通信）数据如何脱敏、授权和审计？

DICOM 可能同时在元数据标签和像素内的文字中含有身份信息，删除文件名或几个标签不等于完成脱敏。应按授权用途处理需要保留的临床字段，检查像素内文字和其他识别线索，并对存储、访问和删除留审计记录。是否适合对外使用还需验证去标识化效果，不能仅凭运行脱敏程序判断。

#### 8. 多模态模型输出如何回链到图片区域、页码和原始证据？

每个抽取字段应关联文件标识、页码或帧号、真实区域坐标和抽取版本，前端按这些信息定位原图。来源位置应由实际解析过程记录，不能让模型编造坐标。若图片与转写结果不一致，展示对应证据并标记待核验，而不是静默选一方。

#### 9. 音视频数据的存储期限、授权和删除策略如何设计？

按业务用途分别规定原音视频、转写、派生特征和审计的访问权限与保存期限，训练复用需要单独确认允许范围。删除时同时处理在线副本、缓存与索引；备份按明确的过期或删除流程处理，并说明何时不可恢复。不能只删除页面上的记录就声称全部副本已清除。

### 六、Agent（智能体）协议与平台能力深挖

#### 1. MCP（模型上下文协议）的 Tools（工具）、Resources（资源）、Prompts（提示模板）分别适合什么场景？

Tools 提供可带参数执行的能力，例如查询药品或创建草稿；Resources 提供客户端可读取的内容，例如一份文档或数据快照；Prompts 提供可复用的提示模板和参数。应按交互方式选择工具、资源或提示模板。读取资源、使用模板和执行工具仍分别受权限约束；当前项目主要使用 Tools。

#### 2. MCP（模型上下文协议） Sampling（模型采样请求）和 Elicitation（信息征询）如何做权限控制？

Sampling 是 MCP 服务端请求客户端调用模型，客户端应检查请求来源、输入内容、模型和费用预算，决定是否执行。Elicitation 是服务端通过客户端向用户请求补充信息，客户端展示来源与字段，并允许拒绝或取消；不能把它当作获取任意敏感信息的通道。具体能力按双方支持的协议版本核对，当前项目没有实现这两类交互。[MCP Elicitation 规范](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-06-18/client/elicitation.mdx)

#### 3. STDIO（标准输入输出）与 Streamable HTTP（可流式 HTTP 传输）如何选型？

STDIO 由客户端启动本地服务进程，通过标准输入输出交换消息，适合本机工具，但进程身份和文件权限仍需限制。Streamable HTTP 通过 HTTP 端点提供 MCP 服务，便于远程或多个客户端访问，需要认证、加密及代理超时配置。传输方式本身不提供患者或工具业务授权，当前项目使用 HTTP 服务。

#### 4. MCP Server（MCP 服务端）如何做多租户鉴权、限流和版本兼容？

先验证调用方身份并从可信身份确定租户，再在每次工具执行前检查该租户的数据源、工具和用户权限。限流与缓存键也包含租户范围，防止跨租户共享结果或耗尽配额。版本升级用明确接口版本和兼容测试，不能把客户端传来的 `tenant_id` 直接当授权依据；当前项目没有完整平台级多租户实现。

#### 5. A2A（智能体间通信）Agent Card（智能体能力卡）如何发现、缓存和更新？

Agent Card（能力卡）描述服务名称、端点、能力及认证方式，调用方可从可信配置、注册中心或协议约定的发现地址读取。缓存应记录版本和有效期，更新时核对端点与能力是否兼容，不在卡片中放密钥。能力卡说明“服务声称能做什么”，不等于授予调用权限；当前项目主要使用配置的专科地址。

#### 6. A2A（智能体间通信）任务状态、取消、回调和 Artifact（产物）如何设计？

短任务可以等待后直接返回结果；长任务应有任务编号、明确状态、产物引用以及查询和取消接口。回调关联任务与事件编号并去重，避免重复通知误触发处理。取消成功也要说明停止到哪一步，不能代表外部写入已回滚；当前项目主要使用请求—响应式专科调用，没有完整长任务生命周期。

#### 7. 协议层成功但业务失败时，错误模型应该如何表达？

HTTP 200 或协议消息正常返回，只说明通信按约定结束，结果仍可能包含业务失败。MCPAdapter 默认可能将 `isError` 转成普通返回文本；当前包装器关闭该错误吞掉行为，将其计为失败并阻止正常临床结论。当前协调器检查 `success`、专科名称、非空回答和轨迹格式，不把失败消息当正常医学答案。若扩展错误契约，应明确错误码、是否可重试及哪些部分已完成，尤其区分未执行与写入结果未知。

#### 8. 如何在协议升级时兼容旧客户端和旧 Schema（结构定义）？

新增可选字段通常可以兼容旧客户端，但修改必需字段、枚举含义或执行语义可能是破坏性变更。应通过版本或能力协商选择兼容格式，需要时新增端点或适配层，并用契约测试覆盖新旧客户端组合。字段名相同也要核对含义，不能只验证 JSON 能解析。

### 七、高级安全与 Computer Use（计算机操作）

#### 1. Browser/Computer Use Agent（浏览器/计算机操作智能体）如何隔离凭据和会话？

为每个用户和任务使用独立浏览器会话或配置，限制它可访问的账号、网站、文件和窗口。登录凭据由受控组件使用，避免交给模型或写入页面内容；上传、下载和剪贴板另按任务授权。任务结束后按保留规则清理临时数据，不能仅因浏览器窗口关闭就认为会话已失效。

#### 2. 如何防止页面内容中的 Prompt Injection（提示词注入）诱导点击或上传文件？

网页内容可能写“点击这里上传全部文件”，但页面无权修改用户任务和工具权限。动作执行前由模型外规则检查实际目标域名、文件、账号和用户批准范围；高风险提交先展示影响供确认。页面指令与用户授权冲突时应拒绝动作，仅靠提示词要求模型忽略恶意内容不够。

#### 3. 下载文件如何做类型校验、病毒扫描和隔离存储？

下载先检查来源和大小，再保存到不可直接执行的隔离目录，核对文件头与实际类型，而不是只信扩展名。随后做恶意内容扫描；压缩包限制解压总量、文件数量和路径，防止资源耗尽或目录逃逸。解析过程使用受限环境，扫描通过也不能视为绝对无风险。

#### 4. SSRF（服务端请求伪造）、路径穿越和任意命令执行如何防护？

SSRF 防护要核对实际连接目标，包括域名解析结果和重定向后的地址，拒绝未授权的内网及元数据服务访问。文件路径先解析、处理链接关系，再确认最终目标位于允许目录。命令使用固定程序和参数数组，避免拼接到 Shell；三者分别控制网络目标、文件目标和程序执行。

#### 5. 如何限制剪贴板、屏幕截图、外部域名和文件系统访问？

按任务限定可截图窗口、可读写剪贴板类型、允许的网络目标和文件目录，并在实际执行时检查。截图或剪贴板里可能同时含凭据和恶意文字，应先处理敏感信息，且不能把其中内容当高优先级指令。授予屏幕读取能力不等于授予任意文件上传能力。

#### 6. 审批界面怎样防止社会工程式参数替换？

可信审批界面展示最终对象、参数和实际影响，确认记录绑定操作者、任务版本、参数摘要与有效期。执行前重新计算摘要并核对批准；例如批准上传 A 文件后，目标变成 B 文件，就必须重新确认。审批界面的内容应来自受控程序，不能直接相信网页自称“已经批准”。

#### 7. 如何对高风险动作执行 Dry Run（试运行）和影响预览？

Dry Run 使用与正式执行一致的校验和计算逻辑，但在提交副作用前停止，返回计划修改哪些对象及预计影响。用户确认后再核对数据版本与最终参数，变化时重新预览。若试运行已经向医院或外部系统提交写请求，就不是真正的无副作用预览。

#### 8. 如何评估 OpenClaw 等具体方案的安全边界？

先明确要评估哪个版本、怎样部署，以及需要防范恶意网页、被攻破工具还是不可信用户。再依据官方设计和实际配置检查凭据、会话、沙箱和审批，不凭名称判断安全。面向可信本地用户的方案，不能未经测试就推断能隔离多个互不信任的租户；本项目没有采用该方案。

### 八、超大规模生产平台

#### 1. 多租户数据、模型配额和工具权限如何隔离？

租户可以是不同医院或机构，其身份应来自验证过的账号或服务凭据。数据库查询、对象存储、缓存、向量检索、下游凭据和费用配额都要限定租户，并在访问时校验。仅给表加 `tenant_id` 不够，后台任务、缓存命中和管理员入口也需检查，当前项目没有完整多租户体系。

#### 2. 如何设计 Model Gateway（模型网关）和多供应商路由？

Model Gateway 位于应用与模型供应商之间，统一处理身份、请求路由、预算、脱敏和调用记录。选择供应商要满足任务能力与数据允许范围；备用模型先验证工具调用和输出行为。主模型失败后不能把含医疗数据的请求自动转给未经批准的供应商，当前项目没有通用多供应商网关。

#### 3. 如何进行跨区域容灾、数据复制和恢复点目标设计？

RPO（恢复点目标）规定最多可丢失多长时间的数据，RTO（恢复时间目标）规定故障后多长时间内恢复服务。先按业务确定二者，再设计数据复制与备份，并演练恢复数据库、密钥、队列和接口连接。复制错误数据也会同步错误，因此复制不能替代备份；跨区域方案还需确认允许的数据使用范围。

#### 4. Service Mesh（服务网格）是否适合 A2A（智能体间通信）服务治理？

Service Mesh 可在服务通信层统一 mTLS、流量策略和观测，适合已有相应运维能力且服务较多的环境。少量服务也可以先用网关和独立服务身份，避免不必要的部署复杂度。无论采用哪种方式，网格识别调用服务不等于批准访问某位患者，业务授权仍由应用执行。

#### 5. 如何做全链路成本归因和租户级预算？

先为整轮任务记录各次模型输入输出词元、供应商计费、工具调用和计算存储开销，再归属到租户、用户和任务。租户预算在发起新调用前检查，避免等费用产生后才发现超额。共享批处理费用应按明确口径分摊，并区分总花费与每个成功任务的平均成本。

#### 6. 如何设计队列优先级、背压和 Admission Control（准入控制）？

Admission Control（准入控制）在接收任务时判断是否有足够预算和容量；队列按租户与优先级调度，同时限制长度和等待期限。Backpressure（背压）是在下游处理不足时减慢或拒绝上游请求，避免无限堆积。超过容量时给出明确处理结果，不能只增加入口实例而不管模型或数据库瓶颈。

#### 7. 如何定义 SLI/SLO（服务指标/服务目标）和 Error Budget（错误预算）？

SLI 是在明确统计窗口内实测的服务指标，例如任务成功率或延迟；SLO 是该指标应达到的目标。例如月成功率目标为 99.9%，错误预算就是该窗口允许的不成功比例或次数。统计分母和“成功”定义必须明确，权限与急症安全另设不可被平均值抵消的验收条件。

#### 8. 如何进行模型、Prompt（提示词）、工具和知识库的联合灰度？

每个发布版本固定模型、提示词、工具接口和知识索引的组合，先在同一任务集上对照，再让少量真实流量进入新组合。监控任务效果、错误和成本，触发回滚时恢复相互兼容的整套组合，而不是只换回模型。高风险场景需独立通过验收，当前仓库的 90/10 路由配置不代表已完成真实灰度。

#### 9. 如何验证容量扩展没有放大数据库、Redis（共享内存存储）和医院接口压力？

记录入口扩容前后，数据库连接数、Redis 延迟、医院接口并发及失败率是否增加到不可接受范围，再用完整链路负载验证。限制跨实例的总连接和下游并发，不能让每个新实例都按原上限额外占资源。HPA 增加入口实例只扩大上游处理能力，不会自动提高医院接口配额或数据库容量。

### 九、个人与通用软技能

#### 1. 为什么离开上一家公司？

我希望下一阶段更深入 Agent（智能体）工程化，围绕工具治理、状态、评测和稳定性承担完整模块责任。这份岗位的具体工作如果与该方向匹配，就是我选择机会的主要原因。

**如果追问“是不是因为薪资”：** 薪资会综合考虑，我更关注工作内容、成长和责任，具体待遇结合岗位正常沟通。

**如果追问“新公司以后遇到瓶颈还会不会走”：** 我会先明确业务目标和双方预期，遇到短期困难通过项目改进解决，希望持续承担有价值的责任。

#### 2. 期望薪资如何结合城市、岗位和总包回答？

我的期望是结合岗位责任、城市和全年总包沟通一个可谈区间，明确月薪、奖金与福利构成。具体金额按真实预期填写。

#### 3. 未来两到三年的技术或管理规划是什么？

未来两三年我希望先把 Agent（智能体）工程化、评测和稳定性做深，再逐步承担架构与项目交付责任，用完成的业务结果验证成长。

#### 4. 自己最擅长的 Agent（智能体）能力是什么，能否承受连续深挖？

如果我的真实优势是工具治理，我会围绕权限、参数、重试、幂等和审计展开，并准备能对应代码的设计与失败案例。

#### 5. 遇到无法解决的问题，如何最小复现并逐级求助？

先整理能稳定触发问题的最小输入、环境、预期与实际结果，并记录已经验证过的假设，再查官方文档或请同事、供应商协助。若影响交付，应尽早说明影响范围、临时处理方式和需要谁决策，而不是等到截止时间才报告无法解决。

#### 6. 如何处理跨部门目标冲突和资源不足？

先明确各方真正要求的结果、资源限制和最终决策人，再列出可以交付的选项及其成本、风险和延期影响。例如同时要求新增功能与按原日期上线时，应让负责人明确优先级。决定后记录范围和责任，避免开发人员自行猜测取舍。

#### 7. 如何向非技术人员解释模型边界和风险？

用一个业务例子说明系统能完成哪些步骤、哪些字段由人确认、失败时会怎样提示，例如能整理指南依据，但不能独立诊断患者。再用样本和分母明确的指标说明验证范围，不把模型术语或一次成功演示当作效果保证。

#### 8. 如何复盘一次失败，而不是把责任归给模型或客户？

先说明任务目标和实际发生的事实，沿流程找到最早偏离预期的位置，再解释当时的判断为什么未能避免失败。修复要对应根因，并给出回归样本或流程变更验证是否有效。经历题使用真实案例，避免笼统归因“模型不稳定”或“客户需求不清”。

## 第五部分：具体场景追问

本部分通过二十八个具体场景解释失败路径，并分别说明当前处理方式与需要扩展的机制。

### 1. 四层意图识别是不是一定比单模型准确，能不能保证全部识别？

不能保证。级联让明确请求在较低成本的层结束，但前层错误接受后，后层没有机会纠正。要在同一批独立任务上比较级联和单模型方案的完整意图匹配、漏意图、延迟与费用；某个小回归集全对，不证明所有表达都能识别。

### 2. 用户没说“同时、另外”，怎么发现多意图？

当前正则可能在没有连接词时仍命中多个意图，但 BERT 只输出一个标签，向量层也依赖多任务线索选择多个候选，因此仍可能漏任务。若扩展，应按语句分别识别动作、对象和交付物，再核对否定与更正。例如“查阿司匹林说明书，核对指南随访建议”有两个目标，即使没说“同时”也应保留两项。

### 3. 十分类 BERT（本项目用于意图分类）能直接解决多标签意图吗？

不能直接解决。当前 Softmax 将十类作为互斥候选，只选择最高分标签；取前两名也可能只是模型在两个类别之间犹豫。多标签方案可用每类独立的 Sigmoid 分数和二元交叉熵训练，或者先分句分类再合并，但都需要相应标注数据和阈值验证。

### 4. 正则标记 0.99、BERT（本项目用于意图分类）阈值 0.95、向量阈值 0.78、大模型标记 0.70，能直接比较吗？

不能。0.99 是规则命中后由代码赋的分数，BERT 输出 Softmax 分数，向量层输出余弦相似度，LLM 的 0.70 也是固定赋值，不是模型计算的可靠概率。只能按各层自己的条件决定是否接受，并用评测报告该层的覆盖率和接受准确率，不能取最大分决定谁更可信。

### 5. 向量第一名超过阈值，但第二名很接近，怎么办？

第一、第二名接近可能表示一句话有两个任务，也可能只表示两类意图难区分，不能直接把两者都返回。当前没有多任务线索时，只要第一名达到 0.78 就接受；有线索时才用 0.04 分差筛选多个候选。若增加单任务分差拒识，应让低分差请求进入核对或澄清，并用独立样本验证误拒率。

### 6. 为什么四层都正常工作，仍然会把不支持的问题分进医疗类别？

十分类模型总是在已有标签中比较，即使输入不属于支持范围，也可能给某个医疗标签高分。当前在意图识别前加范围守卫：不支持的请求结束，混合请求只传递与原文一致的医疗片段，不确定则先澄清。范围守卫也可能出错，因此其测试与分类层的 OOD 测试分别报告，不能宣称前置守卫保证全部正确拒识。

### 7. 输入很长，意图识别为什么突然变差？

先查看分词后的长度与模型实际收到的内容。当前 BERT 输入会截断到 128 个词元，用户放在末尾的第二个目标可能根本没进入模型；这是输入丢失，不一定是模型不理解。可用相同目标分别放在开头、中间和末尾做对照，再评估分段或更长输入，后者也要匹配模型支持范围。

### 8. 多意图都路由到同一个 Agent（智能体），还需要拆任务吗？

当前计划会把目标专科去重，同一专科只执行一次，但分派的任务文本仍应包含全部目标。例如指南检索和检验解读都归 GuideAgent，不能因只调用一次就遗漏其中一项。后续可增加交付物清单逐项验收；当前“有成功工具且无工具失败”的门槛不能证明每个目标都已完成。

### 9. 为什么不能用同一批问题训练、调阈值和证明效果？

训练集用于学习参数，验证集用于选阈值或方案；若再用这两批样本证明最终效果，就可能只是在报告对已见数据的适应程度。最终测试集应保持独立，合成数据还要尽量按模板和同义表达族划分。删除完全相同文本只能减少直接重复，不能排除换词后的同模板泄漏。

### 10. 多意图应该看准确率还是 F1？

应同时看多种指标。Exact Match 要求预测意图集合与正确集合完全一致；Micro-F1 把各类判断合并计算，常见类影响较大；Macro-F1 先逐类计算再平均，更容易看到少数类不足。另列高风险漏意图，并分别报告单意图、多意图和域外样本；不能只用一个总体分数解释全部效果。

### 11. 如何发现级联中某一层实际上没有价值？

在相同评测集和配置下，分别跳过某一层，再比较完整任务效果、延迟和费用，这就是 Ablation（消融实验）。还要单看真正进入该层的残余样本，避免被大量前层已处理的简单请求稀释。若该层不提高覆盖或效果却增加明显成本，才有依据调整或移除。

### 12. 两个医生同时操作同一会话，会不会覆盖状态？

不同医生的会话键包含不同员工 ID，即使患者和会话编号相同，也不是同一个历史存储键。若同一员工对同一患者会话同时发起两轮请求，整轮锁会阻止交错执行。两名医生仍可能通过不同会话修改同一患者档案，这需要档案版本控制，不能靠会话锁解决。

### 13. 调模型时为什么不一直持有数据库事务？

模型和网络等待可能持续数十秒，期间一直持有数据库会话或事务会占用连接并增加锁等待。当前入口先读取授权与档案，结束读事务后执行模型流程，最终再开短事务复核权限并保存。若增加并行数据库任务，各任务还需自己的 AsyncSession，不能共同操作一个会话对象。

### 14. 转诊接口超时，但医院其实已经创建记录，应该重试吗？

不直接重试。当前本地操作记录保留 `unknown`，同一操作再次到达会被阻止；工作人员应通过原请求标识查询本地状态，再核对 HIS 是否已有对应转诊草稿。若医院没有可靠查询或幂等能力，需人工处理，不能换一个请求标识绕过未知状态。

### 15. 数据库写成功了，但通知消息没发出去怎么办？

若扩展消息通知，可把业务记录和待发送事件放在同一数据库事务中提交，再由后台投递事件；发送失败重试，接收方按事件编号去重。这就是 Transactional Outbox（事务发件箱），解决本地业务与通知可靠交接，不能自动让医院写入与本地数据库成为同一事务。当前项目未实现 Outbox。

### 16. Redis（共享内存存储）分布式锁过期后，旧任务继续写入怎么办？

当前释放 Redis 锁时检查所有者，防止旧任务删除新任务的锁，但这不能阻止旧任务继续写数据。可扩展递增的 Fencing Token（栅栏令牌）或版本号，让实际写入目标拒绝过期执行者；目标也必须参与校验。当前没有该机制，续租也不能覆盖所有暂停后迟到的写入。

### 17. 用户关闭页面，后台任务是不是自动停止？

不一定。网络断开可以结束本地响应等待，但正在工作线程或远端服务中执行的任务可能继续，已发出的写入尤其不能假定撤销。若完善取消链路，应检测断连、停止新调度、传递取消并清理资源；捕获 `CancelledError` 清理后继续传播。最终仍需查询相关写操作和下游结果。[Python 任务取消说明](https://docs.python.org/3/library/asyncio-task.html#task-cancellation)

### 18. 熔断器能否把所有错误都计为服务不可用？

不应一概计入。例如药名参数无效或员工无权限，说明请求不能执行，不表示医院服务不可用。当前医院熔断只统计网络与指定 HTTP 瞬态错误，A2A 的计数范围则包含专科调用失败；应按这两种口径解释指标。熔断状态各进程分别维护，不是全系统统一计数。

### 19. 任务开始时有权限，执行中权限被撤销怎么办？

当前 MCP 在每次工具执行前查询员工状态和患者权限，业务入口在最终保存前也复核；因此开始时有权限不代表整轮都获准。撤销发生后，后续校验应拒绝，但已经提交的远端写入不会被追溯撤销。若增加缓存或任务恢复，这些入口也应重新授权，不能仅依赖开始时的快照。

### 20. 缓存为什么可能把其他患者的信息返回出来？

若只用问题文本或相似向量作为缓存键，不同患者都问“能吃这个药吗”时，可能命中同一份个体答案。个体缓存必须包含员工或授权范围、患者和相关事实版本，读取时重新鉴权。公共药品说明书可单独缓存，但不能混入个体结论；当前会话存储不是这种医学答案缓存。

### 21. 开了脱敏函数，是否意味着监控平台绝不会收到原文？

不能保证。模型输入脱敏后，异常、回调或嵌套追踪仍可能从其他路径输出原文，应检查每个实际出口。当前子专科详细追踪关闭，外层记录脱敏摘要，指标标签也不放患者或请求标识；仍需核查目标环境日志和第三方配置。运行一次脱敏函数不等于完成全链路泄露验证。

### 22. HMAC（消息认证码）签名正确，就能防止接口重放吗？

不能。HMAC 证明消息未被改动且签名方持有共享密钥，但攻击者仍可能再次发送截获的同一合法请求。当前发送端把时间戳与正文一起签名，接收方还必须检查时间窗口，并按需要验证随机数与去重记录；这些下游措施要通过医院契约确认。业务写入另需幂等，传输加密也不可省略。

### 23. PyTorch（深度学习框架）能识别 CUDA（英伟达并行计算平台），为什么加多个服务进程反而显存不足？

GPU 可用只说明驱动和环境能访问设备，不保证显存能容纳多个进程。多个入口进程可能各自加载本地 BERT、BGE-M3 及运行缓冲，模型副本和并发输入叠加后就会耗尽显存；云模型权重不在这些进程中。应测各进程峰值，再考虑减少进程、限制并发或集中本地模型推理。

### 24. 健康接口成功，为什么真实问答仍然失败？

Liveness 主要判断进程是否存活；Readiness 按配置判断是否具备接收流量的条件；Startup 给启动过程留出检查时间。它们没有必然执行一次真实医学问答，医院接口契约、模型能力或业务参数仍可能出错。应在授权测试环境验证完整读请求，健康接口的吞吐不能推算问答吞吐。

### 25. 服务商说兼容模型接口，为什么换模型后工具调用坏了？

“兼容接口”可能只表示端点和基础字段相似，不保证支持相同的工具选择、结构化输出或流式参数。切换前应验证模型能返回合法工具名、完整参数及预期结束标记，再检查多次调用和失败行为。若采用流式工具参数，必须收齐并校验后再执行，不能边收到片段边提交动作。

### 26. 自动化测试通过，为什么不能证明所有集成都已验证？

测试只证明所覆盖的场景与组件组合。真实 A2A/MCP 通信测试若替换了模型和医院接口，能验证权限及协议处理，却不能证明供应商模型和医院数据都可用。报告要写明哪些组件真实、哪些使用替身；正式验收还需目标环境和真实接口的授权读写验证。

### 27. 压测并发数、每秒请求数和延迟为什么对不上？

虚拟用户数是压测脚本的用户配置，一个用户可能在思考或等待，不等于当前同时处理的请求数。稳定状态且统计范围一致时，平均在途请求数约等于每秒完成请求数乘平均请求停留时间；不能用 P95 延迟代替平均值。解释报告时还要核对持续时间、用户等待设置和是否包含完整 SSE 响应。

### 28. 面试官要求讲一次线上故障，没有真实案例怎么回答？

我会如实说这是故障注入验证或设计方案，再讲现象、定位、处理和回归。具体案例要能对应代码与记录，线上经历按真实情况回答。
