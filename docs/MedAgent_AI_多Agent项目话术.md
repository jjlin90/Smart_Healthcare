# MedAgent AI 多 Agent（智能体）项目话术与实战追问

核对日期：2026-09-30。本文先用简短示例和详细走读解释项目，再进入面试话术与追问；从头往下读即可。第一至二十一章描述当前代码；后续扩展题描述设计方法，不能自动视作已经实现。上线条件见 [生产验收清单](production-readiness.md)，最近完整项目核查见 [核查记录](audit-2026-09-28.md)。

## 项目定位：为什么做、解决什么问题、效率体现在哪里

### 1. 面向谁，帮助完成什么工作

项目定位是**面向院内医生、药师和医务管理人员的临床辅助任务工作台**。员工在授权患者范围内，用自然语言提出药品查询、用药审核、指南检索、检验数值辅助解读或转诊协同等任务，系统负责识别需求、调用允许的工具并整理结果，最终由临床人员复核。

核心交付物是有工具依据、符合患者权限、能查执行状态的辅助结果。临床人员仍负责医疗判断；当前检验解读需要提供数值，转诊工具生成待确认草稿，真实医院接入需另行联调验收。这些边界决定了它适合辅助工作流程，不能据此宣称已经自动完成诊疗。

### 2. 为什么要做：从工作需求推到工程问题

项目针对的是一类信息查询与任务协调需求：一个请求可能同时涉及药品、指南和患者背景，员工需要得到与当前任务有关的资料并核对。下面列的是项目的需求出发点，未把它们当成已经在目标医院调查、计时过的事实。

| 需要改善的问题 | 本项目怎样处理 | 具体价值 |
|---|---|---|
| 一个请求涉及不同类别的资料，需要分别查询后整理 | 统一输入，按意图分派给对应专科，再汇总工具结果 | 减少员工手工分派任务和拼接结果的步骤 |
| 请求缺药名、检验数值等关键条件，容易反复沟通或查错内容 | 在执行前检查关键槽位并追问 | 将参数补全放在调用工具之前 |
| 医院工具涉及不同患者和不同操作权限 | 入口与工具执行层分别核验员工、患者和动作范围 | 让查询便利性与业务授权同时成立 |
| 只有生成文本，难以判断依据是否取得、操作是否成功 | 要求有效工具证据，记录工具轨迹、写操作状态和最终保存确认 | 便于复核结果及定位失败阶段 |
| 工具请求超时后再次提交，可能重复执行写操作 | 持久化占位、参数校验、未知结果阻断及状态查询 | 降低同一请求被盲目重复执行的风险 |

所以为什么选择 Agent：自然语言请求需要转成不同的工具动作，部分请求需要组合多个专科结果。为什么分三个专科：按症状、药品、指南检验划分可见工具及职责，便于约束权限和检查失败。若只是固定表单查一个接口，普通业务接口也能完成；采用多 Agent 的理由应落在任务变化和受控编排需求上。

### 3. 效率收益在哪里，哪些已经有证据

**工作步骤上的收益**：在接口完成配置与验收后，员工可以在一个入口提出跨类别需求，由系统组织查询和结果汇总，目标是减少重复输入、分别查询及手工整理。这是功能设计带来的预期收益，当前没有同一批任务的人工与系统耗时对照，也没有医院使用前后统计，尚不能量化节省时间或提升百分比。

**模型调用上的优化机制**：四层路由在某层接收后停止继续分类；简单任务直接分派，复杂任务才进入规划。因此，相比“所有意图都由云端大模型分类、所有任务都生成计划”的流程，部分请求能省去相应模型调用。但前置范围判断、专科工具循环和最终汇总仍可能调用云端模型；没有端到端时延、调用成本和对照实验时，不能直接宣称整个请求更快或云端成本下降了多少。

**等待体验上的改善**：最终汇总采用 SSE 增量输出，员工可在生成结束前阅读已到达的文本。当前专科按顺序串行执行，文字流在工具完成后才开始；这改善的是汇总阶段的展示方式，不是已经证明总处理时间缩短。

**现有数字的用途**：33 条意图路由工程回归的严格匹配率与 micro-F1 均为 100%，以及当前 127 项自动化测试，支持工程正确性与边界验证。历史约 401 RPS、P95 790 ms 只来自健康接口压测，不代表完整问答效率，也不能换算为医生工作效率。

### 4. 面试时怎样讲业务价值

> 我做这个项目，是希望把院内员工分散的信息查询和多任务协调收敛到一个受权限控制的入口。员工提出需求后，系统识别任务、补齐关键条件，再让对应专科调用限定工具并汇总证据。它主要减少的是人工分派和整理步骤，同时让患者权限、写操作状态和结果保存可检查。当前我能证明的是工程功能、路由回归和故障处理；还没有医院人工耗时对照，所以我不会把它说成已测得某个效率提升比例。

如果需要验证效率提升，应选取相同难度的药品查询、指南检索和组合任务，对照人工流程与系统辅助流程，记录主动操作时间、等待时间、切换次数、临床复核及修正时间、任务成功率和模型调用成本。保证结果质量与授权条件一致，再计算时间节省率：`（人工基线耗时－系统辅助耗时）/人工基线耗时`。系统辅助耗时必须包含必要复核，不能只统计模型出字时间。完整问答的响应速度则单独测首段文本时间、端到端 P50/P95，不能用健康检查代替。

## 先用一个例子理解项目

把它想成院内员工使用的任务助手。医生登录后选择自己有权限查看的患者，输入“解读以下检验数值，并核对某种药品的注意事项”。以下是**流程示例**，不是一次真实医院接口调用或临床判断；检验数值须由请求提供，当前工具不会按患者标识自动拉取整份报告：

1. **先确认谁在问、能看谁。** FastAPI 检查员工账号、当前角色和患者授权；未授权就停止，不把患者资料交给模型。
2. **判断要办什么。** 急症规则和业务范围守卫先处理不适合常规问答的输入。意图识别发现这里包含“检验结果辅助解读”和“药品信息查询”；如果缺少必要的检验项或药名，先追问。
3. **把任务分给合适的专科。** 两种不同任务由主协调器形成短计划，通过 A2A（智能体间通信）分别交给指南和药品智能体；单一任务可以直接分派。
4. **专科通过受控工具找依据。** 智能体用 MCP（模型上下文协议）工具读取授权范围内的检验或药品信息。工具服务再次核验员工、患者及工具权限；模型生成的内容本身不能替代工具结果。
5. **汇总并返回。** 只有拿到有效工具证据且没有工具失败，才组织回答。服务保存必要的审计和会话状态，再通过 SSE（服务器发送事件）发出完成事件。实际医学结论仍需临床人员复核。

记住三个分工就能继续读后文：**FastAPI 管入口和权限，A2A 管主协调器与专科之间的任务传递，MCP 管专科能调用哪些工具。** BERT 和向量模型负责意图路由；云端大模型负责规划、专科推理或结果组织。它们各自解决不同问题。

本地测试、合成数据和上述示例证明的是代码路径及工程边界；真实医院接口联调、临床效果和生产验收要看独立证据。

## 项目理解详解：按一次请求走读代码

### 先说清楚：这个项目要解决什么

院内员工可能在一次工作中要核对症状、用药和检验信息。如果让一个大模型直接读问题、随意选择医院接口，容易遇到三个问题：它可能看错患者、调用不该调用的工具，或者在工具失败后编出看似完整的答复。

本项目把工作拆成几层：**入口核身份和患者权限；路由层判断任务类型；专科智能体调用限定工具；结果层整理工具证据；存储层留下必要记录。** 这就是它的业务主线。它面向医生、药师和医务管理人员，患者是被授权访问的数据对象，不是工作台登录角色。当前没有患者挂号、缴费等自助服务入口。

用一句话概括：**员工提出院内任务，系统先确认权限和任务范围，再安排合适的专科智能体查证据，最后返回需临床人员复核的辅助结果。**

#### 读图时只记五个角色

| 角色       | 你可以怎样理解   | 本项目中的实现                                                         |
| -------- | --------- | --------------------------------------------------------------- |
| 员工工作台    | 医生操作的页面   | `streamlit_app.py`，负责登录、选择患者、提问、展示过程和结果                         |
| API 入口   | 门卫与任务总台   | `backend/main.py`，负责认证、授权、请求状态、保存及流式返回                          |
| 主协调器     | 判断任务并分派   | `backend/agents.py` 的 `MedicalCoordinator`；单任务直接分派，多任务先规划       |
| 专科智能体    | 在各自领域完成任务 | 症状、药品、指南三个 Agent（智能体）；服务入口在 `backend/a2a_server.py`             |
| MCP 工具服务 | 受权限控制的操作台 | `backend/mcp_tools.py` 提供工具，`backend/mcp_security.py` 每次调用前复核权限 |

**A2A**（Agent-to-Agent，智能体间通信）解决“主协调器怎样把任务交给专科服务”；**MCP**（Model Context Protocol，模型上下文协议）解决“专科怎样调用工具”。BERT 分类模型和 BGE-M3 向量模型负责路由，不是给患者下医学结论的主模型。

```mermaid
flowchart LR
    员工 --> 工作台 --> API[API：身份与患者授权]
    API --> 守卫[急症、范围与澄清]
    守卫 --> 路由[意图识别与任务规划]
    路由 -->|A2A| 专科[症状 / 药品 / 指南智能体]
    专科 -->|MCP| 工具[授权工具与真实数据接口]
    工具 --> 汇总[证据汇总]
    汇总 --> 保存[审计与会话保存]
    保存 --> 工作台
```

这张图画的是**正常请求的主路径**。急症、越界或缺信息的请求会在相应守卫处提前结束；工具失败也不会沿“正常证据汇总”路径完成。

### 第一遍：先看最短的一条请求

假设**已授权**的医生在工作台选中患者，输入：“查询阿司匹林的说明书”。这只是读信息的示例；真实药品库未配置时，工具会报错。

1. 工作台把 `patient_id`（患者标识）、问题、会话标识、请求标识发给 `POST /api/chat/stream`。若没有勾选写操作，`approved_actions`（本次允许的写动作）是空列表。代码见 `streamlit_app.py` 的 `_sse_events`。
2. FastAPI 先验员工 JWT（登录令牌），再从数据库读取员工当前状态和角色，并检查这个员工能否访问所选患者。检查失败时，请求到不了模型。代码见 `backend/auth.py`、`backend/access.py`、`backend/main.py` 的 `chat_stream`。
3. 主协调器依次处理急症规则、业务范围判断、意图识别和必要信息检查。这句话有药名，通常可归到“药品信息查询”；分类具体命中哪一层取决于输入和当前模型，不能预先保证。代码见 `backend/agents.py` 的 `MedicalCoordinator`。
4. 如果只有药品任务，协调器直接选 `DrugAgent`，不用为了一个任务再生成跨专科计划。主协调器通过 A2A 发送任务，并附带短期签名委托，限定员工、患者、请求、专科和工具范围。
5. 药品专科的模型可在自己的工具白名单内选择 `query_drug_info`。MCP 服务重新检查委托令牌、员工和患者权限，工具才会调用配置的药品接口。这里模型**提出调用**，服务器**决定是否允许执行**。
6. 专科把真实工具结果作为依据生成辅助内容；如果没有成功工具证据或工具执行失败，不能把模型生成的文字当作正常临床结果。API 记录审计和符合条件的咨询结果、更新会话，最后发送 SSE（服务器发送事件）的 `done` 完成事件。

你可以把这条链背成：**页面发请求 → API 验权限 → 主协调器定意图 → 药品智能体查工具 → 有证据才答复 → 保存后确认完成。**

#### 一个容易混淆的点：读工具与系统记录

`query_drug_info` 是只读业务工具，不需要员工勾选高风险写动作。即使这次只查询药品，API 仍可能按存储策略保存**本次咨询结果和审计日志**；这与允许模型调用 `save_medical_record` 去**额外创建辅助记录**不是同一个动作。“没有勾选写工具”不等于“系统完全不写任何日志或会话”。

### 第二遍：看一个多任务请求为什么要规划

假设医生已经提供了检验项目、数值、单位、参考范围，又问某种药品的注意事项。这是**流程示例**，不包含真实患者信息。

| 处理点  | 系统要回答的问题     | 为什么需要这一步                   |
| ---- | ------------ | -------------------------- |
| 业务范围 | 是院内医疗辅助任务吗？  | 非医疗请求不应进入医院工具链；混合请求只保留医疗部分 |
| 意图识别 | 是一件事还是多件事？   | “检验结果辅助解读”与“药品信息查询”归属不同专科  |
| 信息检查 | 药名和检验数值是否够用？ | 缺关键参数先追问，不让工具猜输入           |
| 规划   | 哪个专科先做、各做什么？ | 把多任务拆成短计划，并校验专科名单和重复步骤     |
| 执行   | 工具有没有真实返回？   | 避免用空结果或失败结果包装成答案           |
| 汇总   | 怎样把两份结果说明白？  | 最终答复只能基于已得到的专科结果           |

代码中 `Planner` 会生成一个短计划；计划只允许已识别意图所需的专科，越界或重复步骤会换成受控计划。`MedicalCoordinator` **按计划顺序串行**调用专科，当前没有“这两个专科并行调用后同时合并”的实现。每个专科内部再用 LangChain `create_agent` 执行 ReAct（推理与行动）工具循环：模型提出工具调用，收到工具返回后继续判断，直到答复或达到预算。

**检验工具的边界要记住：** `interpret_lab_results` 接收请求提供的检验数据并调用配置的 LIS（检验信息系统）解释接口。当前代码没有“只给 `patient_id` 就自动从医院拉取整份报告”，也没有影像识别或 EMR（电子病历系统）连接器。说明这一点，比把“报告解读”讲成万能读报告更准确。

### 第三遍：为什么有四层意图识别

“意图”就是这句话要办的业务，例如药品查询、症状评估或转诊协同。系统目前有**十种院内任务标签**，但只有**三个专科智能体**；多个标签可以归到同一个专科。比如药品查询与用药审核都归药品专科。

四层是按顺序尝试的路由方法，不是四个模型同时投票：

1. 正则规则先处理关键词与表达很明确的请求。优点是快、可解释；缺点是复杂说法可能漏掉。
2. **本地 BERT** 在十类标签里做单标签预测；分数达到接受阈值才采用。它的 Softmax 分数不是“答案有百分之多少医学正确”。
3. **本地 BGE-M3 向量相似度**把问题与版本化意图原型比较，尝试承接前面未接受的请求；先检查相似度阈值；检测到多任务提示时，还用候选间距筛选组合标签。具体接收条件见第六章。
4. **云端大模型兜底**处理仍无法确定的表达，并把输出限制在允许的任务标签内。调用前对已知敏感字段做规则脱敏；这不等于完全匿名化，也不能代替医院的数据使用审批。

在这四层之前还有 **Domain Guard（业务范围守卫）**：判断医疗、非医疗、混合或不确定。之后还有 **Clarification Guard（澄清守卫）**：问“药名是什么”“报告的项目和值是什么”等。范围判断、意图分类、信息补全是三个不同问题。想象一条问题“帮我看看这个药”：它可能属于医疗范围，也可能识别为用药任务，但缺药名，仍必须先追问。

十类标签的原文、阈值和各自的测试分母见[项目话术第六章](MedAgent_AI_多Agent项目话术.md#六十分类与评测口径)。不要把“十类”说成十个 Agent，也不要把合成测试集分数说成临床准确率。

### 第四遍：三个专科和十四个工具怎样对应

| 专科                  | 主要负责                | 白名单内工具数量 | 记忆方法           |
| ------------------- | ------------------- | --------:| -------------- |
| SymptomAgent(症状智能体) | 症状、院内分诊、转诊协同        | 6        | 与症状、科室、病史和转诊有关 |
| DrugAgent(药品智能体)    | 药品资料、相互作用、禁忌和替代药    | 4        | 与药品安全有关        |
| GuideAgent（指南智能体） | 指南、检验辅助解读、诊疗路径和辅助记录 | 4        | 与指南和检验有关       |

三组工具合计 14 个注册工具，其中 11 个经配置访问外部服务，3 个访问本项目数据库。药品和指南专科得到服务端提供的可信患者档案副本，不代表它们各自拥有 `load_patient_history` 工具。完整工具名及分工见 `backend/agents.py` 的 `AGENT_TOOLS` 和 `backend/mcp_tools.py`。

为什么不让三个专科都看到全部工具？因为模型会根据可见工具选择动作。工具白名单先减少误选，再由 MCP 服务对每一次真实调用核验权限；提示词不能替代服务端校验。

### 第五遍：患者数据和写操作怎么守住

系统有两层身份：**员工登录身份**供工作台访问 API；**内部短期委托**供 API、A2A 和 MCP 服务之间传递受限任务。服务端每次重新查员工状态和患者授权，因此旧令牌不能让已停用员工继续查看患者。

有副作用的工具目前是 `save_patient_history`（更新本项目患者病史字段）、`save_medical_record`（另存本项目临床辅助材料）、`generate_referral`（请求 HIS 创建待医生确认的转诊草稿）。它们默认不提供给模型。员工要在**本次任务**勾选动作，服务端还会按角色和患者再校验；转诊仅医生角色可做。这个勾选是动作级授权，尚没有对模型最终生成的每个参数逐项预览签字。

写入前，MCP 服务以“员工 + 请求标识 + 工具名”记录操作占位，并保存患者及参数摘要。相同参数的已完成操作可以返回原结果；同一标识改参数会被拒绝；处理中或结果未知时不自动重发。特别是外部转诊：请求超时不能说明 HIS 一定没收到，必须先对照 HIS 记录和操作状态。这叫**避免盲目重试**，不能宣称跨本地数据库和医院系统已经实现“恰好一次”。

对外部结果也不能想当然：转诊工具要求 HIS 返回真实的转诊编号和“待确认/草稿”状态；缺失时不能自造一个本地编号称为成功。当前未配置真实医院接口时，相关工具明确失败，不生成模拟医学结果。

### 第六遍：对话、流式输出和失败状态

会话记忆按患者、员工和会话隔离，默认保留 1,800 秒、最多 20 条消息。API 对同一会话的一整轮任务加锁，防止两条同时提交的请求把状态交错。Redis 是共享会话存储；开发环境可使用进程内临时缓存。MySQL 存员工、患者档案、授权、咨询、审计和写操作状态。

SSE 可以理解为服务器按事件逐段告诉页面发生了什么：`session` 告诉页面请求标识，`meta` 说明路由信息，`trace` 给出工具步骤摘要，`delta` 送来文字片段，`done` 表示保存成功后的完成确认，`error` 表示失败。**看到部分文字不等于任务成功**；页面只有拿到 `done` 才能认定本轮完成。正式的模型文字流在专科工具结束、进入最终汇总之后才开始，不能把整个处理过程宣传成即时出字。

数据库提交、Redis 会话更新和 SSE 完成事件是先后操作，不是一个跨系统事务。若写操作已到达医院接口而本地确认丢失，界面会给出请求标识并查询操作状态；`pending`（执行中或待核对）和 `unknown`（结果未知）都需要核对，不能直接换新标识再提交。

A2A 传输历史采用最近消息优先裁剪：每条内容最多 4 KiB，历史 JSON 的 UTF-8 总量最多 16 KiB；完整会话存储仍最多 20 条。裁剪只用于可选上下文，当前任务单独传递，专科从数据库重新读取可信患者档案。裁剪可能丢失较早上下文，不应把历史作为关键临床参数的唯一来源。

## 一、先记住项目事实

- 面向院内医生、药师和医务管理人员；信息科负责账号及系统管理。患者是授权数据对象，不是登录角色。

- 主模型使用 SiliconFlow（硅基流动）的兼容接口，默认配置 `deepseek-ai/DeepSeek-V4-Flash`；本地没有主大语言模型。具体模型可用性须在目标账号联调。
- 三个专科 Agent、14 个 FastMCP 工具，其中 11 个外部接口工具、3 个内部数据工具。
- 已实现员工认证、患者授权、内部委托令牌、动作级写操作确认、持久化写操作去重、会话隔离、超时和错误处理。
- 已有测试及合成数据评测；医院接口路径是待按甲方契约适配的服务适配层，不是已经完成真实医院验收的证明。

## 二、面试开场话术

**简短介绍：** 我负责院内临床辅助平台的意图路由、跨 Agent 编排和受控工具调用。系统先校验员工身份及患者数据访问权限、急症拦截、业务范围判断和必要澄清，再按十类意图分派给症状、药品和指南三个专科智能体。工程侧重点是服务间鉴权、写操作约束、故障处理和可复现评测。

**成果介绍：** 构建 3,800 条院内意图合成数据，支持分类训练与阈值校准；33 条意图路由工程回归的严格匹配率和 micro-F1（微平均 F1）均为 100%。实现 14 个工具注册与专科白名单，通过权限撤销、跨患者调用、重复写入和错误流等自动化测试验证执行边界。

这些数字描述工程验证。面试追问真实临床效果、医院上线人数或业务收益时，只提供实际验收记录支持的结果。

## 三、每一步流程在做什么

```text
Streamlit 院内员工工作台
  → FastAPI：员工 JWT（身份令牌）校验、实时账号状态及患者授权
  → 急症规则：提示启动院内急救流程，不进入常规工具链
  → Domain Guard（范围守卫）：医疗 / 非医疗 / 混合 / 不确定
  → 四层意图识别：从十类院内任务中选择一个或多个
  → Clarification Guard（澄清守卫）：缺少药名、症状、检验项等时追问
  → 单专科直接执行，复杂任务由 Planning Agent（规划智能体）生成短计划
  → A2A（智能体间通信）：携带员工、患者、请求和工具范围的签名委托
  → 专科 create_agent：在工具白名单内做 ReAct（推理与行动）
  → MCP（模型上下文协议）：重新核验权限并调用 HIS、LIS、药品、指南或内部数据库
  → 汇总模型：流式组织已有工具证据
  → MySQL 事务提交 → Redis 会话及阶段状态 → SSE 完成事件
```

TTL（生存时间）限制会话保存时长；默认 1,800 秒、最多 20 条消息。MySQL 保存患者档案、临床辅助记录、权限、审计、转诊记录和写操作状态。

### 多任务请求如何变成受控计划

可以用“辅助解读已提供的检验数据，并查询某药的说明书”理解规划，但这不是一次真实医学执行记录。意图层需要保留两项交付物，再由 `INTENT_AGENT` 映射到 GuideAgent 和 DrugAgent。计划最多三个步骤，每个步骤只能属于注册专科，任务文字最多 4,000 字符。

`Planner._bounded_plan` 不只检查 JSON 能否解析，还检查专科集合是否与已识别意图要求的集合完全一致，以及有没有重复专科。如果模型生成了无关专科、重复步骤或缺少必要专科，会替换成受控计划：每个必要专科执行一次，任务使用原请求。模型返回结构无法通过校验时也有此回退；模型调用本身的网络错误并不因此自动变成成功。

随后 `MedicalCoordinator.stream_native` 在 `for` 循环里依次等待 A2A 结果。当前没有并行执行，也没有让前一个专科结果自动成为后一个专科输入的依赖图。两个专科都完成后，汇总模型才看到结果列表并组织最终文本。因此“串行”描述执行顺序，不代表已经实现完整的跨步骤数据依赖管理。

同一个专科可以负责多个意图，例如指南检索与随访管理都归 GuideAgent。代码会按专科去重，不为每个意图创建一个新 Agent。`complex_task` 也不只是“标签数大于一”：用药审核、检查报告辅助解读、转诊协同等单标签任务也可触发规划入口。

## 四、ReAct 与调用预算

专科使用 LangChain（大模型应用框架）`create_agent`构建 ReAct Agent，由大模型根据当前对话上下文和工具描述选择工具，应用服务端完成权限校验、参数校验及工具执行。工具执行结果以 `ToolMessage` 的形式作为 Observation（观察结果）返回模型，模型根据观察结果决定继续调用工具还是生成最终回答，形成 Reasoning → Acting → Observation 的循环。MCPAdapter（协议适配器）通过带短期令牌的 FastMCP Client 连接工具服务。

模型调用与工具调用分别最多 6 次，不应称为“总共 6 个 HTTP 请求”。同工具、相同规范化参数在一次专科运行内第二次调用会被拦截。没有成功工具证据，或运行中存在工具失败时，专科不能把生成文本作为正常临床结论返回。

默认单次模型超时 30 秒、模型输出上限 2,048 个词元、API 整轮超时 120 秒；医院 HTTP 单次超时 10 秒。取消本地等待不等于撤销已发出的远端写入，写操作结果不明时必须核对。

### 用一次工具循环理解 ReAct

以药品查询为例，下面只描述执行形态，不编造药品接口的具体医学返回：

| 阶段 | 谁负责 | 实际发生的事 |
|---|---|---|
| 准备上下文 | 专科服务 | 加入角色提示、脱敏后的近期历史和当前任务；仅暴露本专科允许的工具 |
| 选择动作 | 模型 | 生成 `query_drug_info` 等工具调用及参数，这是执行建议 |
| 验证与执行 | 工具包装层及 MCP 服务 | 复核工具范围、参数、员工和患者权限，允许后才访问配置的业务接口 |
| 返回观察 | 框架 | 把工具返回转换成工具消息，供模型下一轮判断 |
| 再次判断 | 模型 | 决定补充另一个允许的工具，或生成最终答复 |
| 接受结果 | 业务代码 | 检查工具轨迹是否至少有一次成功且没有失败，再接受专科答案 |

这里的 Reasoning 是模型选择下一步动作的过程，不代表系统应展示或上传模型的内部思维链。可供排障的 `trace` 是工具名、专科和执行状态等摘要，不是完整推理正文。内部工具循环由 `create_agent` 维护，业务代码负责权限、次数和结果验收。

### 为什么设置两种次数上限

模型调用最多 6 次，工具调用也最多 6 次，它们是两项独立预算。一轮模型回复可能包含多个工具调用，所以不能把一次模型调用、一个工具调用和一个 HTTP 请求当成同一个单位。预算耗尽会按错误退出；这能限制资源消耗，不能证明模型已经完成任务。

重复调用拦截又是另一层保护：同一次专科运行中，同工具和相同规范化参数再次出现会被阻止。它限制工具循环；跨请求写操作去重则由第八章的数据库操作键处理。二者的有效范围不同，不能互相替代。

## 五、三个 Agent 的边界

| 专科                  | 允许的工具                                                                                                            |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- |
| SymptomAgent（症状智能体） | analyze_symptoms、suggest_department、get_disease_info、load_patient_history、save_patient_history、generate_referral |
| DrugAgent（药品智能体）    | query_drug_info、check_drug_interaction、check_contraindications、query_drug_alternatives                           |
| GuideAgent（指南智能体）   | search_guidelines、interpret_lab_results、get_treatment_protocol、save_medical_record                               |

三个专科白名单共对应 14 个注册工具；药品和指南专科通过服务端档案快照获得病史背景。指南域的报告解读工具目前调用 LIS（检验信息系统）；影像图片、病理图片识别和 EMR（电子病历系统）连接器没有实现。病史及辅助记录保存在本项目数据库，不等同于医院正式电子病历。

## 六、十分类与评测口径

十类分别是：**症状评估、药品信息查询、临床指南检索、检验结果辅助解读、院内分诊建议、随访管理、用药审核、临床知识查询、转诊协同、检查报告辅助解读**。

**第一组｜SymptomAgent（症状专科）— 围绕"患者本人该去哪"**

- 症状评估 —— 现在怎么了
- 院内分诊建议 —— 去哪个科室
- 转诊协同 —— 换科室/换院怎么衔接

**第二组｜DrugAgent（药品专科）— 围绕"药物安全"**

- 药品信息查询 —— 这个药是什么
- 用药审核 —— 这么吃合不合、有没有风险

**第三组｜GuideAgent（指南专科）— 围绕"找规范依据 + 解读数据"**

- 临床指南检索 —— 权威标准怎么说
- 临床知识查询 —— 疾病知识/鉴别要点
- 检验结果辅助解读 —— 化验单怎么看
- 检查报告辅助解读 —— 影像/报告单怎么看
- 随访管理 —— 按诊疗路径跟踪复查

十分类描述业务标签数量，不是十个 Agent。BERT 使用 Softmax（归一化指数函数）做单标签分类；正则、多意图提示和大模型兜底支持组合标签。不同层的概率、相似度和固定分数不能直接比较。

| 验证对象        | 样本及结果                                                    | 含义                       |
| ----------- | -------------------------------------------------------- | ------------------------ |
| 合成启动数据      | 2,000 训练 / 400 验证 / 1,000 测试 / 400 挑战，共 3,800            | 类别平衡、集合间精确去重；还需关注模板语义相关性 |
| BERT 普通合成测试 | 1,000 条；0.95 阈值覆盖 98.8%，接受准确率 100%                       | 合成工程测试                   |
| BERT 挑战子集   | 100 条否定/模糊单意图，Top-1 60%；阈值覆盖 24%，接受准确率 100%；50 条 OOD 全拒识 | 不同分母单独统计                 |
| 向量残余集       | 400 条挑战中 236 条到达向量层；0.78 阈值接受 10 条且均正确                   | 剩余样本继续兜底，不是全量分类准确率       |
| 路由回归        | 33 条，严格匹配率、复杂任务标记准确率、micro-F1 均为 100%；正则 32 / 向量 1       | 小型工程防回退集合                |

数据原型、校准集和回归集独立管理；不能用挑战集反复调参后再把同集成绩当作独立测试。临床效果需要经授权的真实数据、独立标注和临床审核。

### 四层路由的具体接收条件

代码入口是 `IntentClassifier.classify`。先理解“接收”：一层接收结果后，后面的层通常不再执行；未接收才继续，所以四层不是四次必走的模型调用。

| 走到的层 | 当前接收条件 | 没接收时怎样处理 |
|---|---|---|
| 正则 | 已命中多个意图，或虽只命中一个但没有多任务提示 | 保留命中作为候选线索，继续检查 |
| BERT | 有有效结果、分数至少 0.95，而且没有多任务提示 | 继续向量层，避免让单标签分类压掉多任务 |
| 向量 | 第一候选至少 0.78；无多任务提示时取第一候选，有提示时需选出多个候选才在主分类器接收 | 继续大模型兜底 |
| 大模型 | 返回允许标签并通过结构检查 | 有已命中正则时可返回规则结果并标记 `llm_failed`；没有规则结果则失败 |

这些数字是默认配置，目标环境可以调整。向量层先对不同意图的原型分别取最高相似度，再比较意图候选；多任务提示下，候选还要超过 0.78 且与最高分差不超过 0.04，最多取三个。**当前单任务分支不使用 0.04 做“第一、第二太接近就拒收”的普遍校验**，不能把这个参数讲成所有请求都生效的置信度安全线。

例如“查某药说明书”若正则接收，就不用再跑 BERT；“正在用某药，还想核对检验异常”有多任务提示，即使 BERT 对一个标签很自信，也不能仅凭该单标签提前结束。具体结果仍受实际表达、规则和模型影响，这两个例子用于解释分支，不是新增评测成绩。

### 怎样解释覆盖率和接受准确率

BERT 在 1,000 条合成测试中覆盖 98.8%，意味着其中 988 条达到接受阈值；接受准确率 100% 是这 988 条都正确，不表示剩下 12 条也正确。剩余样本由后续层处理。挑战单意图子集的 24% 覆盖和 60% Top-1 同样是两种统计口径：一个看达到阈值的子集，一个看不经过阈值筛选的首选标签。

向量 10/236 只评价前面没有接收的残余集合；33 条回归则评价固定工程用例的最终路由。它们分母、目标和流程位置不同，不能加总成一个“系统准确率”。当前 33 条中 32 条正则、1 条向量，也不足以单独证明 BERT 和大模型在真实流量中的收益。

出现分类错误时，先记录输入、预测标签、命中层、经过的层和阈值，再判断是规则误匹配、BERT 单标签限制、原型相似度问题还是大模型输出错误。只调整最终提示词，可能改不到真正出错的那一层。原型的精确去重测试防止原文重合，但近义表达和模板族隔离还需要独立检查。

## 七、A2A 服务身份与通信

主协调器实际通过 A2A 发送 task（子任务）、patient_id（患者标识）和裁剪后的 history（只读历史），不发送 profile（档案副本）。A2A 服务先验证委托令牌的签名、有效期、签发者和 audience（目标服务），再按令牌中的员工及患者重新查数据库，组装专科使用的可信档案。协调器的本地调用参数中仍可能包含 profile，但 `_call_a2a` 会在发送前移除它。

子服务运行在 Uvicorn（ASGI 服务程序）中，协议层由 python-a2a 提供；同步协议处理通过线程桥接到服务的单一异步事件循环。成功响应含 success、agent、answer、trace（成功状态、智能体、答案、轨迹）；失败返回通用错误，不泄露内部异常正文。协调器不会把业务失败当作正常回答，也不自动重试 A2A。

委托密钥与员工 JWT 密钥独立；令牌携带 staff_id、patient_id、request_id、agent、tools、approved_actions（员工、患者、请求、专科、工具范围、确认动作）。当前共享服务密钥依赖服务主体可信，传输层仍需目标环境提供 TLS（传输层安全）或 mTLS（双向 TLS）。

### 数据与身份分别从哪里传

| 信息 | 来源和去向 | 为什么这样安排 |
|---|---|---|
| `task` | 协调器发给专科的当前子任务 | 专科要知道这次的交付物 |
| `patient_id` | 由服务端选定，与委托中的患者比对 | 模型或消息参数不能随意切换患者 |
| `history` | 最多最近 20 条中再按 4 KiB/条、16 KiB 总量裁剪 | 限制可选上下文的传输大小；可能丢失早期信息 |
| `profile` | A2A 服务从数据库重新读取，不由客户端传输 | 避免把调用方提供的病史和权限信息直接当权威数据 |
| 员工、请求和授权范围 | HTTP Bearer 委托令牌 | 传递“是谁委托、允许哪位患者和哪些动作” |

业务 JSON 有患者 ID，不等于调用者有患者权限。签名验证通过也不够，服务还要查员工是否停用、患者授权是否撤销。A2A 验证目标是对应专科，MCP 验证目标是工具服务；给 A2A 的令牌不能只因为签名正确就被 MCP 接受。

`MedicalA2AServer.handle_message` 是同步协议入口，实际工作交给服务已经启动的异步事件循环，再同步等待结果；协调器把 A2A 客户端请求放进工作线程。这解决同步 SDK 与异步服务的桥接问题，不等于专科任务已经并行执行。

## 八、MCP 工具、写操作和幂等

每次工具执行前，MCP 中间件核验令牌、工具范围、实时员工状态、患者授权；禁忌症工具使用数据库中的实际病史，不相信模型传入的患者状况。

三个写工具默认不进入可调用集合；只有本次任务勾选确认后才开放。医生和药师可保存病史及辅助材料，创建转诊仅允许医生。这里是**动作级确认**，尚不是对模型最终生成参数逐项预览签名的审批流；正式医嘱、自动处方和无需医生审核的转诊执行不在范围内。

`tool_executions`（工具操作表）先保存执行占位，再调用工具。员工 + 请求标识 + 工具名构成操作键，参数摘要及患者必须一致：完成状态重放保存结果，执行中或结果未知拒绝重复执行，参数冲突拒绝。每个请求同一写工具最多对应一组参数；换新请求标识不受旧键约束，因此不能声称下游 HIS 已实现“恰好一次”。

`GET /api/operations/{request_id}` 仅允许本人查看且再次核验患者权限。`pending`（执行中/待核对）或 `unknown`（结果未知）需要结合 HIS 实际记录和审计人工核对，不能直接删除占位重试。

### 读操作与写操作为什么分开保护

药品查询属于读取，即使读取成功后 API 保存了一条咨询记录，也不代表模型获得了“任意写病历”的权限。`save_patient_history`、`save_medical_record` 和 `generate_referral` 是需要明确确认的工具动作，分别受工具集合、员工角色和本次请求确认约束。

可以按转诊的一次执行理解操作表，但以下是故障机制示例，不是线上事故：

1. 工具执行前先校验参数；校验通过才登记 `pending` 占位，并提交数据库；先占位是为了让第二次相同请求发现已有执行者。
2. 调用配置的 HIS 转诊接口，不自动重试。
3. 得到正常结果后记录 `completed` 和可重放的结果；工具返回错误或抛异常时保留占位并标记 `unknown`。
4. 若同键再次到达：已完成且患者、参数摘要一致则重放结果；参数冲突拒绝；执行中或未知则阻断，不再调用医院。

| 再次请求看到的状态 | 应如何理解 | 当前处理 |
|---|---|---|
| 无已有操作 | 尚未为这个员工、请求、工具登记 | 尝试插入占位；数据库唯一约束处理竞争 |
| `pending` | 可能仍在执行，也可能进程中断后未更新 | 阻止重放，核对原请求 |
| `completed` | 本地已保存正常返回 | 校验参数和患者后复用结果 |
| `unknown` | 无法据本地结果确定医院侧最终状态 | 阻止重放，查医院记录和审计 |
| 同键但参数不同 | 同一个操作标识被用于另一组参数 | 拒绝，避免复用错误结果 |

最容易误讲的是“客户端超时等于医院没写入”。HTTP 回应丢失时，医院可能已经创建转诊单，本地却只知道结果未知。删除占位或换新请求 ID 后直接重试都可能重复创建。当前操作表保护相同请求范围，不是医院侧全局去重；医院契约没有提供幂等键与核对机制时，不能承诺全局恰好一次。

## 九、安全与 ToB 授权

员工登录使用 PBKDF2-SHA256（密码派生算法）60 万次迭代；计算在线程中执行。默认每工号在一个固定 300 秒窗口内跨来源合计最多 10 次登录尝试；窗口切换前后可能出现突发，不是任意滚动 300 秒都只有 10 次；每个来源跨工号总量上限为其 10 倍；配置 Redis 后跨 API 实例共享。限流组件不可用时登录返回 503，不绕过限制。

每次 API 请求从数据库读取员工启用状态和当前角色，停用账号、撤销患者授权或降权后无需等待旧 JWT 过期。医生/药师按 patient_access（员工—患者授权表）访问；医务管理员有医院级读取范围；系统管理员没有默认病历权限。旧用户表患者绑定不作为备用授权通道。

当前问题、历史和嵌套工具结果在模型出站前处理已知姓名、标识、电话、证件等信息。规则脱敏不是完整匿名化，医疗文本上云需要医院批准、数据分级、出站审查和留存规则。生产模式要求显式配置 `CLOUD_LLM_ALLOWED=true`，此开关不替代审批。

急症规则提示医务人员通知责任医生、启动院内急救流程。当前词表是保守关键词拦截，否定句、既往症状和特殊人群仍需临床团队校准；不得宣传为诊断模型。

## 十、记忆、并发和数据库

API 将员工和会话组成内部标识，再与患者以 JSON 编码构成缓存键，避免字符串拼接碰撞及不同员工串用会话。整轮持有会话锁；Redis 锁按所有者释放，租期为请求超时加 60 秒。开发环境可使用本地 TTLCache（过期缓存）；生产要求共享 Redis。

先提交辅助记录和审计，再成对追加用户/助手消息、保存完成阶段，最后发送 done（完成事件）。MySQL 和 Redis 之间不是原子事务；数据库已提交而 Redis 故障时可能没有完成确认。不得直接重跑已确认的写工具，应先查询操作状态。

检查点是阶段记录，不是 LangGraph（状态图框架）的可恢复执行器；当前不支持从任意步骤续跑或精确 SSE 断点续传。上一轮为澄清时，下一轮会合并前次任务与本次补充再识别，不是完整的结构化槽位状态机。

生产必须先执行 `alembic upgrade head`，API 校验版本 `20260926_02`。开发环境可创建表；空数据库迁移、旧患者停用及员工授权迁移有隔离数据库测试。真实 MySQL 升级仍需备份与恢复演练。

### 为什么模型等待期间不长期占用数据库连接

一次问答可能等待意图模型、三个专科、多个工具和最终汇总。如果把数据库事务一直保持到回答结束，即使暂时没有 SQL，也会持续占用连接池。并发请求一多，普通登录、授权和结果保存都可能排队；长事务还会增加锁和回滚负担。

当前 API 先用短会话读取身份与档案，在模型和 A2A 等待期间不保留该读事务；准备最终持久化时再打开短写会话，重新核实员工和患者权限，然后提交咨询与审计。MCP 也在实际工具调用前重新检查权限。因此“开始时有权限”不能代替“写入时仍有权限”。

### 四种记录各自解决什么问题

| 记录 | 核心作用 | 不能替代的能力 |
|---|---|---|
| 会话历史 | 给下一轮提供近期问题和答复 | 不能证明医院写操作是否成功 |
| 阶段检查点 | 标记 started、agents_completed、completed 或 failed 等阶段 | 不支持从任意工具步骤自动续跑 |
| 工具操作表 | 持久化写操作占位、参数摘要和结果 | 不能让 MySQL 与医院接口成为原子事务 |
| 审计及诊断日志 | 解释谁在什么范围做了什么、在哪个位置失败 | 不是业务结果的权威恢复源 |

这些记录不在同一个跨系统事务中。假设咨询已经提交到 MySQL，但随后 Redis 会话保存失败，页面会看到失败而不是 `done`；这不意味着前面所有写入都被回滚。应先查操作状态和持久化记录，再决定是否继续处理，不能把“再问一次”当成无副作用的恢复按钮。

## 十一、界面与 SSE

Streamlit（交互式网页框架）只调用 API，不直接绕过鉴权调用 Agent。界面切换患者或新建任务时清理聊天及写操作确认；提交后确认不沿用下一轮。

| 事件      | 内容                  |
| ------- | ------------------- |
| session | 会话标识、请求标识           |
| meta    | 意图、范围、专科与存储策略       |
| trace   | 工具步骤摘要              |
| card    | 结构化展示卡片，区别于 A2A 能力卡 |
| delta   | 汇总模型增量文本            |
| done    | 持久化及会话保存完成后的确认      |
| error   | 失败提示，不当作成功答案        |

当前 Streamlit 界面将急症 `card` 显示为警示框，并在本次会话重绘时保留；其他类型的 `card` 显示为普通提示。`meta` 是服务端路由元数据，当前界面不单独展示。

子 Agent 先完成工具调用，最终汇总才进行模型原生流式输出。界面遇到 error 或连接结束却没有 done 时显示失败；已批准写入的任务会查询操作状态。流式文本在完成前是暂存结果，生产界面还需医生复核交互和临床验收。

### 文本已经出现，为什么还要等 done

最终汇总开始后，`delta` 表示收到了部分文本；它不是最终业务完成确认。协调器产生自己的完成结果后，API 先拦住 `done`，把它暂存到内存，再完成数据库提交、用户与助手消息成对保存以及完成阶段记录，最后向页面发送 `done`。

可以把时间线读成：**工具完成 → 汇总文本增量 → 汇总结束 → 写咨询和审计 → 写会话及检查点 → 发送 done**。任一保存步骤失败都走 `error`，页面已经显示的文本仍不能视为成功存档的结果。连接直接结束而没有 `done` 时，客户端也显示失败。

当前 `trace` 主要在专科工作完成后整理并发送，因此不能把界面里的轨迹说成工具执行每一步都即时直播。首段文本前仍可能等待意图、规划和工具；`stream=True` 只改善汇总阶段的文本传递，不会消除前置等待。

## 十二、可以用代码解释的故障案例

- 内部服务直接调用绕过入口：增加独立委托验证、目标服务校验和实时患者授权，并用真实本地 HTTP 测试验证拒绝匿名调用。
- JWT 仍有效但员工已停用：不再只相信令牌旧角色，改为读取数据库当前状态。
- 转诊响应丢失：写调用不自动重试；保留操作占位和未知状态，人工核对后决定下一步。
- SSE 提前显示成功：将 done 延后到数据库、会话和阶段状态保存后，客户端检查完成事件。
- A2A 客户端阻塞异步循环：客户端初始化和同步请求均移入工作线程。
- 空库执行迁移未创建表：增加空库创建和重复迁移测试；已有不完整未知结构阻止静默标记成功。

这些是代码审查及故障测试案例；没有线上事故证据时，不把它们叙述成医院生产事故。

### 从症状定位到具体检查点

先确定失败发生在哪一层，再决定看日志、配置还是数据。下表是本地排障路线，不是已发生的生产事故清单：

| 观察到的现象 | 优先检查 | 为什么先查这里 |
|---|---|---|
| 登录失败或登录返回 503 | 员工启用状态、密码、限流 Redis 可用性 | 请求还没有进入意图模型 |
| 登录成功但选患者被拒绝 | 当前角色、`patient_access`、所选患者 | JWT 旧信息不替代数据库实时授权 |
| 请求一直追问 | `DomainGuard` 和 `ClarificationGuard` 的结果 | 范围不明与参数不足都能提前结束 |
| 某种表达总分到错专科 | `IntentClassifier` 的 `source`、`route` 和标签 | 找到实际接收层，再改对应规则或模型 |
| 本地模型启动失败 | 路径、文件权限、BERT 十类标签、权重及设备 | 目录存在不保证模型能加载；服务启动会预热模型 |
| A2A 失败 | 专科存活、令牌 audience、运行循环、业务错误码 | 网络成功但 success=false 仍是失败 |
| MCP 工具不可用 | 服务身份、工具白名单、员工权限、医院配置 | 缺配置时不会提供模拟医学结果 |
| 工具都结束但页面没有成功确认 | SSE `error`、MySQL 提交、Redis 会话及检查点 | 要区分执行成功和结果已保存 |
| 转诊失败后重试被拒绝 | `GET /api/operations/{request_id}` 与 HIS 记录 | 未知结果占位可能是正确的重复写入保护 |
| pytest 在收集或清理时拒绝访问 | 收集范围与临时目录权限分别检查 | `testpaths` 限定收集；独立 `--basetemp` 处理共享临时目录干扰 |

SSE 诊断日志记录阶段、请求标识、异常类型和栈位置；不要为了排障把患者原文、密钥或完整 SDK 异常直接输出到页面。保存一次最小复现及对应版本，比笼统记录“模型不稳定”更容易找到原因。

## 十三、失败处理矩阵

| 场景                            | 当前处理                         |
| ----------------------------- | ---------------------------- |
| 医院只读网络异常或 429/500/502/503/504 | 总计最多 3 次（首次 + 最多 2 次重试），指数退避 |
| 医院参数、权限或业务拒绝                  | 不自动重试，不计入医院瞬态故障熔断            |
| 转诊写入                          | 不自动重试；持久化占位，未知结果需核对          |
| A2A 传输或业务失败                   | 不自动重试，计入对应专科进程内熔断            |
| 模型超时或错误                       | SDK 自动重试关闭；范围判断可进入澄清，其余请求失败  |
| 工具证据不足或失败                     | 不接受专科正常结论，最终发送错误事件           |
| Redis/数据库异常                   | 不发送成功确认；写入后故障需先核对状态          |
| 同会话同时提交                       | 拒绝新并发轮次；不同员工的个人会话分别隔离        |

熔断状态只在当前进程内共享。半开探测有并发和取消保护；它不替代全局容量治理。

## 十四、常见架构题

**为什么三个 Agent？** 按症状、药品、指南检验划分工具职责，比把全部工具同时交给模型更易限制权限和分析失败。

**A2A、MCP、Function Calling 有何区别？** 分别负责智能体通信、工具连接和模型选择函数参数。协议不自动提供患者授权。

**Planning 和 ReAct 有何区别？** 前者生成跨专科短计划，后者在单专科工具集合内根据观察结果选择动作。

**为什么不用长任务框架？** 当前以最多三个专科的短链任务为主，`create_agent` 与确定性协调器已满足当前执行形态。

**结构合法为什么还需校验？** 合法 JSON（结构化数据格式）仍可能越权、参数错误或事实不足；权限和业务规则必须在执行层验证。

## 十五、评测与压测

意图回归、BERT 测试、向量阈值复核分别运行独立脚本，见 README。自动化测试包含真实本地 MCP/A2A HTTP 协议交互，但医院业务和模型执行使用测试替身；不能称作真实医院端到端验收。

历史 Locust（负载测试工具）报告：300 虚拟用户配置，CSV 实际记录 20 秒、8,107 请求、0 失败、约 401 RPS（每秒请求数）、P95 790ms。只测 `/api/health`，不代表完整 Agent、推理或医院接口容量；命令及时间窗口口径见 [压测说明](../loadtests/README.md)。代码变化后发布前需重测，不能把历史结果当成本次新压测。

### 分层验证为什么比只看一条总分有用

先用单层评测看分类模型和阈值，再用路由回归看最终标签是否退化，再用协议及故障测试检查执行边界。最后才是目标医院的真实接口、临床人员和部署环境验收。测试替身可以稳定制造权限撤销、超时或错误返回，但不能证明医院真实字段和网络行为已经匹配。

在项目根目录可运行：

```powershell
# 最终路由工程回归，输出逐条结果
python scripts/evaluate_intent.py --output artifacts/intent_eval_tob_v3.json

# 挑战集中的向量残余：用于校准复核，不作为独立临床测试
python scripts/calibrate_intent_vector.py --dataset evaluation/datasets/intent_challenge.jsonl --thresholds 0.78 --output evaluation/vector_challenge_summary.json

# 代码、索引、依赖和自动化测试的完整预检
python scripts/preflight_git.py
```

BERT 单层评测需要把实际模型目录传给 `scripts/evaluate_intent_bert.py` 的 `--model`，同时用 `--dataset` 明确选择普通测试还是挑战集；不要用另一组数据的分母解释输出。涉及医院资源的验证则需要正式配置和授权，此处命令没有替代这些条件。

报告必须同时记录数据版本、原型版本、模型与阈值及测试范围。已有回归摘要保存数据集和原型 SHA-256，可以核对文本输入是否变化；它并未为所有外部模型服务提供不可变版本证明。只看报告生成日期，还不足以排除模型或配置变化。

## 十八、连续追问示例

**医院一直超时为何不无限重试？** 只读最多三次，写入不重试，整轮还受超时约束；未知写结果走核对。

**工具失败为何不让模型凭常识补答？** 临床任务需要可追溯证据；代码会拒绝没有成功工具或出现工具失败的专科结论。

**三个专科用同一模型还是多 Agent 吗？** 是按职责、工具范围和运行上下文隔离的多个执行主体，不要求使用三个不同模型。

**规则全部覆盖了吗？** 已覆盖工程集合；否定、特殊人群、自然语言长尾需要临床审核及扩充测试，不能承诺穷尽。

### 一组连续追问怎样讲完整

**面试官：工具超时了，直接重新问一次不就行了吗？**

回答：先区分只读和写入。只读查询可按有限重试策略再试；转诊写入不自动重试，因为回应丢失时医院可能已经写成功。当前系统先保存占位，再执行写工具，并用操作表阻止同键重放。

**面试官：那你有幂等键，为什么还需要人工核对？**

回答：本地键是员工、请求标识、工具名的组合，保护的是本地同一操作。换了请求标识就可能成为新操作，医院系统也未必接收同一幂等键。跨系统恰好一次需要医院契约及状态核对，不能只靠本地数据库。

**面试官：怎么判断这次到底算成功？**

回答：工具返回只是一个阶段。API 还要保存咨询、审计、会话和完成检查点，最后才能发 `done`。如果数据库已提交而 Redis 保存失败，页面会收到错误；应查询本人操作状态及医院记录，不把错误提示当成“什么都没写入”。

**面试官：你拿什么证明这套处理有效？**

回答：用代码中的操作键、数据库唯一约束、状态分支和故障测试说明边界；本地真实 HTTP 测试验证协议交互，医院动作使用测试替身。若被问生产事故或临床效果，只引用真实记录，不把本地故障注入说成医院上线经历。

先在项目目录安装 `requirements.txt` 与 `constraints.txt` 中的版本，再配置 `.env`、模型、数据库和内部委托密钥。运行配置检查、数据库迁移和测试后，使用 `scripts/run_all.py` 启动本地服务。生产模式另运行严格配置检查，具体命令见 README。

### 本地启动时应该先后确认什么

1. **环境与配置**：在项目环境安装 README 指定依赖和约束，填写真实 `.env`，先运行 `python scripts/check_config.py`。普通检查核对核心项，缺医院接口时仍可能只给出集成提示；只有普通检查通过不代表所有业务工具可用。
2. **数据库与共享状态**：按使用环境启动 MySQL、Redis，并运行 `python -m alembic upgrade head`。正式数据库迁移先备份；不要为了让服务启动而随意删除生产表。
3. **模型与服务启动**：执行 `python scripts/run_all.py`。脚本使用同一解释器启动 MCP、三个 A2A、API 和 Streamlit，并监视子进程退出；它不是生产编排或自动恢复控制器。
4. **身份和患者授权**：本地联调使用明确输入的患者与员工数据。系统管理员能管理账号不等于能读取病历，不能为排障绕过授权。
5. **读操作闭环**：先选择已配置的只读工具，确认登录、患者选择、路由、工具返回、保存和 `done`。再在受控环境验证已批准的写动作及失败状态。

| 默认服务 | 地址或端口 | 所处位置 |
|---|---|---|
| FastMCP | `127.0.0.1:8002/mcp` | 工具与业务接口 |
| SymptomAgent / DrugAgent / GuideAgent | `8011 / 8012 / 8013` | 三个专科 A2A 服务 |
| FastAPI | `127.0.0.1:8000` | 工作台调用的业务入口 |
| Streamlit | `127.0.0.1:8501` | 院内员工界面 |

端口冲突时先确认占用者，再统一修改服务启动参数和对应配置。只改监听端口而保留调用方的旧 URL，会把“端口已占用”变成“下游不可达”。生产还需 `APP_ENV=production` 对应配置、正式接口与严格检查，不能将本地启动成功等同于上线验收。

# 二十三、Agent（智能体）工程范式与架构辨析

## 1. 你怎么定义 Agent（智能体）？

Agent（智能体）不是“调用一次大模型”，而是模型在目标、工具、状态和执行约束组成的 Harness（智能体执行框架）中，根据 Observation（观察结果）选择下一步 Action（动作），直到达到完成或停止条件。若下一步始终由固定代码决定，更接近 Workflow（工作流）；若模型能在受控范围内依据工具结果动态决定动作，才体现 Agent（智能体）特征。

落到本项目：Planning Agent（规划智能体）决定跨领域短计划，专科 Agent（智能体）通过 LangChain（大模型应用框架） `create_agent` 在白名单工具内执行 ReAct（推理与行动）；权限、患者范围和调用预算由服务端控制，不交给模型自由决定。

## 2. 这个项目到底是 Workflow 还是 Agent（智能体）？

它是“确定性主干 + 动态 Agent（智能体）子流程”的混合架构。登录鉴权、患者授权、急症规则、数据库写入和审计属于固定工作流；意图冲突下的规划以及专科 Agent（智能体）内部的工具选择属于受控 Agent（智能体）循环。

这种混合方式适合医疗场景：高风险边界由代码保证，信息检索和工具组合保留模型的灵活性。不是用了模型就全是 Agent（智能体），也不是存在固定步骤就不能叫 Agent（智能体）系统。

## 3. Prompt（提示词） Engineering、Context（上下文） Engineering 和 Harness Engineering 有什么区别？

- Prompt（提示词） Engineering（提示词工程）解决“任务、角色和输出要求怎么表达”。
- Context（上下文） Engineering（上下文工程）解决“这一轮应该让模型看到哪些指令、证据、工具结果和历史”。
- Harness Engineering（智能体执行框架工程）解决“模型在什么权限、工具、预算、状态、验收和恢复机制中工作”。

本项目的系统提示词属于 Prompt（提示词）；患者档案、近期会话和 MCP 工具结果的筛选属于 Context（上下文）；工具白名单、患者范围注入、最大调用次数、熔断、审计和 checkpoint（检查点）属于 Harness。三者是互补的工程层面，不是互相替代的技术代际。

## 4. Loop、Graph 和 Orchestration 分别是什么？

Loop（循环）描述“动作—观察—再决策”的反馈闭环；Graph（图结构）描述节点之间的控制流、数据依赖或状态迁移；Orchestration（编排）描述谁在什么条件下执行、如何交接和聚合。它们不是互斥选项。

本项目没有手写一串固定 LangGraph 节点冒充 ReAct（推理与行动）。专科内部的 Loop 由 `create_agent` 维护；跨 Agent（智能体）的 Orchestration 由意图、计划和 A2A 完成；业务侧只把高风险流程写成确定性约束。

## 5. Graph 一定比 Chain 更先进吗？

不是。Chain（链式流程）适合短而固定的顺序任务，代码简单、容易测试；Graph 适合条件分支、并行依赖、循环和恢复边界明显的任务，但会增加状态合并、版本和排障成本。选型要看控制流复杂度，而不是框架名。

如果一个任务只是“查药品信息—格式化结果”，用链或普通函数更合适；如果要根据症状评估决定是否追加用药审核和临床指南检索，才需要计划或图式依赖表达。

## 6. Supervisor 和 Plan-and-Execute（规划后执行）是一回事吗？

Supervisor（监督者）是一种多 Agent（智能体）控制拓扑，强调谁拥有调度权；Plan-and-Execute（先规划后执行）是一种执行策略，强调先形成步骤再执行。Supervisor 可以逐步路由而不生成完整计划，Plan-and-Execute（规划后执行）也可以由普通函数执行而没有多个 Agent（智能体）。

本项目的 Planning Agent（规划智能体）负责生成最多 3 个注册专科 Agent（智能体）的短计划，MedicalCoordinator 负责执行与汇总。它属于集中式调度，但不会允许计划产生未知 Agent（智能体）或任意工具。

## 7. 有循环为什么计划还可以是 DAG？

DAG（有向无环图）描述的是某一版计划内部的依赖；外层执行器仍可在失败或新证据出现时进行有限重规划，也可以让每个节点内部运行有界 ReAct（推理与行动）循环。因此“计划无环”和“执行存在循环”不冲突。

关键是给循环设置进展判据：新增有效证据、完成必要步骤或减少验收缺口才算进展；重复相同工具和参数不算进展，应终止或转入失败分支。

## 8. Agent（智能体）与 Dify、Coze 这类平台有什么区别？

Dify、Coze 是低代码应用与编排平台，适合快速验证、常见连接器和运营配置；自研 Agent（智能体）服务适合精细权限、复杂状态、内部协议、审计和性能治理。两者不是能力高低关系，而是控制力、交付速度和维护成本的取舍。

本项目选择 FastAPI（Python 接口服务框架）、A2A、MCP 和 `create_agent`，主要因为员工—患者隔离、医院接口 HMAC（消息认证码）、审计和部署拓扑需要代码级控制。如果只是验证一个知识问答原型，低代码平台会更快。

# 二十四、主 Agent（智能体）路由、槽位与任务契约

## 1. 面对很抽象的指令，Agent（智能体）怎么执行？

先把抽象目标转换成可验收任务：识别对象、动作、约束、时间范围和期望输出；再检查关键槽位是否齐全。缺少会改变医疗结论的核心信息时先澄清，不能让模型自行补全；信息足够时才生成受约束计划。

例如“帮我看看这个患者怎么办”至少需要授权患者、当前主诉和任务目标。系统可以读取已授权档案，但不能猜测未提供的症状、药物或检验值。

## 2. 什么是槽位，和意图有什么区别？

Intent（意图）回答“要做什么”，Slot（槽位）回答“对谁、基于什么、有哪些参数”。“审核阿司匹林是否适合该患者”的意图是用药审核，槽位可能包括药品名、患者 ID（患者标识）、过敏史、当前用药和疾病状态。

意图决定路由到哪个 Agent（智能体），槽位决定工具能否安全执行。意图识别正确但槽位缺失，仍不能调用高风险工具。

## 3. 槽位识别怎么做？

优先使用结构化来源：授权患者由服务端会话提供，既有病史由患者档案工具读取；药品名、症状、时间和检验指标可以用词典、规则、实体识别模型或大模型结构化抽取。所有模型结果都要经过类型、枚举、单位和范围校验。

权限槽位不能从自然语言里相信模型抽取。例如输入文本里写“patient_id=P999”，也不能覆盖 JWT（身份令牌）和授权表确定的患者范围。

## 4. 多轮对话中槽位怎么继承？

槽位要按命名空间和生命周期管理：患者身份与会话绑定，药品或症状只在当前任务有效，明确的新指令可以覆盖旧值。继承时保存来源、更新时间和确认状态，避免把模型推断当作医生确认事实。

用户切换患者、主题或目标时，应清理局部槽位并重新校验授权；不能把上一位患者的用药信息带入下一位患者上下文。

## 5. 用户问题短且模糊怎么办？

先判断能否从当前已授权上下文补齐；仍存在多个会显著改变结果的候选时，返回一个最小澄清问题，而不是列出十个问题。澄清应说明为什么需要该信息，并提供清晰选项。

例如“这个药能吃吗”若当前会话没有唯一药品对象，应先问药品名称；若药品明确但患者过敏史读取失败，应提示数据不可用并停止个体化判断。

## 6. 意图漂移怎么处理？

意图漂移是用户在多轮对话中从一个目标转向另一个目标。每轮都应重新识别当前请求，同时参考但不盲从历史意图；检测到新主题时创建新的局部任务状态，只保留仍有效的患者授权和必要背景。

系统可记录 `previous_intent（上一意图）、current_intent（当前意图）、topic_changed（主题已变化）`，但不能因为上一轮是药品信息查询，就强制把“这个检查指标代表什么”继续路由给 DrugAgent（药品智能体）。

## 7. 路由结果的 Schema（结构约束）应包含什么？

通用设计可包含：`intents、confidence、route、complex_task、required_slots、missing_slots、target_agents、reason`（意图、置信度、路由、复杂任务标记、必需槽位、缺失槽位、目标智能体、原因）。执行计划再补充 `step_id、agent、task、depends_on、timeout、failure_policy`（步骤标识、执行智能体、任务、依赖步骤、超时、失败策略）。

本项目当前使用注册意图、来源、置信度、经过层级和复杂任务标记，并把计划限制为三个注册 Agent（智能体）、最多 3 步。面试时可以解释扩展字段的设计，但不要说当前代码已经实现全部字段。

## 8. 交给子 Agent（智能体）的是一句话还是任务契约？

生产设计应优先传 Task Contract（任务契约），至少包含目标、授权资源范围、已知事实、未知项、允许工具、输出结构、截止时间和失败策略。一句话委派容易丢失边界，也难以判断子 Agent（智能体）是否真的完成。

本项目 A2A 业务载荷传递任务、患者 ID 和裁剪后的历史，不传递 profile 档案副本；专科服务核验委托身份和患者权限后，从数据库重新读取可信档案。进一步标准化时可加入 `task_id、trace_id、schema_version、deadline、retry_count`（任务标识、链路标识、结构版本、截止时间、重试次数）和结构化错误码；这些是扩展设计，不代表当前字段已全部实现。

# 二十五、串行、并行、异步与多 Agent（智能体）协同

## 1. 什么情况下串行执行？

后一步依赖前一步结果、存在先读后写约束或需要按风险顺序审查时使用串行。例如先分析症状和读取病史，再基于标准化结果检查用药禁忌。串行的缺点是延迟累加，因此只保留真实依赖。

## 2. 什么情况下并行执行？

多个只读任务相互独立、使用不同下游资源且聚合规则明确时可以并行，例如同时查询药品说明和指南条款。并行前要检查接口限流、连接池、总预算和取消传播，不能把三个慢调用简单并发后导致下游过载。

## 3. 并行结果怎么合并？

先按来源和任务 ID 校验结果，再区分事实、建议和错误；对相同字段定义合并策略，不能使用“最后写入覆盖”。出现冲突时优先权威、更新且患者范围一致的数据源，并在最终输出保留冲突说明和引用。

## 4. 什么情况下做异步后台任务？

预计超过交互等待时间、可中途保存、用户不需要立即拿到结果的任务适合后台执行，例如批量统计、长报告和大规模知识库重建。系统需要任务 ID、状态查询、取消、超时、结果保留期和通知机制。

本项目的实时临床辅助链路仍是请求内完成并使用 SSE（服务器发送事件），不应描述为已经实现完整任务队列。面试中可以回答后台化设计方案。

## 5. 同步任务阻塞事件循环怎么办？

先定位阻塞来源。HTTP（超文本传输协议）、数据库等 I/O（输入输出）操作使用异步客户端；CPU（中央处理器）密集的 BERT（双向编码器分类模型）/BGE 推理放入线程池、进程池或独立推理服务；不能在 FastAPI（Python 接口服务框架）事件循环里直接执行长时间同步计算。

GPU（图形处理器）推理还要限制并发和批处理，避免多个请求同时抢显存造成抖动。异步只能提高等待阶段的并发，不会让 CPU 计算自动并行。

## 6. Python GIL 会影响 Agent（智能体）系统吗？

GIL（全局解释器锁）主要限制同一进程内 Python 字节码的 CPU 多线程并行，对异步 I/O 影响较小。网络调用可使用 `asyncio`，重 CPU 任务用多进程或外部模型服务，NumPy/PyTorch（深度学习框架）的底层算子通常会释放 GIL，但仍要实际压测线程和显存竞争。

## 7. 多 Agent（智能体）会不会互相甩锅或死循环？

会，尤其当职责重叠、错误码模糊或双方都能重新委派时。解决办法是单一任务所有者、清晰输入输出契约、有限委派层级、全局调用预算和禁止 Agent（智能体）自由生成未知接收方。

本项目采用中心协调器，子 Agent（智能体）不直接无限互派；计划只允许三个注册 Agent（智能体），每个专科内部模型和工具调用都有上限。

## 8. 如何判断多 Agent（智能体）是否值得？

比较拆分前后的端到端任务完成率、高风险错误率、平均工具选择数、P95 延迟、Token 成本和维护复杂度。若只是把同一个 Prompt（提示词）拆成三个名字、工具和权限没有变化，多 Agent（智能体）只会增加延迟。

拆分的合理依据是业务领域、权限、知识、部署自治或团队归属不同。本项目按症状、药品、指南检验三个稳定能力域拆分，而不是按 10 个意图创建 10 个 Agent（智能体）。

# 二十六、上下文、状态和记忆深挖

## 1. State（状态）、Context（上下文）和 Memory（记忆）有什么区别？

State（状态）是系统保存的任务事实和进度；Context（上下文）是某一次模型调用实际看到的信息视图；Memory（记忆）是跨步骤或跨会话保存并按策略取回的信息。状态可以很大，但每轮上下文必须按权限、相关性和 Token 预算重新选择。

## 2. 什么是上下文污染？

无关、过期、低可信或属于其他任务/患者的信息进入当前模型上下文，影响判断，就是上下文污染。常见来源包括跨患者会话复用、旧摘要、错误工具结果、未经隔离的并行 Agent（智能体）状态和外部文档中的恶意指令。

处理方式是命名空间隔离、来源标记、任务范围过滤、版本与时间校验，以及把外部内容当数据而不是系统指令。

## 3. 多 Agent（智能体）共享 State（状态）会不会互相覆盖？

会。通用做法是全局只保存共享事实和任务索引，每个 Agent（智能体）使用自己的局部命名空间；并行写入通过 reducer（归并器）或版本检查合并，不直接覆盖同一个大字典。关键医疗事实只允许权威数据源或人工确认更新。

## 4. RAG（检索增强生成）结果和患者数据冲突怎么办？

患者数据说明“这个患者实际是什么情况”，指南知识说明“一般规则是什么”，二者角色不同。不能用通用文档覆盖患者事实，也不能用个案描述改写指南。最终输出应明确区分个体数据、通用证据和医生决策。

若两个权威来源之间冲突，应检查版本、生效日期、适用人群和来源等级；无法消解时保留冲突并转人工，不让大模型凭语言流畅度选一个。

## 5. 历史摘要会不会把模型带偏？

会。摘要是派生信息，可能遗漏否定词、时间变化和未确认状态。关键病史、过敏、药物和检验值应从结构化原始记录重新读取；摘要只用于压缩对话背景，并保留来源引用和更新时间。

摘要更新可以采用“旧摘要 + 新消息 → 新摘要”，但要对关键字段做程序化对照，不能让模型静默改写已确认事实。

## 6. 工具结果太长怎么办？

不要把原始 JSON（结构化数据格式）全量塞回模型。先用 Schema（结构定义）裁剪到当前任务字段，再对列表分页、去重、排序和限制 Top-K（前 K 条）；长文档保留标题、版本、相关段落和引用位置。被裁掉的原始结果仍可存入受控产物仓库供审计。

## 7. Context（上下文） Builder 怎么设计？

Context（上下文） Builder（上下文构建器）按固定优先级组装：系统安全规则 → 当前任务与患者授权范围 → 已确认结构化事实 → 当前步骤相关工具 → 有来源的检索证据 → 必要的近期历史。每类信息设置预算，低优先级内容超限就裁剪。

构建后还要验证患者对象是否一致、证据是否过期、是否混入指令型外部文本，并记录本轮选了哪些上下文，便于 Bad Case（失败案例）回放。

## 8. Checkpoint 和 Memory（记忆）、日志有什么区别？

Checkpoint 保存可恢复的执行状态；Memory（记忆）保存未来可能需要取回的信息；日志记录发生过什么用于观测与审计。日志不能直接拿来恢复，因为它可能不包含完整状态；记忆也不等于执行游标。

本项目保存 started、agents_completed、completed、failed 等阶段状态。若要实现精确断点续传，还需要事件序号、可重放消息和幂等副作用记录。

# 二十七、稳定性、恢复与故障隔离

## 1. 稳定性的目标是不是永不失败？

不是。生产系统要做到故障可识别、影响可隔离、状态可解释、必要时可恢复，而且不能因为依赖失败而编造成功。医疗场景宁可明确返回“数据源不可用”，也不能用模型记忆补一份看似完整的结论。

## 2. 超时应该怎么设置？

使用分层 Deadline（截止时间）：总任务有总预算，模型、A2A、MCP、医院 API（应用程序接口）和数据库分别有更短预算；下游调用不能超过剩余总时间。超时值来自延迟分位数和业务等待上限，而不是随手设置一个很大的数字。

## 3. 重试为什么可能让故障更严重？

下游已经过载时，所有实例同时重试会形成 Retry Storm（重试风暴）。因此只对明确可重试的瞬时错误采用指数退避和 Jitter（随机抖动），设置总预算，并让熔断器在持续失败后快速拒绝。

权限拒绝、参数错误和业务规则拒绝不应重试；写操作只有具备 Idempotency Key（幂等键）和服务端去重能力时才安全重试。

## 4. Checkpoint 能保证写操作不重复吗？

不能。Checkpoint 只能说明流程保存到了哪里，进程可能在医院系统已写成功、但本地状态落盘前崩溃。恢复时若直接重放就会重复写入。

需要业务幂等键、操作账本或下游状态查询：先确认副作用是否发生，再决定补写还是继续。流程恢复和业务幂等必须分别设计。

## 5. 如何防止过载和故障扩散？

按依赖配置并发上限、连接池、队列长度、速率限制和隔离舱；慢依赖不能占满所有工作线程。达到容量上限时应拒绝、排队或降级，而不是无限接收请求。

模型、医院接口和数据库要分别统计延迟、错误率和并发，避免只看 API（应用程序接口）总体指标而找不到真正瓶颈。

## 6. 模型服务突然不可用怎么办？

先区分急症硬规则、可缓存查询和必须模型推理的任务。急症规则仍可确定性返回安全提示；可缓存的公共知识在版本有效时可以降级读取；需要个体化推理但模型不可用时明确失败并保留任务状态。

备用模型需要提前做工具调用、结构化输出和安全评测，不能在故障时临时切换一个从未验证过的模型。

## 7. 输出波动大怎么排查？

固定输入、模型版本、Prompt（提示词）版本、工具结果和采样参数重放。若工具结果已经不同，先查数据与依赖；工具相同但路由不同，查意图与计划；轨迹相同但最终文本变化大，再查温度、上下文顺序和模型版本。

稳定性不能只靠把温度设为 0，因为供应商实现、并行计算和上下文差异仍可能产生变化。关键结论应由结构化事实和规则约束。

## 8. 故障演练怎么做？

在隔离环境注入超时、429、500、非法 JSON（结构化数据格式）、MCP 不可达、Redis 断开、数据库连接耗尽和模型返回空内容，检查错误分类、重试次数、熔断、审计和用户提示是否符合预期。写操作还要模拟“下游成功、本地超时”的不确定状态。

演练验收不仅看接口有没有返回，还要检查是否越权、是否重复写、是否错误标记成功、是否泄露敏感信息。

# 二十八、输出聚合、流式体验与效果评估

## 1. 多个 Agent（智能体）的结果怎么聚合？

先校验每个子结果的任务 ID、患者范围、来源、状态和 Schema（结构约束），再按计划依赖聚合。结构化事实优先保留原始来源，最终模型只负责组织表达，不允许把失败步骤改写成成功。

本项目由协调器收集实际执行的专科结果，再调用 `Planner.synthesize` 或 `Planner.synthesize_stream` 组织最终答复；汇总方法属于 `Planner` 类，协调器负责调度。只需要一个专科的任务就只执行该专科；单标签复杂任务仍可能经过规划，不必执行全部三个专科。

## 2. 子 Agent（智能体）结果冲突怎么办？

冲突先分类：数据版本冲突、适用条件不同、来源等级不同或模型解释冲突。程序能依据时间和权威等级解决的就确定性处理；涉及临床判断或来源都可信时保留双方依据并提示医生复核。

不要让同一个模型再投一次票就当作真相，因为多个 Agent（智能体）共用底座模型时错误可能高度相关。

## 3. 如何做输出审查？

至少检查：患者对象一致性、必需免责声明、急症红线、禁用诊断/处方表达、引用是否存在、关键单位和值域、工具失败是否被如实保留、敏感信息是否出站。格式审查可以程序化，医学正确性需要权威证据和人工抽检。

## 4. Structured Output 为什么仍可能错？

Structured Output（结构化输出）只提升格式符合率。合法 JSON（结构化数据格式）仍可能包含不存在的意图、越权 patient_id（患者标识）、错误药名和不合理单位。因此需要 Pydantic（Python 数据校验库）校验、枚举、服务端权限、业务规则和必要的来源核对。

## 5. 首 Token 慢怎么定位？

把 TTFT（首词元时间）拆成意图识别、规划、专科模型调用、工具耗时、最终模型首词元和网络发送。当前项目只有最终汇总阶段原生流式，前置 Agent（智能体）与工具完成前用户仍会等待，因此不能只优化模型生成速度。

可做的优化包括模型预热、减少无关工具 Schema（结构约束）、并行独立只读调用、缓存稳定结果和给前端发送阶段事件。

## 6. 流式生成中断怎么办？

用 task_id 和事件序号记录已确认输出，心跳检测断线，客户端按 Last-Event-ID（最后事件编号）恢复。若不能精确恢复，就返回任务最终状态和完整结果，而不是从头重复有副作用的 Agent（智能体）流程。

已发送给用户的错误文本不能静默撤回，只能停止后续输出并追加明确更正。高风险内容最好在段落级安全检查后再发送。

## 7. 如何自动评估执行轨迹？

把端到端任务拆成可检查项：意图是否正确、计划是否包含必要步骤、工具选择与参数是否正确、是否遵守权限、Observation（观察结果）是否被正确使用、是否在预算内停止。优先使用确定性规则和标注对比，模型裁判只评估难以规则化的表达质量。

模型裁判需要独立 Prompt（提示词）、盲评顺序、人工校准和一致性检查，不能让执行模型给自己打分后直接作为结论。

## 8. 缺少真实用户反馈时怎么评估？

建立版本化离线集，覆盖正常、口语、模糊、多意图、越权、急症、工具失败和对抗样本；由业务或临床人员抽样复核高风险结果。发布前做旧版/新版对照，发布后再用匿名真实 Bad Case 更新评测集。

本项目现有 33 条工程回归和合成数据用于工程防回退；正式效果判断仍应建立独立、人工标注、与训练数据隔离的真实测试集。

## 9. 如何控制多 Agent（智能体）成本？

让简单请求在规则、BERT（双向编码器分类模型）或向量层结束；单意图只调用一个 Agent（智能体）；按 Agent（智能体）只暴露相关工具；裁剪工具结果；缓存稳定知识；限制模型、工具和输出 Token；记录每个成功任务的调用次数和成本。

成本优化不能删除安全规则、患者授权或必要证据。应先消除重复上下文和无效循环，再考虑换更小模型。

# 二十九、工具、RAG（检索增强生成）与安全扩展题

## 1. 如果有几千个医院 API（应用程序接口），怎么组织？

不能一次把几千个工具 Schema（结构约束）都塞给模型。先按业务域和风险分层建立工具目录，主路由选择能力域，再在域内按意图、角色和患者范围动态加载少量候选工具。相似接口通过统一业务工具封装，不让模型理解每个厂商的底层字段。

还需要工具注册中心、版本、负责人、权限、超时、幂等、弃用状态和契约测试。MCP 可以统一发现和调用，但不能替代业务目录和授权系统。

## 2. Skill 和 Tool 有什么区别？

Tool（工具）通常是一次可调用的外部能力，具有名称、参数和返回值；Skill（技能）通常封装一套可复用的方法、说明、资源和多步骤工作方式。Skill 可以按任务渐进式披露，只在需要时加载详细内容，避免把所有知识长期塞进上下文。

本项目当前核心是 MCP 工具，不应声称实现了完整 Skill 系统；面试中可以解释若医院科室 SOP（标准作业程序）很多，可将其组织为按需加载的领域 Skill。

## 3. RAG（检索增强生成）召回为空怎么办？

先判断是查询问题、过滤过严、索引缺失还是知识库确实没有。可以做实体归一化、查询改写、放宽非关键过滤和关键词兜底，但不能在没有证据时让模型补答案。最终明确“未检索到权威依据”，并记录缺口供知识库补充。

## 4. RAG（检索增强生成）和数据库结果冲突怎么办？

数据库负责患者当前事实，RAG（检索增强生成）负责知识与指南，两者不能简单覆盖。检查数据时间、指南版本、适用人群和字段定义；若患者数据异常但来源可信，应提示医生核验，而不是为了符合指南范围修改患者结果。

## 5. Prompt（提示词） Injection 怎么分层防护？

第一层区分可信系统指令与不可信用户/文档内容；第二层只暴露最小工具集合；第三层执行前重新做身份、资源和参数授权；第四层对出站内容做敏感信息检测；第五层记录审计和异常行为。

“忽略以上指令”这类文本不能靠另一个 Prompt（提示词）清洗就解决。真正的安全边界在工具网关、数据库查询条件和高危操作确认。

## 6. 如何防止工具返回内容反向控制 Agent（智能体）？

把工具返回标记为 Data（数据）而不是 Instruction（指令），只提取允许字段；外部 HTML、邮件或知识文档中的“调用某工具、上传密钥”等文字不得提升为系统指令。高风险动作必须来自受信任务状态并重新授权。

## 7. 如何防止 Key 和敏感数据泄露？

密钥放 Secret 管理系统或环境变量，永不进入 Prompt（提示词）、日志和工具返回；模型调用前递归脱敏直接标识符；日志采用字段白名单而不是事后正则擦除；错误堆栈不返回给普通用户。

若密钥曾出现在截图或提交历史中，正确动作是立即吊销并轮换，然后清理历史和审计访问，而不是只删除文件。

## 8. 高危工具如何防社会工程式欺骗？

模型生成的收件人、患者、金额或操作对象都不可信。服务端需要把用户确认时看到的参数做摘要签名，签发一次性 Approval Token（批准令牌）；执行时重新验证操作者、对象、参数摘要、有效期和患者范围，任何变化都让确认失效。

本项目已实现每请求动作级确认、角色校验及持久化操作去重。上述绑定最终参数摘要的一次性审批令牌属于完整 HITL（人在回路）扩展方案，尚未落地。

# 三十、模型训练、推理与算法追问

## 1. 为什么意图识别不全部交给大模型？

高频确定性表达使用规则延迟最低且可解释；BERT（双向编码器分类模型）适合稳定分类边界；BGE 向量适合语义近义表达；大模型处理冲突、多意图和长尾。级联让准确性、成本、延迟和可观测性之间更平衡，也方便知道是哪一层出错。

## 2. BERT（双向编码器分类模型）分类分数能直接当真实置信度吗？

不能。Softmax 分数可能过度自信，需要在独立验证集上做可靠性分析、温度缩放或阈值校准，并分别统计覆盖率和接受样本准确率。阈值升高通常减少覆盖、提高接受精度，低分样本交给后续层。

## 3. 如何处理 OOD（分布外）？

OOD（分布外）请求不属于注册意图或训练分布。可以结合最大概率阈值、Top-1（首选类别）/Top-2（次选类别）间隔、向量距离、非医疗负样本和大模型枚举校验做拒识。拒识不是失败，错误自信路由才是风险。

## 4. 微调、RAG（检索增强生成）和 Prompt（提示词）怎么选？

行为格式、稳定分类边界和领域表达习惯可考虑 SFT（监督微调）；需要更新事实、来源和权限过滤时优先 RAG（检索增强生成）；任务说明和少量边界调整先用 Prompt（提示词）。微调不能可靠记住持续变化的医院数据，RAG（检索增强生成）也不能替代模型对复杂指令的遵循。

## 5. Prompt（提示词）调优到瓶颈后怎么办？

先判断瓶颈：缺事实改检索或工具；格式不稳加强 Schema（结构约束）和校验；特定表达识别不稳补训练数据；模型能力不足再评估换模型；只有稳定、重复、可标注的行为差距才值得 SFT。一次只改变一个关键变量并用固定回归集对照。

## 6. 如何降低推理成本？

使用级联路由、模型分级、Prompt（提示词）和工具 Schema（结构约束）精简、上下文裁剪、KV Cache（键值缓存）或前缀缓存、批处理、量化和结果缓存。对于本地 BERT（双向编码器分类模型）/BGE，还可根据延迟与显存要求选择 FP16（半精度）或 INT8（八位整数量化），但必须重新评测效果。

## 7. 为什么 PyTorch（深度学习框架）装好了还可能不能用 CUDA（英伟达并行计算平台）？

需要同时满足 NVIDIA 驱动可用、安装的是带 CUDA（英伟达并行计算平台）的 PyTorch（深度学习框架）构建、显卡架构受支持、依赖 DLL 正常以及进程能看到设备。检查 `torch.version.cuda、torch.cuda.is_available()` 和设备名称；Conda 环境与系统 Python 混用也会造成“装好了但当前解释器找不到”。

已有本地 BERT 评测报告记录 `device: cuda`；具体显卡型号是机器相关信息，不能从仓库的跨机器复现结果推断。部署到容器或 K8s 后仍需要 NVIDIA Container Toolkit（英伟达容器工具）和设备资源声明，并重新验证进程实际使用的设备。

## 8. 幻觉是怎么产生的，怎么降低？

模型生成目标是预测下一个 Token，不是查询真实数据库；上下文缺失、证据冲突、工具失败和强制回答都会增加幻觉。降低方法包括权威工具/RAG（检索增强生成）、来源引用、允许拒答、结构与业务校验、低温度、有界重试和人工复核。

医疗系统最重要的不是让模型“看起来什么都知道”，而是让没有证据的结论无法伪装成有证据的事实。

# 三十一、ToB（面向机构）项目交付与软技能追问

## 1. 如何把医院的模糊需求转成系统能力？

先拆成角色、场景、输入、动作、输出、风险和验收标准，再明确三条边界：系统能自动完成什么、什么必须医生确认、依赖缺失时如何降级。用一条真实业务链路做原型，比先讨论“要几个 Agent（智能体）”更有效。

## 2. 客户说“智能体不好用”，怎么定位？

不要直接调 Prompt（提示词）。按意图与槽位、计划、工具可用性、数据质量、响应速度、最终答案和界面体验分层定位；拿失败样本和链路 Trace（追踪记录）说明问题在哪一层，并给出验证方法和修复优先级。

## 3. 如何定义验收标准？

把主观“好用”转换为场景覆盖率、端到端任务完成率、高风险错误率、人工干预率、P95 延迟、工具成功率、越权拦截率和审计完整率。不同风险场景使用不同门槛，急症和权限不能被总体平均分掩盖。

## 4. 项目到期但甲方不满意怎么办？

先逐条确认不满意点和原验收口径，再展示已完成范围和证据；区分阻塞交付的核心问题与新增优化项，核心问题优先闭环，新增需求进入变更评估和后续迭代。不能临近交付才口头承诺全部完成。

## 5. 开发中新增需求怎么处理？

评估是否新增意图、槽位、工具、Agent（智能体）、状态字段和权限，分析对现有路由与回归集的影响；给出工作量、风险和排期，由业务方确认优先级。涉及范围、工期或安全边界的变化必须留书面记录。

## 6. 业务部门不配合、需求频繁变化怎么办？

用最小可行场景先证明价值，让业务人员参与样本标注和验收；锁定当前迭代范围，新需求进入 Backlog（需求池）评估，而不是随时插入。每轮交付可见结果和数据，减少双方只凭口头描述理解需求。

## 7. 怎么回答“项目最大的难点”？

选一个真实案例，用“现象—定位—方案—验证”回答。例如多意图被单标签模型覆盖：通过路由 Trace 发现 BERT（双向编码器分类模型）提前接受，增加多意图提示检测并让冲突进入大模型兜底，再用组合样本和回归测试验证。重点是定位方法，不要只说技术名词。

## 8. 怎么回答“如果重做一次会改什么”？

回答具体工程取舍，例如更早建立员工—患者授权模型、从第一版就记录每层路由来源、把工具错误统一成结构化协议、为写操作提前设计幂等键。说明这样能减少什么返工或风险，不必把回答包装成“原项目做得很差”。

## 9. 如何证明你不是只会调框架？

从一个失败案例讲到代码边界：为什么选择三 Agent（智能体）、如何约束计划、工具参数在哪里校验、患者范围在哪里注入、依赖失败如何分类、如何设计测试和评测。能解释取舍、失败和验证，比背 `create_agent` 的调用方式更能证明工程能力。

## 10. 面试官要求看内网系统怎么办？

说明医院内部系统受数据、账号、接口和网络隔离约束，不能提供运行环境、患者数据或内部地址；随后把讨论转向可公开的代码结构、接口契约、测试设计和技术决策。不要虚构医院名称、上线人数或借保密名义声称无法验证的成果。

# 三十二、开放式系统设计追问

## 1. 如果增加语音电话入口，怎么设计？

链路可拆为电话网关、VAD（语音活动检测）、ASR（自动语音识别）、对话 Agent（智能体）、TTS（语音合成）和人工转接。医疗场景要支持打断、确认关键实体、急症快速转人工、录音授权、敏感数据保护和整体延迟预算。

这是扩展设计题，不属于当前项目已实现功能。

## 2. 如果增加医学影像或报告图片，怎么设计？

先做文件安全检查、OCR（光学字符识别）和版面解析，保留页码与区域坐标；结构化提取检验项、单位和参考范围，再把原图区域和文本证据交给 GuideAgent。模型输出只能做辅助解释，不能替代影像科或病理诊断。

## 3. 如果让 Agent（智能体）生成月度医疗服务总结，怎么闭环？

先确定统计口径与权限，使用结构化查询生成指标，再让模型解释变化和异常；每条结论保留可下钻的数据来源，生成报告后执行数值一致性检查和人工审核。大批量任务使用后台队列、任务状态和可恢复产物，不放在一次 HTTP（超文本传输协议）请求里完成。

## 4. 从开发版走向生产版还要检查什么？

检查身份接入、最小权限、数据分级、医院接口契约、密钥管理、审计、幂等、超时熔断、容量、模型与知识版本、离线评测、灰度回滚、告警、备份恢复和安全测试。每一项都要有责任人、验收记录和回滚方式。

回答这类题时应说“生产化清单和实施方案”，除非确有目标环境记录，否则不要把配置文件等同于已经完成生产上线。

# 三十三、扩展储备题与标准答案

本章收录代码 Agent（智能体）、强化学习、多模态及平台化等扩展题，并提供标准答案或回答框架，方便根据目标岗位准备。答案描述通用原理与设计方案，不自动代表 MedAgent AI 已实现这些能力；个人经历题须结合真实经历回答。

## 一、代码 Agent（智能体）与 AI Coding（人工智能编程）

适合目标岗位明确包含 Coding Agent（编程智能体）、研发效能平台或代码大模型时扩展。

问题清单：

1. 代码 Agent（智能体）如何建立 Repository Map（代码仓库结构地图）？
2. 如何从报错、符号依赖和测试覆盖选择最小上下文？
3. 为什么代码修改应输出 Patch（补丁）而不是整文件覆盖？
4. 如何设计“定位—修改—测试—审查—修复”的有界循环？
5. 如何在 Sandbox（沙箱）中限制文件、命令和网络权限？
6. 如何防止 Agent（智能体）修改无关文件、删除用户代码或泄露仓库密钥？
7. 单元测试通过但业务仍错误时，如何增加集成测试和回归测试？
8. 多个 Coding Agent（智能体）并行修改时，如何处理分支、冲突和责任边界？

### 标准答案

1. **Repository Map 怎么建立？** 先解析目录、构建文件—模块—符号—调用—测试关系，再叠加入口、配置和所有者信息。它是按任务裁剪上下文的索引，不是把整个仓库塞进 Prompt（提示词）；动态语言和反射场景还要用运行日志、测试和搜索补足静态分析。
2. **怎么选择最小上下文？** 从报错栈、目标符号或失败测试出发，沿定义、引用、调用者、配置和相关测试逐层扩展；每加入一段上下文都要能说明它与验收条件的关系。找不到证据时继续检索，不凭文件名猜实现。
3. **为什么输出 Patch？** Patch 只表达必要差异，便于人审查、冲突检测、回滚和权限控制，也能减少整文件重写造成的无关格式变化。应用前仍要校验基线版本和上下文，防止补丁落到过期代码。
4. **如何设计代码循环？** 先得到可复现失败和验收标准，再执行最小修改、静态检查、相关测试和全量回归；把真实错误作为下一轮 Observation（观察结果）。达到验收、连续无进展、范围越界或预算耗尽时停止。
5. **Sandbox 怎么限制？** 使用临时工作区、非特权用户、只读基线、允许目录白名单、命令白名单、CPU/内存/时间配额和默认断网；依赖下载、凭据访问、宿主目录挂载和外部写操作单独审批。容器本身不是完整安全边界，高风险场景还要强化隔离。
6. **如何防止越界修改和泄密？** 在执行层限制可写路径和 Git diff 范围，密钥通过代理注入且不让模型读取，破坏性命令与发布动作要求人工确认；完成后扫描新增文件、绝对路径、密钥和大文件。Prompt（提示词）中的“不要修改”只能是辅助提醒。
7. **单测通过但业务仍错怎么办？** 补契约测试、集成测试和端到端测试，覆盖数据库、网络、权限和真实序列化边界；把原始 Bad Case 固化成回归用例。覆盖率只说明代码被执行过，不证明断言和业务语义正确。
8. **多个 Agent（智能体）并行修改怎么治理？** 按模块或任务分配独立分支/工作树和明确所有者，尽量避免交叉文件；合并前先同步基线、运行各自测试，再解决语义冲突并跑整体回归。最终合并权和发布权由统一协调者或人工持有。

与当前项目的连接点：工具白名单、调用预算、结构化 Observation（观察结果）、Git 上传前检查和自动化测试方法可以迁移；但当前 MedAgent AI 不是代码 Agent（智能体）项目。

## 二、强化学习与 Agent（智能体）训练

适合岗位描述明确包含 RL（Reinforcement Learning，强化学习）、RLHF（基于人类反馈的强化学习）、GRPO（组相对策略优化）或训练平台时扩展。

问题清单：

1. 如何防止 Reward Hacking（奖励投机）？
2. Verifier（验证器）需要评估正确性、格式、安全还是过程？
3. 如何检测和缓解 Entropy Collapse（熵坍缩）？
4. 什么是 Gradient Starvation（梯度饥饿），如何处理？
5. 长思维链训练如何减少 Train–Inference Mismatch（训练与推理不一致）？
6. 训练数据如何按难度、质量、长度和可验证性分层筛选？
7. KL Divergence（KL 散度）约束应该按 Token、序列还是阶段计算？
8. GRPO 的 Group Size（组大小）如何在方差、显存和吞吐间取舍？
9. 什么时候应该做 SFT（监督微调），什么时候继续优化工具和流程？
10. 如何判断某个 Bad Case 应归因于模型能力，而不是检索、工具或编排？

### 标准答案

1. **如何防 Reward Hacking？** 奖励必须与真实任务结果交叉验证，保留独立对抗集和人工抽检，监控 reward 上升但真实成功率、安全性或多样性下降的背离。KL 只能限制偏移，不能证明没有钻奖励漏洞。
2. **Verifier 评估什么？** 至少评估准确性、鲁棒性、目标一致性和校准度，并区分事实、逻辑、格式与安全错误。高风险结果优先用代码执行或数据库核对，低置信度交人工，不能把一个模型 Verifier 当唯一真值源。
3. **熵坍缩怎么处理？** 监控 token（词元）熵、KL、同一 Prompt（提示词）的有效多样性、奖励分布和保留集能力；通过学习率、更新幅度、KL/clip/熵正则、奖励缩放和数据多样性做消融。调高推理温度只能增加表面随机性，不能修复已经坍缩的策略。
4. **什么是 Gradient Starvation？** 它是强预测特征快速降低损失，使其他仍有预测力的特征几乎得不到梯度的特征竞争现象，不等同于长尾不均衡或多任务梯度冲突。应通过特征消融和 OOD（分布外）测试确认，再考虑 spectral decoupling（谱解耦）、反事实数据或表示约束。
5. **如何减少训推不一致？** 训练和推理保持相同 Prompt（提示词）模板、工具条件、长度预算、解码约束与输出格式，并在真实推理配置下评测。训练奖励不能鼓励冗长推理，而生产又强制极短输出。
6. **数据如何分层？** 先去重和清洗，再按质量、多样性、难度、领域和安全风险分层；优先保留当前策略尚未掌握但可以学习和验证的样本。训练、开发、对抗和最终保留集必须隔离。
7. **长序列 KL 怎么设计？** 明确 reference policy（参考策略）、KL 估计器、mask、按 token（词元）求和还是按有效长度平均，并监控长度偏置；固定或自适应系数都要用消融验证。不能把日志中的某个近似 KL 直接当成完整分布距离。
8. **GRPO Group Size 怎么选？** 没有通用最优值，应固定总 batch、训练 token（词元）和采样设置，对 4/8/16 等候选做消融，比较非零优势组比例、奖励方差、pass@k、训练稳定性和单位收益成本。组越大只代表采样更多，不保证有效多样性。
9. **什么时候做 SFT？** 错误需满足高频、稳定、可标注、可学习，并且 Prompt（提示词）、规则、工具、检索和流程修复无效。若事实来源错误或工具缺失，SFT 只会把错误固化进参数。
10. **Bad Case 如何归因？** 沿 Trace 找最早偏离契约的节点，固定其余变量做反事实重放：固定工具结果只换模型、固定模型输出只换检索或计划。只有上下文和工具事实正确、流程完整但模型仍稳定失败，才主要归因模型能力。

与当前项目的连接点：本项目做过 BERT（双向编码器分类模型）意图分类训练和工程评测，但没有开展大模型强化学习，不能把分类微调描述成 RL 实践。

## 三、大模型底层与研究型问题

适合偏模型算法、研究工程或训练推理一体岗位时扩展。

问题清单：

1. Self-Attention（自注意力）为什么拆成 Query、Key、Value（查询、键、值）？
2. Multi-Head Attention（多头注意力）解决什么问题？
3. KV Cache（键值缓存）如何影响显存、吞吐和并发？
4. 长上下文中的 Attention Sink（注意力汇聚）和 Context（上下文） Corruption（上下文腐化）是什么？
5. FlashAttention（高效精确注意力）为什么能减少显存访问？
6. 量化中的 Calibration（校准）、离群值和精度损失怎么处理？
7. Speculative Decoding（投机解码）适合什么场景？
8. MoE（Mixture of Experts，混合专家）如何在参数规模与计算量之间取舍？
9. World Model（世界模型）、GVF（General Value Function，广义价值函数）等研究概念如何与 Agent（智能体）联系？
10. 参考资料中的 OaK 等非主流架构应先核对论文、定义和适用范围，再决定是否纳入话术。

### 标准答案

1. **为什么有 Q/K/V？** Query 表示当前位置要找什么，Key 表示其他位置可匹配什么，Value 表示真正被聚合的内容；`softmax(QKᵀ/√d_k)V` 把匹配与内容分开学习。
2. **多头注意力解决什么？** 不同注意力头可以在不同投影子空间学习位置、语义或关系模式，再拼接融合。它提升表达能力，但头数增加会改变单头维度、显存和计算，并非越多越好。
3. **KV Cache 如何影响推理？** 自回归解码缓存历史 token（词元）的 Key/Value，避免每步重复计算历史；代价是显存随层数、序列长度、并发和 KV 头数增长，长上下文服务常由 KV Cache 而非模型权重限制并发。
4. **Attention Sink 和 Context（上下文） Corruption 是什么？** Attention Sink 指部分早期 token（词元）获得不成比例的注意力、并可能承担稳定计算的“汇聚点”；Context（上下文） Corruption 是长上下文中干扰增加导致关键信息利用能力下降的更宽泛现象。二者相关但不是同义词。
5. **FlashAttention 为什么更快？** 它通过分块和在线 softmax 减少注意力计算在 GPU 高带宽显存与片上 SRAM 之间的数据搬运，并避免物化完整注意力矩阵；核心是 IO-aware（输入输出感知）优化，不是改变注意力数学定义。
6. **量化如何校准？** 用代表性校准集估计激活/权重范围和缩放因子，关注离群通道、逐张量与逐通道粒度、权重与激活位宽；比较精度、延迟、显存和真实硬件算子支持。模型变小不等于在所有硬件上都更快。
7. **投机解码适合什么场景？** 小草稿模型一次提出多个 token（词元），大模型并行验证并按目标分布接受，因此在不改变目标模型分布的正确实现下可降低解码延迟。收益取决于接受率、草稿成本、批量和系统开销，低接受率时可能无收益。
8. **MoE 如何取舍？** 每个 token（词元）只路由到少量专家，使总参数量增长而单 token（词元）计算相对可控；代价是路由负载不均、通信、专家并行、容量溢出和训练稳定性问题。MoE 不等于每次调用多个独立 Agent（智能体）。
9. **World Model 与 GVF 怎么联系 Agent（智能体）？** World Model 预测环境或抽象状态在动作后的变化，支持规划；GVF 预测某策略下未来信号的折扣累积，可形成可查询的预测知识。GVF 可以是世界知识的一部分，但一组 GVF 不自动构成完整可规划世界模型。
10. **遇到 OaK 等非主流架构如何回答？** 先请对方明确论文、演讲和版本，再按原始来源解释定义；不把二手文章中的简称当作统一行业标准。当前项目未使用该架构，可将讨论落到自己实现过的工具约束、状态管理和规划验证。

与当前项目的连接点：可以结合 BERT（双向编码器分类模型）、BGE-M3、CUDA（英伟达并行计算平台）和量化经验回答基础推理问题，但不要扩展成未做过的大模型训练经历。

## 四、Deep Agents（深度智能体框架）与开放式长任务 Agent（智能体）

适合岗位明确使用 `deepagents`、Deep Research（深度研究）、文件系统 Agent（智能体）或长期任务 Agent（智能体）时扩展。

问题清单：

1. Deep Agents（深度智能体框架）与 LangChain（大模型应用框架） `create_agent` 的能力边界是什么？
2. Todo Planning（待办规划）、文件系统和子 Agent（智能体）委派分别解决什么问题？
3. 大量上下文为什么要外置到文件或产物仓库？
4. 子 Agent（智能体）如何隔离上下文又共享必要产物？
5. 长任务如何保存进度、恢复执行和传播取消信号？
6. 如何限制 Shell（命令行）、文件写入和网络访问？
7. 什么时候使用 Deep Agents（深度智能体框架）属于过度设计？

### 标准答案

1. **Deep Agents（深度智能体框架）与 `create_agent` 的边界？** `create_agent` 提供可配置的模型—工具循环和 Middleware（中间件）扩展点；Deep Agents（深度智能体框架）构建在该核心之上，预装规划、文件系统、上下文压缩、子 Agent（智能体）和长期记忆等 Harness 能力。短链工具任务适合自行配置 `create_agent`，开放式长任务才更需要 Deep Agents（深度智能体框架）。
2. **Todo、文件系统和子 Agent（智能体）分别解决什么？** Todo 让计划和进度显式化；文件系统把大结果外置，减少上下文占用；子 Agent（智能体）用独立上下文处理专业子任务。它们解决不同瓶颈，不能只因为任务“复杂”就全部打开。
3. **为什么把上下文外置？** 模型窗口有限且长上下文会产生干扰。将完整产物放在文件/对象存储中，只把索引、摘要和当前步骤所需片段放进 Prompt（提示词），可以保留可追溯原文并控制 Token；外置后仍要做权限和路径隔离。
4. **子 Agent（智能体）如何隔离又共享？** 每个子 Agent（智能体）拥有独立消息历史和工具集合，通过结构化任务契约接收目标，并把带来源的 Artifact（产物）返回共享仓库；主 Agent（智能体）只读取必要摘要或引用。不要共享一个可任意覆盖的全局消息列表。
5. **长任务如何恢复和取消？** 在可恢复边界保存计划版本、步骤状态、产物引用、预算和副作用账本；恢复前核对外部动作是否已发生。取消信号要向子任务和工具传播，停止新调度，并把已完成产物和未完成原因持久化。
6. **如何限制 Shell、文件和网络？** 使用沙箱、非特权身份、只读基线、允许路径/命令/域名白名单、资源配额和审批；短期凭证由执行边界按任务注入。模型能够调用 `execute`（执行命令）不等于拥有宿主机任意权限。
7. **什么时候是过度设计？** 任务步骤少、上下文小、无需文件产物/子 Agent（智能体）/长期恢复，且现有工作流能稳定完成时，Deep Agents（深度智能体框架）会增加权限、依赖和排障面。本项目医疗短链已有 A2A、Redis/MySQL 和 Planning（任务规划），因此选择 `create_agent` 更清晰。

与当前项目的连接点：本文已经解释为什么医疗短链选择 `create_agent`；除非项目真的引入文件系统、通用子 Agent（智能体）和长期任务，否则不要把 Deep Agents（深度智能体框架）写入技术栈。

## 五、多模态与语音 Agent（智能体）深挖

当前文档只保留了语音入口和报告图片的系统设计题，以下内容尚未展开。

问题清单：

1. Streaming ASR（流式语音识别）如何处理打断、端点检测和噪声？
2. Barge-in（用户插话）时如何停止 TTS（语音合成）并取消下游任务？
3. 关键药名、剂量和身份信息如何做二次确认？
4. 多人对话如何做 Speaker Diarization（说话人分离）？
5. 语音、文本和工具事件如何维护统一时间线？
6. OCR（光学字符识别）如何处理医学表格、单位和参考范围？
7. DICOM（医学数字成像和通信）数据如何脱敏、授权和审计？
8. 多模态模型输出如何回链到图片区域、页码和原始证据？
9. 音视频数据的存储期限、授权和删除策略如何设计？

### 标准答案

1. **流式 ASR 怎么处理打断和噪声？** VAD 负责检测人声起止，Endpointing（端点检测）判断话轮何时提交 final；流式 ASR 输出可修订 partial。用领域词表、噪声训练和两遍重打分提高准确性，业务写操作只允许稳定/final 文本触发。
2. **Barge-in 怎么处理？** 播放 TTS 时声学前端仍监听用户语音，确认真实人声后立即停止播放、取消尚未提交的生成和工具任务，并为新话轮创建版本号。旧版本晚到的结果必须被丢弃，避免打断后继续播报。
3. **药名、剂量和身份如何确认？** 对高风险实体使用专用词表/实体模型，回显规范化结果，并要求用户或医护人员逐项确认；确认记录绑定原音频片段、文本、患者和任务版本。低置信度不能自动进入写操作。
4. **多人说话怎么办？** Speaker Diarization（说话人分离）只给出说话人片段聚类，不自动证明真实身份；还需要会话座位、登录身份或人工绑定。身份不确定时只能记录“说话人 A/B”，不能把内容写入具体患者档案。
5. **如何维护统一时间线？** 给音频 chunk、ASR 假设、用户话轮、模型输出、工具调用和 TTS 片段统一事件 ID、时间戳、话轮版本与因果关系；partial 修订产生新版本，旧事件保留审计但不再驱动执行。
6. **医学表格 OCR 怎么做？** 先做版面检测、行列重建和单元格识别，再抽取项目名、结果、单位、参考范围和异常标记；用值域、单位和行列一致性规则校验，并保留页码、区域坐标和原图引用。不能只把 OCR 文本拼成一段交给模型。
7. **DICOM 如何治理？** DICOM 既包含像素也包含患者和设备元数据；接入时做合法授权、标签级去标识化、传输加密、访问审计和保留期管理。去掉姓名并不保证匿名，日期、机构、UID 和烧录在图像中的文字也可能识别患者。
8. **如何回链到视觉证据？** 每个结构化字段和结论保存 `document_id、page/frame、bounding_box、extractor_version`（文档标识、页码或帧号、边界框、抽取器版本），前端允许定位原始区域；模型生成不能创造不存在的坐标。视觉证据和文本转写冲突时应提示人工核验。
9. **音视频数据如何保存？** 遵循目的限制和最小保留：区分原始媒体、转写、派生特征和审计元数据，分别设置权限、期限与删除流程；训练复用需要独立授权。备份、缓存和向量索引也必须同步删除，不能只删主表。

与当前项目的连接点：GuideAgent（指南智能体）的检查报告辅助解读、证据引用和患者授权可以复用；当前代码没有语音、影像模型或 DICOM（医学数字成像和通信）接入。

## 六、Agent（智能体）协议与平台能力深挖

适合平台工程、Agent（智能体）基础设施或协议集成岗位时扩展。

问题清单：

1. MCP 的 Tools、Resources、Prompts（工具、资源、提示模板）分别适合什么场景？
2. MCP Sampling（模型采样请求）和 Elicitation（信息征询）如何做权限控制？
3. STDIO（标准输入输出）与 Streamable HTTP（可流式 HTTP（超文本传输协议））传输如何选型？
4. MCP Server（MCP 服务端）如何做多租户鉴权、限流和版本兼容？
5. A2A Agent Card（智能体能力卡）如何发现、缓存和更新？
6. A2A 任务状态、取消、回调和 Artifact（产物）如何设计？
7. 协议层成功但业务失败时，错误模型应该如何表达？
8. 如何在协议升级时兼容旧客户端和旧 Schema（结构定义）？

### 标准答案

1. **MCP 三种核心原语怎么选？** Tools（工具）由模型选择并执行动作；Resources（资源）由应用读取并作为上下文；Prompts（提示模板）通常由用户/客户端选择复用。查询并不必然是 Tool：稳定只读内容可建 Resource，需要参数化计算或外部动作才更适合 Tool。
2. **Sampling 和 Elicitation 如何授权？** Sampling（采样）是服务端请求客户端代为调用模型，客户端必须控制可用模型、预算和返回内容；Elicitation（信息征询）让服务端请求用户补信息或完成安全流程，客户端要展示真实来源、限制字段，并禁止服务端借此静默索取密钥。具体交互以双方协商的协议版本和能力声明为准。
3. **STDIO 与 Streamable HTTP（超文本传输协议）怎么选？** STDIO 适合客户端本机拉起、单用户、进程级隔离的服务器；Streamable HTTP（超文本传输协议）适合远程、多客户端、认证和水平扩展。远程传输要考虑 HTTPS、OAuth、会话/无状态、断线恢复和代理超时，不能把本地 STDIO 安全假设直接搬到公网。
4. **MCP Server 如何做多租户？** 在传输层认证，在工具执行层按租户和用户重新授权；工具目录、数据源、配额、审计和缓存键都带租户范围。Schema（结构约束）公开不等于调用有权，长期密钥也不能放入工具描述或模型上下文。
5. **Agent Card（智能体能力卡）怎么发现和缓存？** 可通过 well-known 地址、内部注册中心或直接配置发现；缓存时记录协议版本、能力、技能、端点、安全方案和有效期。敏感扩展卡需要认证，卡片不应携带静态密钥；更新后重新验证兼容性再替换缓存。
6. **A2A 任务与产物怎么设计？** 短请求可直接返回 Message；长任务使用 Task 状态、状态更新和 Artifact 更新，支持流式、查询、取消或订阅。客户端按 task ID 幂等处理重复通知，取消是请求而不是对外部副作用已回滚的保证。
7. **协议成功但业务失败怎么表达？** HTTP（超文本传输协议）/JSON（结构化数据格式）-RPC 成功只表示消息传输成功；业务响应必须另有 `success、error_code、retryable、task_state、partial_result`（成功标志、错误码、是否可重试、任务状态、部分结果），并把失败步骤和可重试性结构化返回。不能用含有 `answer`（回答内容）字段就判断成功。
8. **如何兼容协议升级？** 通过版本协商、能力声明、可选字段、默认值和宽容读取实现向后兼容；破坏性变更使用新版本端点或适配层。契约测试要覆盖旧客户端、新服务端和反向组合，未知字段应忽略还是拒绝需由协议明确规定。

与当前项目的连接点：已有 FastMCP（MCP 工具服务框架）工具服务、MCPAdapter、A2A 服务和 Agent Card（智能体能力卡），可作为基础；高级协议能力需要以实际版本和代码为准。

## 七、高级安全与 Computer Use（计算机操作）

适合安全 Agent（智能体）、浏览器 Agent（智能体）、桌面自动化或高风险执行岗位时扩展。

问题清单：

1. Browser/Computer Use Agent（浏览器/计算机操作智能体）如何隔离凭据和会话？
2. 如何防止页面内容中的 Prompt（提示词） Injection（提示词注入）诱导点击或上传文件？
3. 下载文件如何做类型校验、病毒扫描和隔离存储？
4. SSRF（服务端请求伪造）、路径穿越和任意命令执行如何防护？
5. 如何限制剪贴板、屏幕截图、外部域名和文件系统访问？
6. 审批界面怎样防止社会工程式参数替换？
7. 如何对高风险动作执行 Dry Run（试运行）和影响预览？
8. OpenClaw 等具体安全方案需要先确认其版本、威胁模型和官方资料，再做比较。

### 标准答案

1. **浏览器/桌面 Agent（智能体）如何隔离会话？** 每个用户和任务使用独立浏览器配置、Cookie 存储和沙箱，短期凭证由平台代理注入，模型不能读取明文；跨域、下载、上传和剪贴板默认拒绝。任务结束后销毁临时会话，并审计访问过的域名和动作。
2. **页面注入怎么防？** 网页文字、ARIA 标签、邮件和附件全部视为不可信数据，不能改变系统目标或工具权限；动作前由模型外策略校验域名、对象、参数和用户授权。检测器与分隔符只能降低风险，最小权限才限制被劫持后的影响面。
3. **下载文件怎么治理？** 先限制来源域名和大小，保存到隔离区，校验真实 MIME、扩展名和文件魔数，做恶意代码扫描及压缩炸弹检查；解析器使用沙箱。未经确认的文件不能执行、上传或进入共享目录。
4. **SSRF、路径穿越和命令执行怎么防？** URL 使用协议/域名/IP 白名单并阻止内网与元数据地址；文件路径规范化后确认仍在允许根目录；命令调用使用固定可执行文件和参数数组，不拼接 shell 字符串。执行进程使用最小系统权限和网络出站策略。
5. **剪贴板、截图和文件访问怎么限制？** 采用按能力授权：默认关闭，需要时只开放指定窗口、区域、格式或目录，并在敏感字段进入模型前脱敏。截图和剪贴板内容也可能包含注入文本，不能因为来自本机就视为可信。
6. **审批如何防参数替换？** 在可信界面显示规范化后的动作对象、参数、数据范围和副作用，对其摘要签名并绑定操作者、任务版本和有效期；执行层重新计算摘要。任何参数变化、超时或身份变化都要求重新审批。
7. **Dry Run 怎么设计？** 使用与真实执行相同的校验和计算路径，但在最终提交前停止，返回预计修改、受影响对象、权限检查和不可逆风险。Dry Run 不能调用真实副作用接口，且预览到执行之间若数据版本变化应使确认失效。
8. **OpenClaw 怎么回答？** 先说明其具体版本和威胁模型；参考官方安全边界，它偏向可信操作者的 local-first（本地优先）Agent（智能体）基础设施，不能默认当作互不信任多租户的隔离边界。比较时看网关暴露、会话隔离、沙箱、Skill 供应链、凭证和审批，而不是只讨论“指令清洗”。

与当前项目的连接点：员工—患者授权、工具白名单、HMAC（消息认证码）、脱敏和审计原则可以迁移；当前系统不是通用 Computer Use Agent（智能体）。

## 八、超大规模生产平台

适合平台架构、资深后端或大规模 Agent（智能体）基础设施岗位时扩展。

问题清单：

1. 多租户数据、模型配额和工具权限如何隔离？
2. 如何设计 Model Gateway（模型网关）和多供应商路由？
3. 如何进行跨区域容灾、数据复制和恢复点目标设计？
4. Service Mesh（服务网格）是否适合 A2A 服务治理？
5. 如何做全链路成本归因和租户级预算？
6. 如何设计队列优先级、背压和 Admission Control（准入控制）？
7. 如何定义 SLI/SLO（服务指标/服务目标）和 Error Budget（错误预算）？
8. 如何进行模型、Prompt（提示词）、工具和知识库的联合灰度？
9. 如何验证容量扩展没有放大数据库、Redis 和医院接口压力？

### 标准答案

1. **多租户如何隔离？** 身份令牌携带租户，数据库行/Schema（结构约束）、对象存储前缀、缓存键、向量集合、工具凭证和配额都显式带租户范围；服务端每次访问重新授权。不能只依赖前端隐藏或 Prompt（提示词）中的租户 ID。
2. **Model Gateway 怎么设计？** 统一模型认证、路由、超时、重试、限流、脱敏、成本和观测；根据任务能力、数据出境、延迟和预算选择供应商。Fallback（后备模型）必须提前做工具调用与安全回归，不能故障时临时换模型。
3. **跨区域容灾怎么做？** 先定义 RPO（恢复点目标）和 RTO（恢复时间目标），再选择备份、异步/同步复制和冷/温/热备；医疗数据还要满足驻留、加密和审计要求。切换演练必须验证数据一致性、密钥、DNS、队列和外部接口，而不只是应用能启动。
4. **Service Mesh 是否适合 A2A？** 服务网格可提供 mTLS（双向传输层安全）、服务发现、流量治理和遥测，适合大量内部服务；但会增加延迟、证书和排障复杂度。服务数量少时，应用网关加标准 HTTP（超文本传输协议）客户端可能更简单，业务授权仍必须由应用完成。
5. **成本如何归因？** 为每个请求记录租户、用户、任务、模型、输入/输出 Token、缓存命中、工具次数、GPU 时间和存储/网络用量，再汇总到成功任务和业务场景。共享批次需按可解释规则分摊，避免只看供应商总账单。
6. **如何做背压和准入？** 在入口按优先级和租户限流，队列设置最大长度与过期时间；根据模型并发、数据库池和下游容量决定是否接收。系统过载时应快速拒绝、排队或降级，不能让超时请求继续占用资源。
7. **SLI/SLO/Error Budget 怎么定义？** SLI 是实际测量指标，如可用率、P95 延迟、任务完成率和高风险错误率；SLO 是目标；Error Budget 是允许的不达标空间。医疗系统要把越权、急症漏拦截等安全指标单独设门槛，不能被总体可用率抵消。
8. **如何联合灰度？** 把模型、Prompt（提示词）、工具 Schema（结构约束）和知识库版本写入 Trace；每次尽量只改变一个主要变量，使用固定离线集、影子流量和小比例 Canary（灰度）比较。出现高风险回归立即回滚完整版本组合，而不是只回滚模型名。
9. **如何验证扩容不会压垮下游？** 分层压测并监控数据库连接、慢查询、Redis 命中/内存、医院 API（应用程序接口） QPS 和错误率；API（应用程序接口） Pod 扩容时给下游配置全局限流和连接预算。HPA（水平自动扩缩容）只能增加上游实例，若下游固定容量，盲目扩容会放大故障。

与当前项目的连接点：已有 K8s 灰度清单、Prometheus（监控指标系统）、Redis、熔断和压测基础；目标集群验证、多区域容灾和平台级多租户尚未作为项目事实。

## 九、个人与通用软技能

这些问题很可能出现在完整面试中，但不属于 MedAgent AI 项目技术话术，可后续单独整理成个人面试文档。

问题清单：

1. 为什么离开上一家公司？
2. 期望薪资如何结合城市、岗位和总包回答？
3. 未来两到三年的技术或管理规划是什么？
4. 自己最擅长的 Agent（智能体）能力是什么，能否承受连续深挖？
5. 遇到无法解决的问题，如何最小复现并逐级求助？
6. 如何处理跨部门目标冲突和资源不足？
7. 如何向非技术人员解释模型边界和风险？
8. 如何复盘一次失败，而不是把责任归给模型或客户？

### 标准答案框架

1. **为什么离职？** 标准回答：我这次考虑新的机会，主要是希望在下一阶段获得更系统的技术成长。过去的工作让我积累了 NLP（自然语言处理）、RAG（检索增强生成）和 Agent（智能体）应用开发经验，现在我希望进一步参与更完整的 Agent（智能体）工程化项目，深入工具治理、状态管理、效果评测和生产稳定性，同时承担更完整的模块设计与交付责任。我看这个岗位的技术方向和工作内容与我的下一阶段规划比较匹配，所以想主动寻求新的发展机会。这不是因为对原公司或团队不满，核心还是个人成长和岗位匹配。

   如果追问“是不是因为薪资”：薪资是选择机会时会综合考虑的一部分，但不是我这次变动的唯一原因。我更关注工作内容、技术成长空间、团队方向以及自己能够承担的责任，薪资会结合岗位要求和市场水平正常沟通。

   如果追问“新公司以后遇到瓶颈还会不会走”：我不会因为短期困难就频繁变动。我更看重岗位是否有清晰的业务目标、持续学习空间以及双方预期是否一致；入职前把这些问题沟通清楚，入职后通过项目结果证明价值，是我更希望采用的方式。

2. **期望薪资怎么答？** 区分月薪、奖金、补贴和总包，参考目标城市、岗位级别和自身可验证能力给出可谈区间；下限应是真实可接受值。不要虚报历史收入或编造其他 Offer（录用意向）。

3. **职业规划怎么答？** 明确未来两三年的主线，例如先深耕 Agent（智能体）工程化、评测和稳定性，再逐步承担架构或带项目职责；说明目标岗位提供的工作内容如何连接该路径，不要只说“技术和管理都可以”。

4. **最擅长什么？** 选择一个能经受连续追问的方向，并准备定义、设计、代码边界、失败案例和指标。例如选择工具治理，就要能解释 Schema（结构约束）、权限、重试、幂等和审计，而不是只列 MCP 名词。

5. **遇到不会的问题怎么求助？** 先构造最小复现，整理输入、环境、期望、实际结果、日志和已排除项；再按内部文档、同事、官方文档/Issue、供应商支持和风险升级的顺序求助。影响业务时及时报告，不隐瞒也不把原问题整包甩给别人。

6. **跨部门冲突怎么处理？** 先把各方目标、约束和决策权写清，用业务价值、风险和验收指标对齐；提出可选方案及影响，让负责人做取舍。会议结论、范围和变更必须留痕。

7. **怎么向非技术人员解释边界？** 用业务场景说明“能自动做什么、什么时候会转人工、失败时会看到什么”，避免只讲模型参数；用可理解的风险示例和指标解释，而不是承诺“模型一定不会错”。

8. **如何复盘失败？** 按时间线描述目标、事实、最早偏离点、当时决策、根因、修复和防复发机制；区分系统原因和个人改进，不把“模型不稳定”或“客户需求变了”当终点。最后给出新增测试、监控或流程变化。

扩展时必须结合个人真实经历填写，不能从参考答案中复制公司、薪资、客户或生产数据。

# 三十四、补充高频场景：从代码细节到故障追问

本章补充已有原理题之外的具体场景：为什么路由会漏、请求取消后发生什么、状态如何避免串写，以及怎样证明评测可信。标为“当前实现”的内容对应代码；“设计方案”用于回答扩展追问，不应说成已完成的上线实践。

## 一、多意图识别与评测可信度

### 1. 四层意图识别是不是一定比单模型准确，能不能保证全部识别？

**标准回答：** 不能保证。级联可以平衡成本、延迟与覆盖，但前层错误接受后，后层通常没有纠错机会。设计重点不是层数，而是各层的接受条件、拒识机制和最终任务覆盖率。当前正则命中可提前返回，因此需要专门测试“命中一个容易识别的意图，却遗漏另一个意图”的输入。验证时同时比较单模型基线与完整级联，统计错误提前退出、漏意图、费用和延迟，不能只展示每层成功案例。

### 2. 用户没说“同时、另外”，怎么发现多意图？

**标准回答：** 连接词只能作为线索，不能作为唯一判据。例如“辅助解读报告并给出院内接诊科室”仍然包含两个交付物。设计上先识别请求片段，再提取每个片段的动作、对象和交付物，结合上下文判断是否需要组合；还要区分“无需转诊，只查药品信息”中的否定。当前代码使用多意图提示词辅助判定，不能据此承诺完整覆盖；测试集应包括无连接词、否定、改口、跨轮补充和不同患者对象。

### 3. 十分类 BERT（双向编码器分类模型）能直接解决多标签意图吗？

**标准回答：** 当前 BERT（双向编码器分类模型）用 Softmax（归一化指数函数）并取最高分，属于单标签分类，不是原生多标签模型。如果改成多标签，需要多热标签、逐类 Sigmoid（逻辑函数）、二元交叉熵损失和逐类阈值；也可采用分句后分别分类再合并，但必须保留跨句依赖。不能只把最高分改成前两名，就宣称完成多标签训练。验证需要标签组合集和负例，检查额外误报与遗漏，而不只是单标签准确率。

### 4. 正则标记 0.99、BERT（双向编码器分类模型）阈值 0.95、向量阈值 0.78、大模型标记 0.70，能直接比较吗？

**标准回答：** 不能。正则分数是规则标记，BERT（双向编码器分类模型）分数是模型输出，余弦相似度是几何相似程度，当前大模型分数则是固定赋值，都不天然等于正确概率。应分别在独立数据上校准接受策略，统一报告“接受覆盖率、接受后准确率和拒识率”。不要根据这些原始分数直接跨层选最大值，也不要把固定的 0.70 解读为七成可靠。

### 5. 向量第一名超过阈值，但第二名很接近，怎么办？

**标准回答：** 同时检查绝对相似度和第一、第二候选的分差。高分但小分差可能是类别边界模糊，也可能是真实多意图，应交给后续判定或澄清，而不是一律选第一名或全部接受。当前代码的 Margin（分差阈值）主要用于有多意图线索时选取相近标签，不等同于已经实现单意图歧义拒识。阈值要在独立验证集调优，并在冻结测试集报告结果。

### 6. 为什么四层都正常工作，仍然会把不支持的问题分进医疗类别？

**标准回答：** 闭集分类被要求从固定类别中选答案，遇到域外问题也可能高分误分。因此当前链路已在十类意图之前增加 Domain Guard（医疗范围守卫），输出 medical（医疗）、non_medical（非医疗）、mixed（混合）或 uncertain（不确定）。非医疗固定回复且不调用专科工具；混合请求只传递服务端验证过的原文医疗片段；不确定请求先澄清。50 条 OOD（分布外）挑战样本用于评测 BERT 的拒识能力；另有范围模型异常时停止后续工具调用的测试。两种测试口径不能混为一谈，也不能据此保证未来所有非医疗表达都能被识别。

### 7. 输入很长，意图识别为什么突然变差？

**标准回答：** 先检查实际送入模型的词元数量和截断策略。当前 BERT（双向编码器分类模型）最长输入为 128 个词元，末尾请求可能被截掉。方案可以是先抽取请求区域、分段识别并汇总，或评估更长输入，但不能丢失否定、患者对象等关键限定。使用“相同请求放在开头、中间、结尾”的对照样本，区分长度问题与分类本身的问题。

### 8. 多意图都路由到同一个 Agent（智能体），还需要拆任务吗？

**标准回答：** 需要区分执行者去重和交付物去重。两个意图由同一个专科 Agent（智能体）负责，可以只调用一次，但输入契约必须保留两个子任务，输出也要逐项对应。设计任务—交付物清单，聚合时逐项检查完成、失败或需澄清，不能以“该 Agent（智能体）调用成功”替代全部子任务完成。测试应包含两个意图映射同一 Agent（智能体），以及其中一个工具失败的情况。

### 9. 为什么不能用同一批问题训练、调阈值和证明效果？

**标准回答：** 训练用于拟合参数，验证用于选模型与阈值，测试用于最终独立检验。合成数据还要按原始模板、同义改写族和来源分组划分，避免同一道题的近义版本分散到两侧造成泄漏。意图原型集也要独立管理；只做到文件不同，不足以证明语义没有泄漏。报告数据来源、去重方法、标签审核、版本和样本分布，合成集分数不能直接代表真实院内流量效果。

### 10. 多意图应该看准确率还是 F1？

**标准回答：** 两者都要，但定义清楚。Exact Match（集合严格匹配率）要求预测标签集合完全正确；Micro-F1（微平均 F1）汇总各标签计数，Macro-F1（宏平均 F1）等权平均各类结果，帮助发现少数类别问题。另外单列漏掉高风险意图的比例，以及单意图、多意图和域外子集。小样本满分只能说明这组样本全对，不能推出未来请求都能识别。

### 11. 如何发现级联中某一层实际上没有价值？

**标准回答：** 做 Ablation（消融实验），分别移除正则、BERT（双向编码器分类模型）或向量层，在同一测试集比较效果、延迟、成本与后续层负载。除了全量成绩，还要看真正到达该层的剩余难例；不能用简单样本上的准确率代表它在级联里的表现。某层若只节约很少成本却引入明显漏识别，就调整接受阈值或移除，不为了凑四层而保留。

## 二、并发、事务和失败恢复

### 12. 两个医生同时操作同一会话，会不会覆盖状态？

**标准回答：** 当前按员工、患者和会话隔离个人上下文，整轮会话锁拒绝同一会话的并发请求，消息成对写入；两个医生各用自己的会话。同一患者档案仍可能被不同授权人员编辑，复杂共享协作需要档案版本校验或乐观锁。当前 Redis 锁未实现栅栏令牌，超出租期的陈旧执行者风险需结合数据库版本控制处理，不能把锁等同于跨系统事务。

### 13. 调模型时为什么不一直持有数据库事务？

**标准回答：** 模型或医院接口可能耗时较长，一直持有事务会占用连接、扩大锁冲突，并让外部重试与数据库回滚纠缠。通常先用短事务读取必要快照，释放连接后调用模型，最终再用短事务校验版本并保存；关键状态变更仍由数据库约束保护。并发任务不要共享同一个可变 AsyncSession（异步数据库会话），应按任务管理会话生命周期。[SQLAlchemy 并发会话说明](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#using-asyncsession-with-concurrent-tasks)

### 14. 转诊接口超时，但医院其实已经创建记录，应该重试吗？

**标准回答：** 先把结果标成“未知”，不能认定失败后直接重复提交。设计上由业务幂等键绑定操作、患者、请求内容与结果，再通过下游查询或对账确认；相同键不同参数应拒绝。若下游既不支持幂等也不能查询，就转人工核查，不能承诺自动实现恰好一次。故障测试要覆盖“远端已提交、响应丢失”的时刻，而不只是请求发出前断网。

### 15. 数据库写成功了，但通知消息没发出去怎么办？

**标准回答：** 可采用 Transactional Outbox（事务发件箱）：业务记录和待发送事件在同一数据库事务提交，再由后台任务投递；消费者按事件 ID 去重，失败有重试与告警。它解决本地数据库与消息投递之间的可靠衔接，不等于跨医院接口的全局原子事务，也不保证只投递一次。验证进程在提交后、投递后但标记前退出的恢复行为。这是扩展设计，不是当前项目已实现事实。

### 16. Redis 分布式锁过期后，旧任务继续写入怎么办？

**标准回答：** 锁租期不代表旧执行者会自动停止。释放锁必须校验所有者令牌，不能删掉别人新获取的锁；重要写入还需版本检查或 Fencing Token（栅栏令牌），由被保护资源拒绝旧版本执行者。仅加续租仍不能完全排除暂停、断网后迟到写入。测试暂停旧任务直到锁过期，让新任务执行后再恢复旧任务。[Redis 分布式锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

### 17. 用户关闭页面，后台任务是不是自动停止？

**标准回答：** 不能假设。需要检测断连、传播取消信号、停止后续调度，并在清理逻辑中释放资源；取消正在等待的协程不代表已经运行的线程或远端写入也被撤销。Python 的 CancelledError（取消异常）应在清理后继续传播，避免被错误吞掉。业务层要区分取消、失败和结果未知，必要时查询远端操作状态。[Python 异步取消说明](https://docs.python.org/3/library/asyncio-task.html#task-cancellation)

### 18. 熔断器能否把所有错误都计为服务不可用？

**标准回答：** 不合适。无权限、参数错误和业务拒绝通常不代表依赖故障；应区分故障类型，按依赖或操作划分熔断统计，避免一个错误请求影响所有人。当前医院接口只把网络异常与指定瞬态 HTTP 状态计入熔断，参数、权限和业务拒绝不计入；A2A 仍按整个专科调用失败计数，二者统计口径不同。半开探测还需要处理探测任务取消、超时和资源清理。验证业务拒绝、并发半开探测及取消路径；多进程实例的本地熔断状态也不会天然共享。

## 三、权限、缓存和可观测性

### 19. 任务开始时有权限，执行中权限被撤销怎么办？

**标准回答：** 开始授权不应成为无限期通行证。敏感工具真正执行前重新校验员工、患者和操作权限，长任务可绑定授权版本并在关键步骤复核。缓存和检查点恢复也要遵循当前权限，而不是只相信旧令牌中的患者列表。测试在计划生成后撤销授权，确认工具不会继续读写。不能只靠模型提示词告知“你现在没有权限”。

### 20. 缓存为什么可能把其他患者的信息返回出来？

**标准回答：** 如果只按问题文本或向量相似度命中，两个患者的相同提问可能共享答案。个性化结果通常不适合跨患者语义缓存；确需缓存时，要把患者、授权范围、数据版本、模型与知识版本纳入隔离和失效策略，命中后仍重新鉴权。公共药品资料与患者解释应分开缓存。验证同问不同患者、授权撤销、源数据更新和不同版本切换。

### 21. 开了脱敏函数，是否意味着监控平台绝不会收到原文？

**标准回答：** 不能只检查最外层。模型回调、嵌套 Trace（调用链）、工具异常、HTTP（超文本传输协议）日志和附件都可能成为旁路。设计上优先采用字段白名单、在发送边界脱敏，限制采样、权限和保留期，并核对实际发出的数据。使用带可识别标记的测试文本检查所有出口，不使用真实患者数据做验证。患者 ID、请求 ID 等高基数字段也不应直接作为 Prometheus（监控指标系统）指标标签。

### 22. HMAC（消息认证码）签名正确，就能防止接口重放吗？

**标准回答：** 不能。HMAC（基于密钥的消息认证码）可以验证共享密钥条件下的消息完整性与来源，但同一合法请求仍可能被复制重发。防重放需把时间戳、随机数和请求规范化内容纳入签名，服务端检查时间窗口并原子记录已用随机数；业务写入还需要幂等控制。传输继续使用 HTTPS（安全超文本传输协议），密钥不能写入日志。具体协议应与医院接口约定一致。

## 四、部署和现场排障

### 23. PyTorch（深度学习框架）能识别 CUDA（英伟达并行计算平台），为什么加多个服务进程反而显存不足？

**标准回答：** 能使用 CUDA（并行计算平台）不代表显存足够。多个工作进程可能各自加载 BERT（双向编码器分类模型）、嵌入模型和推理缓冲区；再叠加输入长度、批大小与并发，显存会重复占用。先确认每进程实际设备、模型数量与峰值显存，再评估独立推理服务、有界队列或减少工作进程。不要用无限并发替代容量规划，也不能因为安装了 GPU 版本就声称所有推理都跑在 GPU。

### 24. 健康接口成功，为什么真实问答仍然失败？

**标准回答：** 进程存活、服务就绪和端到端可用是三件事。Liveness（存活探针）判断是否需要重启，Readiness（就绪探针）决定是否接收流量，Startup（启动探针）给慢启动留时间；再用独立业务探测检查关键链路。不要让外部模型短暂故障直接触发所有进程反复重启。当前健康入口压测结果不能代表真实模型、医院接口和长连接的容量。[Kubernetes（容器编排平台）探针说明](https://kubernetes.io/docs/concepts/workloads/pods/probes/)

### 25. 服务商说兼容模型接口，为什么换模型后工具调用坏了？

**标准回答：** 请求格式兼容不代表工具调用、结构化输出、流式增量、停止原因和上下文限制完全一致。建立能力契约测试，覆盖不调用工具、一次调用、多次调用、参数异常和流式工具参数分片；完整拼接并校验参数后才执行，不能拿半段 JSON（结构化数据格式）调用工具。模型版本变更应通过固定回归集再灰度，失败可切回已验证的版本组合。

### 26. 自动化测试通过，为什么不能证明所有集成都已验证？

**标准回答：** 单元测试通常用 Test Double（测试替身）隔离外部依赖，验证控制逻辑；契约测试检查接口结构；集成测试验证真实组件交互；端到端测试验证业务目标。它们互补，不能相互替代。报告时明确哪些调用是真实模型、真实 Redis、测试医院接口或替身，保留版本与环境信息，避免把“测试通过”扩大为“所有医院接口均已联调”。

### 27. 压测并发数、每秒请求数和延迟为什么对不上？

**标准回答：** 虚拟用户数不等于同时在途请求数，还受思考时间、等待方式和任务分布影响。在稳定系统且统计边界一致时，平均在途数约等于吞吐率乘以平均停留时间；不能把 P95 延迟直接代入平均值关系。应分别压健康入口、意图识别、完整 Agent（智能体）链路和流式长连接，记录失败率、排队、首字延迟、总延迟与资源瓶颈，避免把入口性能包装为完整推理容量。

### 28. 面试官要求讲一次线上故障，没有真实案例怎么回答？

**标准回答：** 可以明确说“我用故障注入验证过这一场景”，再按现象、假设、证据、定位、修复与回归测试说明。如果只做过设计，就说“我的处理方案是”，不要改成“当时医院线上发生过”。准备能对应代码和测试的例子，如超时、意图误判或状态恢复，比编造客户事件更能经受连续追问。离职原因等个人回答也只选符合自身经历的表述。

## 五、为什么增加这些题，哪些没有继续堆叠？

- 增加多意图、分数校准和数据划分题：它们直接决定四层识别结果是否可信，是面试官最容易沿实现追问的地方。
- 增加并发、取消、未知结果和权限撤销题：这些问题往往只在真实请求交错或下游异常时暴露，能体现工程判断。
- 增加部署、模型兼容和测试边界题：帮助解释“本地能跑”到“可靠交付”之间需要哪些验证，不虚报项目能力。
- 不再重复通用 ReAct（推理与行动）、RAG（检索增强生成）、重试定义：前文已有答案，本章只补具体失败场景。
- 编程 Agent（智能体）、强化学习等较远方向继续保留在第三十三章：方便目标岗位扩展，不混入当前项目核心实现。

## 2026-09-30 边界修复补充

- 当前自动化测试为 127 项通过；正文注明 2026-09-28 的 103 项属于历史测试记录。
- 范围守卫区分预约办理请求与临床背景：“已预约检查，请审核用药”“出院后复查随访计划”属于临床辅助；患者自助挂号、预约办理、缴费仍不支持。
- 三种写工具在登记 `pending` 之前校验参数。确定的参数错误不占位，修正后可使用同一请求标识重试；通过校验后发生调用、确认或结果保存失败，仍保守记录 `unknown` 并要求人工核对。
- 本地监控需使用 `python scripts/run_all.py --observability`，指标转发端口为 9100；Prometheus 分别抓取 API 与三个专科进程。业务接口保持回环监听，MCP 服务进程未单独暴露指标。

- 上传预检覆盖候选 Python 文件的静态导入和字面量模块启动命令；backend/scripts/tests/migrations 中的新 Python 文件和关键验证文件须先加入索引。此检查不保证识别动态拼接的所有依赖。
- HTTP 延迟指标统计响应创建时间，不含 SSE 正文传输或整轮耗时；响应创建阶段未处理的普通异常计入 500；响应头之前的取消不记为 500，响应头之后取消保留已记录状态。指标入口的网络访问范围由宿主机防火墙控制。

- Redis 锁已通过真实 Redis 7.4 容器验证：180 秒 TTL、同会话互斥、按所有者释放和取消释放。自动化测试另覆盖 use_redis=True 客户端调用分支；未验证故障转移或网络分区。
- 整轮 120 秒预算尚未作为统一截止时间传播到专科。子 MCP 令牌到期时间不超过父 A2A 令牌；但 API 超时和令牌过期均不能撤销已经发出的远端写入，不能把剩余执行窗口固定说成 30 秒。未收到 SSE done 应视为未确认完成，写结果需核对操作表及 HIS。
