## q-001

### 主问题｜Prompt Injection 如何分层防护？

原文位置：13-Agent安全防护.md 第 23 行（原件保存在同步前备份）。

**项目口述：** 权限在入口、A2A 专科和 MCP 工具执行点重复核验；数据库中的员工状态、角色和患者授权优先于旧令牌。专科只得到受限工具，患者 ID 服务端注入；原始任务摘要与签名委托绑定。外部文档和工具文字是数据，不允许改变授权、目标患者或写动作范围。

**针对本题的设计展开（原文原理，作为方案解释）：**

Prompt Injection 是攻击者把恶意指令混进模型能读到内容里（用户输入、检索文档、网页、工具返回），诱导模型执行非预期动作。防护要分层，因为注入来源不止一个：

本章给出完整安全分层；Context Builder（上下文构建器）如何把外部内容作为不可信数据组装，见 对应主题。

1. 来源与数据流层：标记用户输入、网页、邮件、RAG 和工具返回的 provenance，把外部自然语言视为不可信数据；分类器和字符串清洗只能降低噪声，不能成为安全边界。

2. 上下文层：分区呈现系统目标、用户授权和外部内容，限制不可信内容进入规划/记忆；但分隔符或“系统 > 用户”的提示优先级不构成确定性保证。

3. 能力层：按任务发放最小权限、短期凭证和工具白名单，限制文件、网络、数据域及可调用动作，使模型被诱导后也没有越权能力。

4. 策略与执行层：在模型外做身份、资源、参数、状态版本和业务规则校验；高风险动作使用绑定具体参数的审批或重新认证。

5. 输出与监控层：控制敏感数据流向外部 sink（数据接收端），记录可审计事件并持续做注入、越权和数据外泄红队测试。

核心原则：把模型视为可能被操纵的不可信规划器；真正的安全边界必须由模型外的权限、策略和执行系统提供。 Prompt Injection 仍是持续演化的问题，不能承诺靠某个检测器彻底消除。[NIST：Agent Hijacking 评估](https://www.nist.gov/news-events/news/2025/01/technical-blog-strengthening-ai-agent-hijacking-evaluations)

**在 MedAgent 中怎么补全：** Prompt 可以提示忽略注入，但真正防线是白名单、schema、可信身份、固定数据源、写入确认和审计。进一步对最终参数做审批绑定、限制外部域名和文件权限、加入注入回归；不将未测试的‘万能注入检测’写成已有能力。

## q-004

### 主问题｜如何防御社会工程式指令欺骗（如邮件收件人被篡改）？

原文位置：13-Agent安全防护.md 第 47 行（原件保存在同步前备份）。

**项目口述：** 病史更新、辅助材料保存和转诊草稿都需要院内角色、患者授权及本轮动作批准。工具层按员工＋请求标识＋工具建立唯一 operation_id，同时核对参数摘要；同键同参数完成结果可重放，冲突拒绝，pending/unknown 阻止重发。转诊只创建待医生确认的草稿，超时不自动重试。

**针对本题的设计展开（原文原理，作为方案解释）：**

防御的关键是高风险动作必须走确定性的授权链路，而不是让模型自己判断"这个请求合不合理"：

2. 升级鉴权：执行前按真实主体、资源和动作校验权限，高风险操作要求 step-up authentication，例如追加认证因子或重新验证身份。

4. 限制影响面：外发域名、金额、数量、频率和数据分类设硬上限，必要时使用双人审批或只生成草稿。

5. 审计与撤销：记录来源、授权、执行结果和可撤销句柄；日志本身不得保存明文密钥和敏感正文。

**在 MedAgent 中怎么补全：** 批准动作范围不等于对模型最终每个参数都完成确认；参数级审批仍需预览和有期限的规范参数摘要绑定。独立档案表单已实现 expected_revision 条件更新、409 冲突拒绝与修改字段名审计，不能套用 MCP 的操作状态表。外部 HIS 的一致性仍需对账、补偿契约和人工核对。

### 主问题｜工具调用安全怎么处理（Key 泄露、敏感信息暴露）？

原文位置：13-Agent安全防护.md 第 69 行（原件保存在同步前备份）。

**项目口述：** 权限在入口、A2A 专科和 MCP 工具执行点重复核验；数据库中的员工状态、角色和患者授权优先于旧令牌。专科只得到受限工具，患者 ID 服务端注入；原始任务摘要与签名委托绑定。外部文档和工具文字是数据，不允许改变授权、目标患者或写动作范围。

**针对本题的设计展开（原文原理，作为方案解释）：**

工具调用安全围绕"别泄露、别越权、别被注入"三点：

1. Key/凭证安全：密钥不进入 prompt、模型可读环境或日志；由凭证代理/密钥服务按任务签发短期、可撤销、最小 scope token（权限范围令牌）；

2. 敏感信息脱敏：模型上下文、日志、错误信息里对手机号、身份证、地址等做脱敏；

3. 权限最小化：每个工具只授予完成任务所需的最小权限（呼应模块 4 Q6）；

4. 参数校验：工具参数做 schema/类型/范围校验，防止注入或越权参数；

5. 出站与审计：限制工具可访问的域名、协议和数据分类；记录调用主体、授权依据、参数摘要、结果与状态版本，日志应防篡改且避免二次泄密。

**在 MedAgent 中怎么补全：** Prompt 可以提示忽略注入，但真正防线是白名单、schema、可信身份、固定数据源、写入确认和审计。进一步对最终参数做审批绑定、限制外部域名和文件权限、加入注入回归；不将未测试的‘万能注入检测’写成已有能力。

## q-010

### 主问题｜OpenClaw 从哪些层级做安全防护？指令清洗怎么落地？

原文位置：13-Agent安全防护.md 第 89 行（原件保存在同步前备份）。

**项目口述：** 当前项目没有接入 OpenClaw。我会按可迁移的安全边界回答：员工身份和患者授权、固定院内数据源、专科工具最小权限、输入与工具返回当作不可信数据、写动作审批和审计。指令清洗只能降低风险，不能授予权限；具体产品是否具备这些机制，需要核对其版本与实现。

**针对本题的设计展开（原文原理，作为方案解释）：**

先说明威胁模型：OpenClaw 官方把它定位为面向可信操作者的 local-first（本地优先）Agent 基础设施，并不把“互不信任用户共用同一 Gateway”当作默认安全边界。共享 Slack、公开消息入口或多租户部署不能直接沿用这个假设。[OpenClaw SECURITY.md](https://github.com/openclaw/openclaw/blob/main/SECURITY.md)

生产防护至少分七层：

1. 部署边界：Gateway 不直接暴露公网；使用 pairing/allowlist、强认证和独立租户/主机边界。

2. 会话边界：不同消息、用户和任务隔离 session、workspace 与 memory，避免跨会话污染；隔离上下文不等于隔离工具权限。

3. 外部内容处理：邮件、网页、文件、搜索结果统一标成 `EXTERNAL_UNTRUSTED_CONTENT`，携带来源元数据，并剥离常见 chat-template/role token。

4. 能力与审批：工具默认最小权限；命令审批绑定精确 command、cwd、env，以及可识别文件的内容快照，参数变化后重新审批。

5. 运行时隔离：按风险启用 sandbox、只读挂载、文件范围和网络 egress（出站流量）控制；不能假定默认配置已经提供完整沙箱。

6. Skill/插件供应链：固定版本和来源，安装前做人工/静态审查，限制安装权限并校验更新差异。

**在 MedAgent 中怎么补全：** Prompt 可以提示忽略注入，但真正防线是白名单、schema、可信身份、固定数据源、写入确认和审计。进一步对最终参数做审批绑定、限制外部域名和文件权限、加入注入回归；不将未测试的‘万能注入检测’写成已有能力。

### 追问｜如何验证防护真实有效？

原文位置：13-Agent安全防护.md 第 107 行（原件保存在同步前备份）。

**项目口述：** 权限在入口、A2A 专科和 MCP 工具执行点重复核验；数据库中的员工状态、角色和患者授权优先于旧令牌。专科只得到受限工具，患者 ID 服务端注入；原始任务摘要与签名委托绑定。外部文档和工具文字是数据，不允许改变授权、目标患者或写动作范围。

**针对本题的设计展开（原文原理，作为方案解释）：**

建立 direct/indirect injection、跨会话污染、恶意 Skill、参数篡改、凭证外泄和审批失效测试。验收不能只是“模型拒绝了攻击”，而要证明即使模型被诱导，未授权工具调用、敏感数据外发和高风险副作用仍被确定性边界拦截。

**在 MedAgent 中怎么补全：** Prompt 可以提示忽略注入，但真正防线是白名单、schema、可信身份、固定数据源、写入确认和审计。进一步对最终参数做审批绑定、限制外部域名和文件权限、加入注入回归；不将未测试的‘万能注入检测’写成已有能力。
