## q-001

### 主问题｜上下文怎么管理？

原文位置：06-上下文与状态管理.md 第 55 行（原件保存在同步前备份）。

**项目口述：** 可信患者档案来自数据库，近期对话与任务快照分开保存；工作台切换患者会清理上下文与未提交编辑。新任务隔离旧历史，待澄清任务只复用有界原问题和本轮补充，不把上轮助手猜测当临床事实。A2A 历史有条数、单条字节和总字节预算。

**针对本题的设计展开（原文原理，作为方案解释）：**

分层管理的核心不是“把所有历史保存起来”，而是把对话内容、任务状态、外部结果、长期记忆分开管理，再按当前节点的需要组装 prompt。

我一般会把上下文分成四层：

1. 短期上下文：当前会话最近几轮，用于理解当前对话。

2. 任务状态：intent、slots、plan、当前节点、已完成结果，用于驱动任务继续执行。

3. 外部结果：数据库、RAG、工具调用得到的结果，不直接把原始大对象塞进 prompt，而是先结构化、过滤。

4. 长期记忆：用户偏好、历史结论等跨任务信息，按需检索。

真正送给模型的是 Context Builder 根据“当前步骤契约 + 读权限 + 证据时效 + token 预算”生成的受限视图，而不是底层完整 state。每个关键事实应携带 `source_ref / observed_at / object_version / trust_class`，否则模型看到了内容，系统却无法判断它属于谁、是否过期以及能否支撑当前决策。

**在 MedAgent 中怎么补全：** 进一步做 Context Builder：固定职责与授权先保留，当前目标和关键临床事实次之，然后按任务需要选工具证据，最后才是历史摘要。摘要保留来源、时间和原文引用，压缩策略要用多轮任务完成率和错误继承率验证。

**代码依据：** [backend/a2a_context.py](../../backend/a2a_context.py)、[backend/memory.py](../../backend/memory.py)、[backend/task_context.py](../../backend/task_context.py)

## q-004

### 主问题｜多轮对话如何保持准确？

原文位置：06-上下文与状态管理.md 第 78 行（原件保存在同步前备份）。

**项目口述：** 每轮有 request_id，任务还有 task_id 和 plan_version。员工可选新任务、补充或更正；自动模式只续接待澄清问题，明确新请求切新任务并隔离旧历史。完整更正递增版本、丢弃旧业务输入；只有指代或局部含糊更正时先追问。A2A 返回必须匹配签名委托中的任务、计划版本和步骤，旧结果不能写回新计划。

**针对本题的设计展开（原文原理，作为方案解释）：**

多轮对话不能只靠聊天历史维持准确性，至少要把会话、任务、槽位、历史摘要分开。

- session state：记录当前会话的基础状态。

- 槽位状态：记录当前任务已经确认的业务字段。

- 任务状态：记录当前执行到哪一步、有哪些依赖和中间结果。

- 历史摘要：保存较早对话的压缩信息，避免无限堆积原始消息。

这样做的好处是：即使历史对话很长，主 Agent 也可以先看结构化状态，再按需取历史，而不是依赖模型自己从几十轮聊天里重新推断当前状态。

**在 MedAgent 中怎么补全：** 当前补充仍是有界的原问题与本轮信息组合，并非完整按字段合并。设计上把槽位按任务保存来源和时效，同任务只继承仍适用的字段，明确新值只覆盖对应字段；换患者或换任务不继承业务槽，身份始终重新从可信会话核验。

**代码依据：** [backend/task_context.py](../../backend/task_context.py)、[backend/main.py](../../backend/main.py)、[backend/a2a_server.py](../../backend/a2a_server.py)

## q-007

### 主问题｜上下文过长怎么办？

原文位置：06-上下文与状态管理.md 第 99 行（原件保存在同步前备份）。

**项目口述：** 现有对话保留最近 20 条，A2A 历史单条最多 4 KiB、总预算 16 KiB。新加工具 Observation 有长度上限、内容摘要和 truncated 标记，过长前序证据不会作为完整原文传递。当前没有实现可靠的长期摘要器、历史向量召回和父子块文档压缩。

**针对本题的设计展开（原文原理，作为方案解释）：**

上下文过长时，我不会只采用一种压缩方式，而是做分层处理：

1. 滑动窗口保留最近几轮原文，保证当前对话的细节和语气不丢。

2. 摘要压缩把较早的对话压成任务级摘要，保留脉络而不是保留全部原文。

3. 关键信息抽取把影响后续执行的事实转成结构化字段，例如用户已经确认的时间、金额、对象。

4. 历史检索对于可能影响当前任务、但不适合长期放在 prompt 里的信息，按需取回。

所以真正的策略是“最近内容直接保留，历史内容压缩，关键事实结构化，非必要历史按需检索”。

**在 MedAgent 中怎么补全：** 医疗场景压缩必须保留药名、否定词、单位、参考范围、患者对象和版本来源。大文档放授权产物库，state 保存引用；对截断或摘要缺失的关键依据重新检索。用固定模型做原文与压缩对照，而不是拿模型升级掩盖压缩损失。

**代码依据：** [backend/a2a_context.py](../../backend/a2a_context.py)、[backend/evidence.py](../../backend/evidence.py)、[backend/agents.py](../../backend/agents.py)

### 主问题｜如何防止上下文污染？

原文位置：06-上下文与状态管理.md 第 120 行（原件保存在同步前备份）。

**项目口述：** 每轮有 request_id，任务还有 task_id 和 plan_version。员工可选新任务、补充或更正；自动模式只续接待澄清问题，明确新请求切新任务并隔离旧历史。完整更正递增版本、丢弃旧业务输入；只有指代或局部含糊更正时先追问。A2A 返回必须匹配签名委托中的任务、计划版本和步骤，旧结果不能写回新计划。

**针对本题的设计展开（原文原理，作为方案解释）：**

防止上下文污染，本质上是控制“什么信息有资格进入当前任务”。

我一般做四层：

1. task_id 隔离：不同任务拥有独立的槽位、计划和中间结果。

2. 意图变化检测：用户明显换话题时，不继续沿用上一任务的执行状态。

3. 上下文白名单：每个 Agent 明确哪些字段可以读取，避免无关信息进入 prompt。

4. 冲突检测：当前输入与历史槽位、工具结果不一致时，不直接让模型自行猜，而是进入校验或澄清。

### 主问题｜工具结果错误怎么办？

原文位置：06-上下文与状态管理.md 第 232 行（原件保存在同步前备份）。

**项目口述：** 专科返回辅助回答和脱敏的真实工具 Observation；协调器汇总时优先依据 Observation，并查看截断标记和调用状态。执行前后都限制权限和格式，每个意图检查对应工具覆盖。最终医学结论仍需要医生复核，当前没有独立临床审查模型证明结论正确。

**针对本题的设计展开（原文原理，作为方案解释）：**

工具结果不能因为“工具返回了 JSON”就默认可信。更稳的做法是：调用 → schema 校验 → 业务合理性校验 → 标记可信状态 → 再进入上下文。

### 主问题｜如何压缩上下文？

原文位置：06-上下文与状态管理.md 第 334 行（原件保存在同步前备份）。

**项目口述：** 现有对话保留最近 20 条，A2A 历史单条最多 4 KiB、总预算 16 KiB。新加工具 Observation 有长度上限、内容摘要和 truncated 标记，过长前序证据不会作为完整原文传递。当前没有实现可靠的长期摘要器、历史向量召回和父子块文档压缩。

**针对本题的设计展开（原文原理，作为方案解释）：**

上下文压缩的重点不是单纯“删字”，而是把信息从原始对话形式转换成任务需要的最小信息集合。

常见做法是：

- 长对话先做摘要，保留任务脉络；

- 关键实体和约束抽成结构化字段；

- 已完成任务的细节只保留最终结论和必要引用；

- 历史中偶尔需要的信息不常驻 prompt，而是通过检索按需恢复。

因此压缩后模型看到的应该是“任务状态 + 关键事实 + 当前需要的信息”，而不是一份越来越长的聊天记录。

**在 MedAgent 中怎么补全：** 医疗场景压缩必须保留药名、否定词、单位、参考范围、患者对象和版本来源。大文档放授权产物库，state 保存引用；对截断或摘要缺失的关键依据重新检索。用固定模型做原文与压缩对照，而不是拿模型升级掩盖压缩损失。

### 主问题｜是否有全局 state？

原文位置：06-上下文与状态管理.md 第 463 行（原件保存在同步前备份）。

**项目口述：** 全局层保存当前员工、患者、会话、请求与任务版本，局部层由各专科维护本轮消息和工具轨迹。会话缓存按员工关联会话与患者隔离，并用会话锁阻止同一会话同时执行。专科只返回结果，不能随意覆盖入口的授权上下文。
