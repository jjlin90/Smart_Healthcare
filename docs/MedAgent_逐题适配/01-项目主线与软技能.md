## q-001

### 主问题｜说下你理解的 Agent

原文位置：01-项目主线与软技能.md 第 27 行（原件保存在同步前备份）。

**项目口述：** 我把 Agent 的运行约束落在服务端：任务输入结构、专科和工具白名单、患者授权、模型与工具调用上限、超时熔断、重复调用阻断、工具依据覆盖和持久化完成确认。Prompt 描述职责，代码决定一次动作能否执行。

**针对本题的设计展开（原文原理，作为方案解释）：**

Agent 不是"大模型换了个名字"，而是"大模型 + 工程化闭环"。可以分三层理解：

- 内核层：LLM（大语言模型）负责理解和生成，是"大脑"；

- 能力层：Function Calling 让模型表达结构化调用意图，MCP 标准化外部能力的接入，记忆/状态让模型在多轮中有连续性；

- 工程层：任务拆解、状态管理、结果校验、异常兜底，保证模型不是"裸奔"，而是可控的执行体。

一句话总结：普通大模型调用是"一问一答"，Agent 是"带着目标和工具去完成任务"。面试时先给这个定义，再讲你项目里 Agent 具体做了什么，不要停留在概念层面。

**在 MedAgent 中怎么补全：** 进一步的长任务运行环境需要统一任务预算、持久执行队列、节点状态和验收器。框架能提供组件，业务权限和副作用状态仍由应用负责，不能仅靠装一个框架完成生产治理。

**代码依据：** [backend/agents.py](../../backend/agents.py)、[backend/mcp_security.py](../../backend/mcp_security.py)、[backend/resilience.py](../../backend/resilience.py)

## q-002

### 追问｜Agent 和普通大模型调用有什么区别？

原文位置：01-项目主线与软技能.md 第 39 行（原件保存在同步前备份）。

**针对本题的设计展开（原文原理，作为方案解释）：**

普通大模型调用：输入 prompt（提示词） → 输出文本，无状态、无工具、无循环，一轮结束。Agent：有目标、有循环的执行体——会拆任务、按需调工具、根据工具结果调整下一步，直到完成或触发兜底。可以举三个直观区别：(1) 大模型调用不会主动查数据库，Agent 会；(2) 大模型调用多轮之间互相不记得，Agent 有状态管理；(3) 大模型调用失败就失败，Agent 会重试、降级。本质区别是"有没有自主执行的闭环"。

**在 MedAgent 中怎么补全：** 进一步的长任务运行环境需要统一任务预算、持久执行队列、节点状态和验收器。框架能提供组件，业务权限和副作用状态仍由应用负责，不能仅靠装一个框架完成生产治理。

## q-003

### 追问｜Agent 是否具备任务理解、任务拆解、工具调用、状态管理、结果校验、异常兜底？

原文位置：01-项目主线与软技能.md 第 43 行（原件保存在同步前备份）。

**项目口述：** 我把 Agent 的运行约束落在服务端：任务输入结构、专科和工具白名单、患者授权、模型与工具调用上限、超时熔断、重复调用阻断、工具依据覆盖和持久化完成确认。Prompt 描述职责，代码决定一次动作能否执行。

**针对本题的设计展开（原文原理，作为方案解释）：**

这是面试官最想听的框架，逐条讲：

- 任务理解：意图识别 + 槽位抽取，把用户模糊输入变成结构化任务；

- 任务拆解：计划生成，把任务拆成带依赖关系的步骤；

- Function Calling：按 schema（参数结构）生成工具调用意图，由应用侧校验并执行；

- MCP：通过标准协议接入 Tools、Resources 和 Prompts 等外部能力；

- 状态管理：全局 state（状态）存任务级信息，节点间传递；

- 结果校验：审查节点检查事实一致性、格式、安全；

- 异常兜底：重试、降级、转人工，保证链路不断。

这些是评估工程成熟度的检查项，不是 Agent 必须同时具备的定义。最小 Agent 可以只执行有界的模型—工具反馈循环；是否需要规划、长期记忆或独立审查，应由任务决定。

**在 MedAgent 中怎么补全：** 进一步的长任务运行环境需要统一任务预算、持久执行队列、节点状态和验收器。框架能提供组件，业务权限和副作用状态仍由应用负责，不能仅靠装一个框架完成生产治理。

## q-004

### 主问题｜什么是 Multi-Agent？

原文位置：01-项目主线与软技能.md 第 57 行（原件保存在同步前备份）。

**项目口述：** 项目是一个主协调器加三个专科：SymptomAgent 做症状评估、院内分诊和转诊协同；DrugAgent 查药品和审核用药；GuideAgent 处理指南、检验、报告、随访与临床知识。Planning、SafetyGuard、DomainGuard 是协调流程中的职责模块，没有另建检索、通知或独立审查服务。

**针对本题的设计展开（原文原理，作为方案解释）：**

Multi-Agent 是把一个复杂任务拆给多个职责不同的 Agent 协作完成。典型结构是"主 Agent 调度、子 Agent 执行"：主 Agent 负责意图识别、计划生成、路由分发、结果聚合；子 Agent 各自负责一类能力，比如检索 Agent、查询 Agent、工具 Agent、审查 Agent。可以类比：单 Agent 是"全栈工程师"，Multi-Agent 是"项目经理 + 专业团队"——前者什么都会一点但深度有限，后者各司其职、职责清晰。面试时先讲这个结构，再用你项目里的实际分工举例，别只给定义。

**在 MedAgent 中怎么补全：** 按业务目标、可信数据和工具权限划分，而不是按每个 API 拆 Agent。增加角色前，在同一任务集上比较完成率、交接损失、耗时与成本；不能假设多角色天然准确。

**代码依据：** [backend/agents.py](../../backend/agents.py)、[backend/a2a_server.py](../../backend/a2a_server.py)

## q-005

### 追问｜多 Agent 和单 Agent 有什么区别？

原文位置：01-项目主线与软技能.md 第 63 行（原件保存在同步前备份）。

**项目口述：** 项目是一个主协调器加三个专科：SymptomAgent 做症状评估、院内分诊和转诊协同；DrugAgent 查药品和审核用药；GuideAgent 处理指南、检验、报告、随访与临床知识。Planning、SafetyGuard、DomainGuard 是协调流程中的职责模块，没有另建检索、通知或独立审查服务。

**针对本题的设计展开（原文原理，作为方案解释）：**

单 Agent 由一个执行体处理任务，也可以按步骤筛选工具和隔离权限。多 Agent 按职责拆成多个执行体，可以分别配置提示词、工具与运行状态；同样需要执行层权限校验和状态合并规则。设计时比较四个维度：

- 职责：单一职责 vs 全能型——全能 prompt 越长越互相干扰；

- 权限：比较任务级工具范围与执行点校验；单 Agent 和多 Agent 都能实现最小权限，角色拆分本身不是安全边界；

- 状态：比较本轮状态隔离、共享事实与合并规则；独立执行体也可能共享历史或患者事实，不能仅看 Agent 数量；

- 可定位性：比较步骤记录、工具轨迹与恢复契约；单 Agent 也可以定位和重试具体调用，多 Agent 不会自动获得这些能力。

回答时用这四个维度对比，比背定义有说服力。

**在 MedAgent 中怎么补全：** 按业务目标、可信数据和工具权限划分，而不是按每个 API 拆 Agent。增加角色前，在同一任务集上比较完成率、交接损失、耗时与成本；不能假设多角色天然准确。

**代码依据：** [backend/agents.py](../../backend/agents.py)、[backend/a2a_server.py](../../backend/a2a_server.py)

## q-006

### 追问｜为什么不把所有能力都写在一个 Agent 里？拆分依据是什么？

原文位置：01-项目主线与软技能.md 第 74 行（原件保存在同步前备份）。

**项目口述：** 项目是一个主协调器加三个专科：SymptomAgent 做症状评估、院内分诊和转诊协同；DrugAgent 查药品和审核用药；GuideAgent 处理指南、检验、报告、随访与临床知识。Planning、SafetyGuard、DomainGuard 是协调流程中的职责模块，没有另建检索、通知或独立审查服务。

**针对本题的设计展开（原文原理，作为方案解释）：**

拆分依据是：业务复杂、工具多、权限不同、任务链路长。全塞一个 Agent 的代价可以逐条讲：

1. prompt 越长越互相干扰——一段 prompt 管五个业务域，模型注意力被稀释，意图识别准确率直接下降；

2. 工具越多选错率越高——几十个工具平铺给模型，选错概率随工具数上升；

3. 如果一次暴露全部工具，会增大权限面；单 Agent 也可按任务和步骤分别授予读写权限；

4. 缺少步骤记录和恢复契约时，失败难定位；这取决于执行器和可观测设计，不是单 Agent 的必然限制。

拆分之后，这四类问题分别变成可独立开发、独立测试、独立降级的模块。

**在 MedAgent 中怎么补全：** 按业务目标、可信数据和工具权限划分，而不是按每个 API 拆 Agent。增加角色前，在同一任务集上比较完成率、交接损失、耗时与成本；不能假设多角色天然准确。

**代码依据：** [backend/agents.py](../../backend/agents.py)、[backend/a2a_server.py](../../backend/a2a_server.py)
