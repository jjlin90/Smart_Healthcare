## q-007

### 主问题｜子 Agent 之间如何通信？

原文位置：04-子Agent与任务编排.md 第 92 行（原件保存在同步前备份）。

**项目口述：** 主协调器用 python-a2a 向三个专科发送 task、patient_id、有界历史和原始任务。短期签名委托绑定员工、患者、请求、目标专科和工具范围，并用摘要绑定原始输入。专科重读患者档案，返回回答、调用轨迹、脱敏工具 Observation 以及 task_id、plan_version、step_id；主协调器检查身份、格式与版本。

**针对本题的设计展开（原文原理，作为方案解释）：**

子 Agent 的通信方式主要看两个维度：是否需要实时返回，以及通信双方希望保持多强的耦合。

同步场景可以使用 HTTP/RPC，由主 Agent 发起调用并等待结果；异步场景可以通过消息队列或事件总线解耦，让发送方不必一直等待。共享状态适合在同一个任务上下文中传递中间结果，但需要严格限制写入范围；A2A（Agent-to-Agent，Agent 间通信协议）或自定义通信协议则重点解决 Agent 之间消息格式统一的问题。

在当前这种“主 Agent 统一调度”的架构里，通常不会让子 Agent 自由互相调用，而是由主 Agent 负责路由和协调。这样做的核心价值不是通信更简单，而是让调用关系、权限、超时、重试和故障定位都集中可控。

无论采用哪种通信方式，消息都应该带 `task_id / trace_id / plan_version / step_id / attempt_id`，并明确 source、target、input、context、status 等字段。这样一个任务跨多个 Agent 后，仍然可以还原完整执行链路并拒绝旧计划、旧尝试的迟到结果。

## q-010

### 主问题｜子 Agent 有自己的状态吗？

原文位置：04-子Agent与任务编排.md 第 137 行（原件保存在同步前备份）。

**项目口述：** 全局层保存当前员工、患者、会话、请求与任务版本，局部层由各专科维护本轮消息和工具轨迹。会话缓存按员工关联会话与患者隔离，并用会话锁阻止同一会话同时执行。专科只返回结果，不能随意覆盖入口的授权上下文。

**针对本题的设计展开（原文原理，作为方案解释）：**

有，但建议做“任务级状态”和“Agent 级状态”两层隔离。

全局 state 保存主流程真正需要共享的信息，例如用户输入、intent、slots、plan、各节点的执行状态以及最终结果；局部 state 保存某个 Agent 的中间变量、工具调用参数、检索结果、局部重试次数等，不应该把所有细节都污染到全局状态中。

这样设计有两个好处：第一，主 Agent 可以看到任务全貌并做下一步调度；第二，子 Agent 的内部实现可以独立变化，不会因为修改一个局部字段就影响其他 Agent。

更重要的是状态更新要可控。尤其是并行执行时，不能让多个 Agent 随意修改同一个字段，而应该按命名空间或 step_id 写入自己的结果，再由主 Agent 做合并。对于需要断点续跑的生产系统，还应该给关键步骤保存 checkpoint，而不是只把状态存在进程内存里。

**在 MedAgent 中怎么补全：** 独立档案编辑已要求先读取 revision，再以 expected_revision 保存，服务端核对内容快照并以 SQL 比较全部原字段后更新；冲突返回 409，重载并核对后再保存。会话锁和档案保护是两层机制。图框架的 Reducer 可以管理 state，但不替代数据库并发与写操作幂等。

**代码依据：** [backend/memory.py](../../backend/memory.py)、[backend/task_context.py](../../backend/task_context.py)、[backend/main.py](../../backend/main.py)

## q-013

### 主问题｜子 Agent 失败怎么办？

原文位置：04-子Agent与任务编排.md 第 157 行（原件保存在同步前备份）。

**项目口述：** 把权限失败、参数缺失、依赖故障和写入未知分开。权限失败拒绝；缺信息先询问；安全只读医院查询对瞬时网络错误及 429/部分 5xx 最多三次指数退避，转诊写调用不自动重试；连续依赖失败进入熔断。专科或工具失败不会被包装成成功答案。

**针对本题的设计展开（原文原理，作为方案解释）：**

子 Agent 失败不能简单理解成“重试一次”。生产环境里要先判断失败属于哪一类，再决定处理策略。

可以把失败大致分成四类：瞬时故障，例如网络抖动、限流、临时超时，适合有限次数重试；持续性故障，例如依赖服务长期不可用，应该快速失败并切换降级路径；业务性失败，例如参数不合法、数据不存在，通常重试没有意义，应重新补槽、改路由或直接返回业务错误；副作用已经发生但后续失败，则要考虑回滚或补偿。

因此主 Agent 接收到的最好不是简单的“success=false”，而是统一的错误码、错误类型、是否可重试、是否可补偿、已执行到哪一步等结构化信息。这样它才能判断是 retry（重试）、replan（重规划）、skip（跳过）、rollback（回滚）还是人工接管，而不是再次调用模型猜原因。

## q-028

### 主问题｜并行结果怎么合并？

原文位置：04-子Agent与任务编排.md 第 275 行（原件保存在同步前备份）。

**项目口述：** 带依赖的计划按依赖调度，独立只读步骤用 asyncio.gather 同批执行；批准了写动作时整个计划保持串行。前序的脱敏工具依据在预算内传给依赖节点，过长时明确提示重新查询，不截断后冒充完整资料。同批出错仍等待在途调用结束，再传播失败，避免解锁后留后台动作。

**针对本题的设计展开（原文原理，作为方案解释）：**

并行执行真正难的地方不在“同时调用”，而在于多个结果到齐之后怎么判断整个任务是否成功。

通常会定义一个聚合策略：哪些子任务是必须成功的，哪些是可选的；等待多久算超时；部分成功时是否允许生成最终结果。不能所有任务都简单地使用“全部成功才成功”。

例如三个独立数据源查询中，核心数据库是必选项，推荐数据源只是增强项，那么核心查询失败应该阻止最终答案，而增强项失败可以标记为“部分数据不可用”。因此并行节点最好为每个 step 定义 status、required、timeout、fallback 等元数据，聚合器再根据策略决定继续、降级还是失败。

同时要注意超时后的迟到结果：如果主流程已经基于降级结果完成，迟到结果不能再次无条件覆盖最终结果，需要通过 task_id / step_id / version 控制结果写入。

**在 MedAgent 中怎么补全：** 并发只解决互不依赖的 IO 等待，不能把串行数据依赖打散。CPU 推理要在线程或独立模型服务中运行，并控制 GPU 与连接池并发；后台长任务应采用持久队列和状态查询，不能把 async 函数当成可靠任务队列。

原文位置：04-子Agent与任务编排.md 第 375 行（原件保存在同步前备份）。

**项目口述：** 对一般启用 GIL 的 CPython，线程适合等待网络 IO，CPU 密集的 Python 计算通常用进程或专门推理服务；PyTorch 等原生算子与 GPU 执行还取决于底层实现。Lock 不可同线程重复获取，RLock 可重入，但异步协程临界区应用 asyncio.Lock，不能拿线程锁替代。项目用 to_thread 隔离同步客户端和本地推理，不声称线程等于多核推理加速。

### 主问题｜Plan-and-Execute 怎么做？

原文位置：04-子Agent与任务编排.md 第 420 行（原件保存在同步前备份）。

**项目口述：** 简单明确任务直接匹配专科；多意图或复杂任务由 Planner 生成最多三步计划。服务端检查专科白名单、去重、意图要求的专科覆盖以及依赖只能指向已列出的前序步骤。结构或依赖非法时改用确定性短链，不能让模型添加未注册服务。

**针对本题的设计展开（原文原理，作为方案解释）：**

**在 MedAgent 中怎么补全：** 计划能表达依赖与独立查询，当前没有无限自主改计划：只读依据缺失最多一次重新识别，普通工具故障不等于意图错误。若扩展更多节点，增加节点超时、验收条件、输入引用和版本化节点状态，同时限制重规划预算。

### 主问题｜执行过程中能否动态改计划？

原文位置：04-子Agent与任务编排.md 第 483 行（原件保存在同步前备份）。

**项目口述：** 我按识别前、执行中和执行后处理：前三路发现分歧时二次识别；执行前校验关键参数和权限；执行后检查每个意图是否有对应的成功工具依据，例如病史读取不能代替药品说明书查询。只读任务覆盖不匹配时最多复核并重路由一次；批准写动作或出现写调用时禁止自动重跑。

**针对本题的设计展开（原文原理，作为方案解释）：**

例如计划原本是 A → B → C，A 已成功，B 返回的数据说明原来的 C 不再适用，这时应该保留 A 的结果，只重新规划 B 之后未完成的部分。这样既节约模型调用，也避免已经完成的步骤被重复执行。

replan 最好有触发条件，例如关键结果偏离预期、发现新信息、依赖服务返回新的可用能力、原计划中的 Agent 不可用等。同时需要限制 replan 次数，防止出现“规划失败 → 重规划 → 再失败”的循环。

因此动态规划和稳定执行并不矛盾：规划可以动态，但需要在明确的版本边界上交接。

`publish_if_version` 同时保证新版本递增、可复用产物显式登记、受影响的确认失效及派发事件可靠记录；不能先更新数据库再无保障地发一条队列消息。正在执行写操作的发布与执行入口还需通过服务端状态协调，避免检查后又发起旧操作。

**在 MedAgent 中怎么补全：** 工作台已能提交意图纠错，服务端重新核验患者权限和原请求所属员工，保存为待临床复核记录，不自动作为训练标签。完整闭环还需要结论与目标的语义核验、复核工单及标注发布流程。工具成功不是医学正确证明；写入不明先查状态、核对 HIS，跨系统补偿取决于医院接口。

鉴权应该由服务层完成，而不是依靠消息里的 source 字段自我声明；超时应该按调用跳数和整个任务分别控制；幂等应该确保同一个 task/step 重复投递时不会造成重复副作用；失败也应该通过统一 error schema 回传，让上游知道“失败是临时的还是业务性的”。

所以通信协议设计的重点并不只是字段多少，而是让消息具备可追踪、可重试、可幂等和可恢复的能力。

**在 MedAgent 中怎么补全：** 不用 A2A 也可通过进程内异步函数、自定义 HTTP 或消息队列分派，核心仍是任务契约、授权、超时和业务状态。当前统一 deadline_at 通过签名委托传到专科和 MCP，新调用只用剩余预算；服务是主从式，专科不能任意互相调用。队列、回调和长期任务是扩展项。

## q-104

### 主问题｜怎样从系统角度评价多 Agent 是否值得？

原文位置：04-子Agent与任务编排.md 第 1057 行（原件保存在同步前备份）。

**项目口述：** 项目是一个主协调器加三个专科：SymptomAgent 做症状评估、院内分诊和转诊协同；DrugAgent 查药品和审核用药；GuideAgent 处理指南、检验、报告、随访与临床知识。Planning、SafetyGuard、DomainGuard 是协调流程中的职责模块，没有另建检索、通知或独立审查服务。

**针对本题的设计展开（原文原理，作为方案解释）：**

先定义端到端任务成功，再看拆分是否改善它。Agent 数量、消息数量和单节点成功率都不是最终目标；一个局部表现更好的 Agent，也可能因上下文交接错误使整个任务变差。

本题只回答“是否值得拆成多 Agent”的架构判断；项目级指标定义、测试集与抽检方法以 对应主题 为准，稳定性专项指标见 对应主题。

**在 MedAgent 中怎么补全：** 按业务目标、可信数据和工具权限划分，而不是按每个 API 拆 Agent。增加角色前，在同一任务集上比较完成率、交接损失、耗时与成本；不能假设多角色天然准确。
