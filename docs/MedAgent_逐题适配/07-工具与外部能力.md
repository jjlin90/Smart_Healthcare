## q-001

### 主问题｜LangChain 常用工具有哪些？

原文位置：07-工具与外部能力.md 第 25 行（原件保存在同步前备份）。

**项目口述：** 模型通过 Function Calling 选择工具并生成结构化参数，LangChain 的 MCPAdapter 和 FastMCP 客户端通过 MCP 调用工具服务。FastMCP 注册 14 个工具，包括真实医院查询以及本地病史、辅助材料存储；服务端再次检查委托、员工状态、患者范围和写动作权限。两者在同一链路中使用。

**针对本题的设计展开（原文原理，作为方案解释）：**

如果面试官沿用旧版口径，可以说自己用过 Tool、PromptTemplate、Retriever、Memory、AgentExecutor 和 OutputParser，但要主动补充：这不再是 LangChain 1.x 的权威“六大组件”分类。

当前 LangChain 1.x 将 `create_agent` 作为标准 Agent 入口，其底层运行在 LangGraph 上。面试时更适合按实际工程边界讲：

- Model：推理与工具选择；

- Tools：向模型描述可用能力，真实执行仍由应用控制；

- Middleware：动态模型/工具选择、上下文工程、摘要和护栏（guardrails）；

- State / Context：管理执行状态和当次模型可见信息；

- Structured Output：将结果约束为应用可验证的契约；

- LangGraph runtime：承载节点、循环、持久化和人工介入。

旧 chains、部分 retrievers 和旧版 Agent 实现已迁入 `langchain-classic`，所以不能再用旧导入路径当成当前默认架构。[LangChain：What's new in LangChain v1](https://docs.langchain.com/oss/python/releases/langchain-v1)

**在 MedAgent 中怎么补全：** 工具注册要同时维护参数、输出、错误、权限、读写属性和版本契约；新增工具先做契约测试和权限回归，再开放给对应专科。不能把工具描述中的 readOnlyHint 当真正的服务端授权。

## q-004

### 主问题｜LangGraph 和 LangChain Agent 区别？

原文位置：07-工具与外部能力.md 第 50 行（原件保存在同步前备份）。

**项目口述：** 简单明确任务直接匹配专科；多意图或复杂任务由 Planner 生成最多三步计划。服务端检查专科白名单、去重、意图要求的专科覆盖以及依赖只能指向已列出的前序步骤。结构或依赖非法时改用确定性短链，不能让模型添加未注册服务。

**针对本题的设计展开（原文原理，作为方案解释）：**

LangChain 更偏“组件与调用链抽象”，提供 Tool、Retriever、Prompt 等可复用组件；LangGraph 更偏“有状态的流程编排”，通过节点、边和 State 描述任务如何执行。

简单任务可以直接用 LangChain 的组件组合起来，但当系统出现多 Agent、条件分支、循环、人工介入、Checkpoint、失败恢复时，仅靠自由调用链很难控制执行状态。此时把流程显式建模成状态图更容易调试和恢复。

所以我不会把二者理解成完全替代关系，而是：LangChain 更像能力组件层，LangGraph 更像复杂任务编排层。

**在 MedAgent 中怎么补全：** 计划能表达依赖与独立查询，当前没有无限自主改计划：只读依据缺失最多一次重新识别，普通工具故障不等于意图错误。若扩展更多节点，增加节点超时、验收条件、输入引用和版本化节点状态，同时限制重规划预算。

## q-010

### 主问题｜MCP 是什么？

原文位置：07-工具与外部能力.md 第 96 行（原件保存在同步前备份）。

**项目口述：** 模型通过 Function Calling 选择工具并生成结构化参数，LangChain 的 MCPAdapter 和 FastMCP 客户端通过 MCP 调用工具服务。FastMCP 注册 14 个工具，包括真实医院查询以及本地病史、辅助材料存储；服务端再次检查委托、员工状态、患者范围和写动作权限。两者在同一链路中使用。

**针对本题的设计展开（原文原理，作为方案解释）：**

MCP 可以理解成一层标准化的上下文与外部能力接入协议：外部系统按统一方式暴露能力，Host（宿主）/Client（客户端）按协议发现并使用它们。

它解决的核心问题不是“模型怎么决定调用”，而是“工具怎么标准化接入 Agent 生态”。例如一个 MCP Server 可以统一暴露数据库、文件系统或业务 API 的能力，客户端不需要为每个外部系统重新设计一套专用适配方式。

基础原语不只有 Tools：

- Tools：可调用的动作，包含名称、描述和输入/输出 schema；

- Resources：可按 URI 读取的上下文或数据；

- Prompts：服务端暴露的可复用提示模板。

工程价值是让能力描述、发现和交互接口标准化，并让 Host、Client 与 Server 的责任分开。但 MCP 本身不等于权限系统或业务安全系统，真正高风险操作仍要在服务端做鉴权、参数和业务规则校验。[MCP 官方文档](https://modelcontextprotocol.io/docs/getting-started/intro)

**在 MedAgent 中怎么补全：** 工具注册要同时维护参数、输出、错误、权限、读写属性和版本契约；新增工具先做契约测试和权限回归，再开放给对应专科。不能把工具描述中的 readOnlyHint 当真正的服务端授权。

### 主问题｜MCP 和 Function Calling 区别？

原文位置：07-工具与外部能力.md 第 120 行（原件保存在同步前备份）。

**项目口述：** 模型通过 Function Calling 选择工具并生成结构化参数，LangChain 的 MCPAdapter 和 FastMCP 客户端通过 MCP 调用工具服务。FastMCP 注册 14 个工具，包括真实医院查询以及本地病史、辅助材料存储；服务端再次检查委托、员工状态、患者范围和写动作权限。两者在同一链路中使用。

**针对本题的设计展开（原文原理，作为方案解释）：**

两者解决的是不同层的问题。

Function Calling 解决“模型如何表达一次工具调用”，重点是模型侧的结构化调用接口，例如工具名和 JSON 参数。

MCP 解决“外部工具如何以统一方式被发现、描述和接入”，重点是工具接入层。

### 主问题｜你的 RAG 跟 Agent 是怎么配合的？

原文位置：07-工具与外部能力.md 第 233 行（原件保存在同步前备份）。

**项目口述：** MedAgent 目前通过 GuideAgent 的 search_guidelines、get_treatment_protocol 等工具调用医院知识接口，不是在这个仓库内完成切块、建向量库和 rerank。BGE-M3 在本项目用于意图原型匹配。简历里的 med_rag 是独立项目，不能把它的指标直接算作 MedAgent 结果。

**针对本题的设计展开（原文原理，作为方案解释）：**

RAG 在 Agent 系统里通常不是独立于 Agent 的整套应用，而是一种可以被调度的知识能力。

设计上可以根据复杂度选择封装方式：

- 简单 RAG：query → 向量检索 → 返回 topK（前 K 条），适合直接做 Tool。

- 复杂 RAG：包含 query 改写、多路召回、rerank（重排）、过滤、压缩、引用校验等步骤，更适合封装成独立的 Retrieval Agent。

主 Agent 主要负责判断“这个问题需不需要知识检索”；RAG 负责回答“去哪里找、怎么找、哪些候选证据相关”，并返回来源、版本和相关性分数。结果是否足以支撑结论、来源是否具有业务权威性，仍由验收与业务策略判断。

这样做的好处是把任务路由和检索算法解耦，后续修改召回、重排策略时，不需要修改主 Agent 的整体业务流程。

**在 MedAgent 中怎么补全：** 接入 RAG 时将授权后的医学检索封装为 GuideAgent 工具，返回原文片段、文档标识、页码、版本日期和检索状态；按员工和院内数据范围过滤后再召回。正常空结果可改写或询问，依赖故障停止生成，缺证据不让模型凭记忆替代。
